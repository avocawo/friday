## Установка

1. Клонируйте Friday и добавьте `bin` в `PATH` или задайте `FRIDAY_BIN`.
2. Установите нужные агентам CLI: Claude Code (`claude`) для моделей Anthropic и Z.ai, Codex CLI (`codex`) для моделей OpenAI. Войдите в них как обычно.
3. Для гейта и браузерной приёмки установите Docker. Для браузерной приёмки нужен Chrome с отладочным портом 9333 и открытая сессия со входом в стенд.
4. Состояние хранится в `~/.local/share/friday` (переопределяется через `FRIDAY_HOME`). Профили и секреты в репозиторий не попадают: папка `profiles/` в `.gitignore`.

### Плагин для Codex и Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

Плагин учит агента читать `status` и `plan`, а запуск задачи, утверждение и решения оставляет вам.

## Как идёт задача

1. **`start`** создаёт ветку `friday/KEY` от свежего `origin/<base_branch>` и рабочую копию, фиксирует раскладку ролей и пишет план: вехи из 2–5 этапов, файлы, оценку объёма, кодовые и браузерные критерии, выжимку правил проекта для исполнителя. План проверяется без модели (объём, файлы, порядок, критерии), потом его проверяет модель другого вендора, и планировщик один раз отвечает на замечания: принимает каждое или отклоняет с обоснованием.
2. **`plan`** показывает план, вопросы, отклонённые замечания и пересечения файлов с другими активными задачами.
3. **`approve`** утверждает план и запускает конвейер в фоне (`--no-run` — только утвердить, потом `run`).
4. **Веха.** Исполнитель работает в одной сессии на веху и коммитит каждый этап. Гейт запускается на коммите; при провале исполнитель получает только упавшие секции лога. Ревью вехи смотрит дифф этой вехи вместе с результатом гейта. Блокирующие находки исполнитель исправляет или оспаривает; оспоренные уходят вам. Вехи с интерфейсом проходят браузерную приёмку в изолированном preview. После двух провалов подряд веху берёт модель уровнем выше в новой сессии.
5. **Финал.** Финальное ревью и слепая проверка всего диффа идут параллельно; блокирующие находки получают один раунд исправлений.
6. **Черновой MR** открывается, если в профиле задан `delivery`; иначе его текст сохраняется в `merge-request.md` в папке задачи.

Конвейер останавливается только когда гейт так и не прошёл, исполнитель ничего не сделал, среда недоступна или кончились модели, разрешённые правилами. Разногласия ревью его не останавливают.

`decide KEY name "text" --reopen M2` записывает ваше решение. Переоткрываются только названные вехи и зависящие от них; без `--reopen` решение учитывают следующие вехи. `resume` продолжает остановленную или упавшую задачу, `stop` останавливает идущую: агенты завершаются вместе с дочерними процессами.

Чтобы вернуть план до одобрения, запишите, что изменить, через `decide` и выполните `replan KEY`. Планировщик переделывает ждущий план в новой сессии; причина правки — решения, записанные после этого плана. Новый план снова проходит проверки и ревью модели другого вендора и затем ждёт вашего одобрения, даже при `approval: auto`. Карточка задачи, её история и расходы сохраняются. Сам `decide` модель не запускает, поэтому можно записать несколько решений и перепланировать один раз. Если перепланирование упало, прежний план по-прежнему ждёт одобрения. `--brief` заново передаёт постановку задачи, если задача начата до того, как Friday стал её хранить.

## Профиль

Профиль — JSON-файл. Ключ `extends` подключает другой профиль (например, общий каталог моделей); пути считаются от файла профиля.

| Ключ | Назначение |
| --- | --- |
| `name`, `repository` | Имя и путь к репозиторию проекта |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | Откуда и где создавать ветку задачи; шаблон по умолчанию `friday/{key}`, раскладка `key` или `branch` |
| `models`, `roles` | Каталог моделей и предпочтения по ролям (ниже) |
| `engineering_policy` | Правила для планировщика и ревью |
| `rules_docs` | Документы с правилами проекта, по которым Friday один раз делает дайджест для планировщика и ревьюера плана (по умолчанию `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). Дайджест хранится по хешу содержимого и переиспользуется задачами, пока документы не меняются; планировщик не читает их целиком |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | Карта репозитория в промпте планировщика и ревьюера плана, чтобы они не разведывали структуру вызовами инструментов. `none` (по умолчанию) — без карты. `builtin` — отслеживаемые файлы с числом строк. `graphify` — плюс символы каждого файла и сколько файлов его импортируют, по графу [graphify](https://github.com/Graphify-Labs/graphify) (`uv tool install 'graphifyy[mcp]==0.9.100'`; он только разбирает код, модель не используется; граф лежит в `FRIDAY_HOME/maps`, не в репозитории). На замере CS-2 карта не удешевила планирование (без карты $6.19, `builtin` $7.08, `graphify` $7.97 — по одному прогону), поэтому выключена по умолчанию. Карта кэшируется по коммиту. Если она длиннее `repo_map_budget` символов (60000), её сначала сокращают, убирая символы, потом сворачивая папки. `repo_map_mcp: true` (только с `graphify`) даёт обеим ролям запросы к графу: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`; на Codex не проверено вживую. Ревьюер плана получает текущий текст файлов, названных в плане (до 40000 символов) |
| `approval` | `owner` (по умолчанию) — план ждёт `approve`. `auto` — план утверждается сам после проверки и конвейер сразу запускается; в журнале отмечено, что план утверждён автоматически |
| `limits` | `stage_files` и `stage_lines` — лимиты этапа (10 и 500) |
| `worktree_setup` | Команды, которые Friday запускает в новой рабочей копии до планирования (зависимости и подобное): массивы аргументов с подстановкой `{repository}` и `{worktree}`; должны быть повторяемыми. Пример для npm на macOS: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Команды, которые исполнитель может запускать сам, в точной форме: `"python3 -m pytest"`, а не `python` |
| `executor_deny_read` | Дополнительные пути, которые shell исполнителя не может читать |
| `milestone_rounds` | Сколько раундов исполнителя получает веха (4) |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | Команда проверки в Docker; `git-diff` сравнивает с базой задачи |
| `environment_errors` | Шаблоны строк лога, означающих сбой среды, а не кода |
| `browser`, `preview`, `behavior_test_policy` | Стенд, preview и правила браузерной приёмки |
| `tracker` | Yandex Tracker (API или MCP), из него читается описание задачи |
| `journal` | Куда писать журнал задачи: `[{"kind": "markdown", "dir": "..."}, {"kind": "jsonl", "dir": "..."}]`; `journal_dir` — короткая запись для одного markdown-журнала |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` и ключ `github.repository` или `gitlab.base_url` + `gitlab.project` |

### Модели и роли

```json
"models": {
  "fable": {"model": "claude-fable-5-1", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver` — чем запускается модель: `claude` или `codex`. Z.ai идёт через Claude Code; токен читается из файла, доступного только владельцу.
- `tier` — `frontier`, `strong` или `efficient`; `strength` упорядочивает модели внутри уровня.
- `effort` — глубина рассуждения (`low` … `max`); одну модель можно описать несколько раз с разным значением.
- `scarce` — дорогая модель: используется один раз на задачу, если правила позволяют обойтись без неё.
- `price` — цена за миллион токенов по видам (`input`, `output`, `cache_read`, `cache_write`) для оценки расхода, когда вендор цену не сообщает.

Роли: `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. Списки в `roles` — предпочтения: если подходящей модели в списке нет, Friday берёт другую из каталога. Жёсткие правила: код смотрят только `frontier`-модели, ревьюер не слабее автора работы, слепую проверку делает не автор кода. Мягкие правила (по порядку): не та же модель, что автор; дорогая модель один раз; другой вендор; слепую проверку делает не автор плана. Мягкое правило можно нарушить, только если иначе нельзя, и нарушение записывается в историю задачи.

Пример раскладки ролей — в [examples/models.json](../../examples/models.json).

## Журнал

Карточка задачи — единственный источник правды. Журналы её отображают и обновляются сами после значимых событий: план готов и утверждён, веха готова или упала, решение владельца, финальное ревью, MR, остановка. Вручную их обновляет `friday journal KEY`.

- `markdown` — страница `KEY.md` и общая страница «Friday — сейчас» со всеми задачами. Для Obsidian укажите папку хранилища: у страниц есть front matter (ключ, состояние, расход, тег `friday`), а задачи связаны wiki-ссылками. На странице задачи — план с допущениями и несогласованными замечаниями, вехи со сводкой исполнителя и коммитами, спорные находки, решения, расход по ролям и хронология.
- `jsonl` — все события задачи для анализа в таблицах или дашбордах.

Шаблоны — Markdown с подстановками `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. Friday берёт шаблон из поля `template` получателя, затем из `.friday/task.md` в репозитории проекта, затем встроенный ([friday/templates](../../friday/templates)). Текст между `<!-- friday:notes -->` и `<!-- /friday:notes -->` — ваш: он сохраняется при каждом обновлении. Страницу, которую написал не Friday, он не перезаписывает.

## Настройки машины

`FRIDAY_HOME/machine.json` задаёт общие ресурсы для всех задач:

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

По умолчанию одновременно идут один гейт и два браузера, вендоры не ограничены. Квоты вендоров учитываются автоматически: запуск, упёршийся в лимит, записывает, когда квота вернётся, и до этого момента вендор при подборе моделей пропускается.

## Границы

- **Песочница исполнителя.** Shell исполнителя (Claude Code) работает в песочнице: без сети, без чтения `~/.ssh`, `~/.aws`, `~/.config` и подобных, запись только в рабочую копию и временную папку, без запуска вне песочницы. Команды вне `executor_commands` и не являющиеся git-командами отклоняются. Codex работает в своей песочнице с теми же границами.
- **Ревьюеры** только читают. Слепая проверка запускается в пустой папке.
- **Гейт** работает в контейнере без сети, на снимке коммита, смонтированном только для чтения.
- **Браузер** получает только инструменты Friday для одного preview; обход авторизации и чтение заголовков авторизованных запросов запрещены.
- **Публикация.** Friday пушит только ветку своей задачи и открывает только черновой MR/PR. Он не перезаписывает чужую ветку, не сливает и не развёртывает.
- **Что ещё не проверено вживую:** роли на Codex, браузерная приёмка и публикация в GitLab проверены только тестами с фейками.
