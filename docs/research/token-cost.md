# Расход токенов и денег в Friday: где уходит и как сократить

Дата: 03.11.2026. Материал: события и транскрипты карточки CS-1 (`~/.local/share/friday/cards/CS-1`, 13 запусков 02.11), начало карточки CS-2 (идёт сейчас, профиль `cs-map-none`), код `friday/plan.py`, `milestone.py`, `final.py`, `runner.py`, `models.py`, `card.py` и официальная документация (ссылки в конце).

## Главное

1. **Больше половины денег (57%) — запись в кэш с TTL 1 час.** Claude Code на подписке пишет кэш основной сессии с TTL 1 ч по цене 2× от входа. Запуски Friday длятся 1–10 минут, а паузы между вызовами API внутри сессии обычно около минуты, им хватает 5 минут по цене 1,25×. Переменная окружения `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` в `runner.py` сэкономила бы на CS-1 около $7,2 (21%).
2. **Fable 5.1 обошёлся в 75% расхода CS-1, хотя в профиле стоит только на проверке плана.** M2 по правилу «сложная веха» отдали Opus, и после этого три разных правила подняли проверки до Fable:
   - браузер: жёсткое правило «не слабее автора» (Sonnet — tier strong, автор Opus — frontier). Три запуска стоили $9,35 вместо примерно $2,2 на Sonnet;
   - review M2 и final-review: мягкая сортировка `closeness` (Opus «проверял бы себя», а это ранжируется хуже повторного использования дефицитного Fable);
   - blind-code: жёсткое правило «не модель автора кода».
3. **25% расхода CS-1 ушло на выброшенные запуски.** План Fable за $5,43 пропал, потому что проверяющий Codex упёрся в квоту уже после планирования; в текущем коде этот сценарий уже закрыт коммитом `1dce9ac`. Ещё $2,78 стоил браузерный прогон, в котором не удалось наблюдать ни одного критерия.
4. **Учёт стоимости завышен при `--resume`.** `total_cost_usd` в событии `result` считается за всю сессию, а не за запуск. Ревизия плана записана как $4,48, а по её собственным токенам стоит $1,01. Итог CS-1 по событиям — $36,83, по токенам — $33,35. Поэтому сравнение «$12,37 на CS-1 против $7,64 на CS-2» завышено. Если пересчитать CS-1 по токенам, планирование стоило $8,90 без выброшенного плана Fable или $14,33 вместе с ним.
5. Вариант C (карта репозитория, чтение файлов пачками, файлы плана в промпте проверяющего) бьёт по своей части расхода: по числу вызовов API на планировании и по объёму прочитанного. На CS-1 эта часть стоит около $1–2 из $33. Это нужная мера, но не самая крупная.

Цены за 1 млн токенов по [странице цен](https://platform.claude.com/docs/en/about-claude/pricing). Для Fable и Opus они совпадают с ценами, которые выводятся из `costUSD` в логах Claude Code: я решил систему уравнений по 8 запускам Fable и 3 запускам Opus, расхождений нет.

### Что видно в транскриптах

- **Запись кэша ≈ всё, что попало в контекст.** Каждый новый токен контекста записывается в кэш один раз, поэтому эта статья растёт вместе с объёмом прочитанного и написанного за сессию.
  - Планировщик Fable прочитал 57 файлов (298k символов). Среди них `CODING_GUIDELINES.md` (58k), `eslint.config.mjs` (26k), `TESTING.md` (25k) и `DESIGN.md` (21k) — это 130k символов только правил.
  - Проверяющий план прочитал 48 файлов (217k символов), в том числе те же документы. `CODING_GUIDELINES.md` он прочитал дважды.
  - Финальное ревью прочитало 15 файлов (72k символов), в том числе `eslint.config.mjs` и `TESTING.md`, хотя линтер уже прогнан гейтом.
- **Fable сам читает файлы пачками, Opus и браузер — нет.**
  - Fable делал около 10 вызовов инструментов на один вызов API: 8 вызовов API на 78 инструментов.
  - Opus на планировании делал 2,5 на вызов (36 вызовов API на 91 инструмент), на исполнении — 1,8.
  - Браузерная роль делала 1,0–1,2.
  - Чтение кэша растёт пропорционально числу вызовов API, умноженному на размер контекста. Отсюда 4,0M прочитанных токенов у Opus-планировщика против 0,6M у Fable.
- **Ревизия через `--resume` начинала с контекстом 253k.** Это уже исправлено в 5be33cf: ревизия идёт в новой сессии. Промпт ревизии начинается тем же текстом, что промпт планировщика, поэтому префикс попадает в кэш, если ревизия запущена на той же модели в пределах TTL.
- **Браузер.**
  - Одиночные результаты бывают огромными: `take_snapshot` — до 55k символов (12 снапшотов на 226k в одном прогоне), `list_network_requests` — 48k символов за один вызов, `take_screenshot` — до 400k символов base64.
  - Контекст дорастает до 90–130k за 35–45 вызовов API.
- **Исполнители дешёвые.**
  - GLM на M1 стоил $1,37, Opus на M2 — $1,92.
  - Opus-исполнитель читает только нужные файлы (43k символов) и гоняет `npm run check`.
  - Ревьюеры вех получают дифф в промпте и читают мало: 5–6 файлов.
- **Системный промпт Claude Code занимает 7,7–11k токенов на запуск.** Между запусками одной модели в пределах TTL он берётся из кэша: второй и третий браузерные прогоны начали с 8,9k прочитанных токенов. Это $0,1–0,2 на запуск, мелочь.

## 3. Как запускаются агенты (что важно для расхода)

- **Запуск агента.** `runner.Claude.command` запускает `claude -p --output-format stream-json --restricted --strict-mcp-config --model … --tools … --settings … [--effort] [--json-schema]`.
  - Ограничения хода, бюджета и TTL кэша не задаются.
  - Промпт роли целиком идёт первым сообщением пользователя, системный промпт стандартный.
- **Учёт стоимости.** В `Claude.read` событие `result` переписывает `usage` итогами запуска (они правильные, за запуск), а `cost_usd` берёт из `total_cost_usd` (он за всю сессию). Затронуты ревизия через resume (уже ушла) и **второй и следующие круги `develop`**: `milestone.run` продолжает сессию исполнителя через `resume=session`. `status.totals` и строка стоимости в черновике MR (`final.description`) суммируют это значение.
- **Выбор моделей.** `models.allowed` применяет «не слабее автора» ко всем ролям, включая `browser`. `models.executor` переводит сложную веху на frontier-модель. В итоге после Opus-исполнителя все проверки уходят на Fable: самого Opus исключает мягкое правило «не проверять себя», а Codex без квоты.
- **Промпты ролей.**
  - Планировщик (рабочая копия plan.py, вариант C): PIPELINE + правила + задача + дайджест + карта.
  - Проверка плана: то же плюс план и тексты его файлов (до 40k символов).
  - Ревью вехи: правила + `milestone_text` (там `document["rules"]` из плана, а не дайджест) + гейт + дифф вехи.
  - Финал: правила + сводка плана + критерии + дифф всей задачи.
  - Слепая проверка: критерии + дифф.
  - Браузер: правила + URL + критерии вехи.

### Подробности по мерам

**1. TTL кэша 5 минут.**
- Основание: запись кэша стоила $19,1; при 5-минутном TTL было бы 19,1 × 1,25/2 ≈ $11,9.
- Риск: промах кэша, если между вызовами API одной сессии проходит больше 5 минут, например при долгом `npm run check`. Тогда префикс записывается заново по 1,25×. Средний вызов Fable длился около 50 с.
- Замер: в `result.modelUsage` записи кэша должны перейти из `…1h…` в `…5m…`. На одинаковом сценарии запись кэша в $ должна упасть примерно на 37%, а число записанных токенов — не вырасти больше чем на 10%.
- Оговорка: на подписке `cost_usd` расчётный. Как TTL влияет на расход квоты плана, документация не говорит, это надо проверить по счётчику квоты.

**2. Браузер без правила «не слабее автора».**
- Основание: Sonnet стоит в 5 раз меньше Fable на выходе и записи кэша и в 2,5 раза меньше на чтении.
- Риск: роль наблюдает поведение, а не судит код, но более слабая модель может хуже доводить сценарий до конца.
- Замер: A/B на одной и той же вехе и коммите. Сравнить вердикт, число `unverifiable` и стоимость.

**3. Проба проверяющего до планирования.**
- Что было: Fable спланировал, Codex отказал по квоте через 8 с, старт упал, перекастинг выбрал другого планировщика.
- В текущем коде этот сценарий закрыт `1dce9ac`: `make` берёт сохранённый черновик, `cast(planner=…)` оставляет Fable планировщиком, `plan_review` меняет проверяющего, у которого кончилась квота. $5,43 больше не теряются.
- Остаётся вопрос качества: при недоступном Codex Fable проверяет собственный план. Если сначала проверить доступность вендора проверяющего (`models.availability` или короткая проба), каст с самого начала будет «план Opus, проверка Fable».
- Замер: в `events.jsonl` нет пары `run_finished(plan)` → `start_failed` → новый `plan`, и нет заметки о самопроверке на `plan-review`.

**4. Честный учёт стоимости и телеметрия.**
- При `--resume` брать стоимость из токенов запуска (`models.estimate`) или как разность с предыдущим `total_cost_usd` той же сессии.
- Добавить в `run_finished` поля `api_calls` (уникальные `message.id`), `ctx_max`, `thinking_tokens` и раздельные `cache_write_5m`/`cache_write_1h`.
- Тогда сравнения карточек не потребуют разбирать транскрипты.

**5. Ужать ответы браузерных инструментов.**
- Делать снапшот только видимой области или нужного узла, обрезать или фильтровать `list_network_requests` по пути и методу, ограничить скриншоты.
- Основание: контекст 90–130k почти целиком состоит из результатов инструментов; если вдвое сократить объём, запись кэша и чтения уменьшатся примерно вдвое.
- Риск: агент может не увидеть нужный элемент; оставить ему способ запросить полный снапшот.
- Замер: `ctx_max` и запись кэша на браузерный прогон при том же вердикте.

**6. Дайджест правил ревьюерам.**
- `milestone_text` передаёт только выбранные планировщиком `rules`. Финал и проверка плана всё равно читают `eslint.config.mjs`, `TESTING.md` и `CODING_GUIDELINES.md` (финал — 37k символов, проверка плана — около 90k).
- Сделать: передавать `plan.digest_text(digest)` и писать в правилах ролей, что линтер уже прогнан гейтом, а исходники правил открывать только по нужному разделу через Grep.
- Замер: число `Read` по файлам из `rules_sources` в транскриптах review, final-review и plan-review должно стремиться к нулю.

**7. Вариант C (идёт).**
- Основание: у Opus-планировщика на CS-1 чтение кэша было $0,80 при 36 вызовах API. Если довести его до 8–10 вызовов, как у Fable, сэкономится около $0,6. Ещё около $0,5–1 даст меньший объём чтения правил и дерева.
- Цена карты: `BUDGET = 60000` символов — это около 17k токенов, которые пишутся в кэш в каждом из трёх запусков планирования (около $0,14 на Opus и $0,34 на Fable за запуск). Окупается, если карта заменяет хотя бы 2–3 файла или Glob-обхода.
- Замер: инструменты на вызов API и `ctx_max` у plan и plan-review; CS-2 с картой против CS-2 без карты на одном коммите.
- Подсказку о параллельных вызовах [рекомендует документация](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices). Для Fable в длинных циклах она советует повторять её после каждого раунда результатов. В `claude -p` это недоступно, поэтому одного указания в промпте может не хватить.

**8. Effort по ролям.**
- Основание: мышление на CS-1 стоило $4,59, из них около $4,3 — роли Fable и Opus xhigh на plan, plan-review и final-review. Мышление оплачивается как выход ([документация](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost#pricing)), а effort влияет на все выходные токены и число вызовов инструментов ([effort](https://platform.claude.com/docs/en/build-with-claude/effort)).
- Кандидаты: `blind-code` high → medium (один вызов, 9,7k мышления); `final-review` и `plan-review` — только по итогам A/B.
- Риск: пропущенные замечания.
- Замер: на одном плане или диффе сравнить число и тяжесть замечаний и стоимость при high и medium.

**9. Проверяющие для работы Opus дешевле Fable.**
- Варианты:
  - разрешить Opus другого effort проверять Opus-исполнителя (сейчас «проверяет себя» — это мягкое правило);
  - не поднимать сложную веху до Opus, а давать её `sonnet-high`;
  - ждать квоту Codex (до 4 ноября 12:10).
- Основание: Fable дороже Opus в 2,5 раза; review M2, final-review и blind-code стоили $5,85 на Fable и стоили бы около $2,35 на Opus.
- Риск: ослабляется независимость проверки, ради которой правила и введены. Решать владельцу.

**10. Предохранители `--max-budget-usd` и `--max-turns`.**
- В `runner.Spec` добавить `max_budget_usd` и `max_turns`, в `Claude.command` — передачу этих флагов, а пределы на роль задавать в профиле.
- Это не экономия на нормальном прогоне, а защита от зацикливания: браузер на 45 ходах, планировщик на 92.
- `--max-turns` есть в [справочнике CLI](https://code.claude.com/docs/en/cli-reference), хотя в `claude --help` 2.1.312 не показан. `--max-budget-usd` считает по клиентской оценке и может превышать порог.
- Риск: обрыв на законно длинной задаче. Лимит должен быть с запасом, примерно 2× от медианы роли.

**11. Ужать системный промпт.**
- В init-событии видны десятки встроенных скиллов и команд.
- Основание: 7,7–11k токенов системного промпта на запуск.
- `--bare` не подходит: он не читает OAuth, то есть не работает на подписке. `--exclude-dynamic-system-prompt-sections` полезен только для общего кэша между машинами.
- Замер: `ctx0` первого вызова.

**12. Повторно использовать результаты между запусками.**
- Запоминать вердикт браузера и ревью по ключу (HEAD, критерии, версия адаптера и правил).
- На CS-1 браузер трижды прогнали на одном M2 во время отладки Friday ($9,35). В штатной работе повторы редки: польза только при перезапусках.

Чего не делать:
- Batch API (−50%) — не подходит: агентный цикл CLI не пакетируется.
- Компакция (`--autocompact`) на коротких сессиях не нужна: максимальный контекст 257k встречался только в ревизии через resume, которой больше нет.

## 5. Рекомендуемые следующие 3 шага

1. **Учёт и TTL в `runner.py` (меры 4 и 1).**
   - При resume считать `cost_usd` по токенам запуска, в `run_finished` писать `api_calls`, `ctx_max`, `thinking_tokens` и раздельные записи кэша 5m/1h.
   - В `spec.env` добавить `CLAUDE_CODE_PROMPT_CACHE_TTL=5m`.
   - Проверка: один дешёвый прогон роли (например, `blind-code` на готовом диффе) показывает `ephemeral_5m_input_tokens > 0` и `…1h… = 0`.
2. **Браузер на модели профиля и с компактными снапшотами (меры 2 и 5).**
   - Исключить `browser` из правила «не слабее автора» в `models.allowed`.
   - В адаптере ограничить снапшот и список сетевых запросов.
   - Проверка: повторить приёмку M2 CS-1 на том же коммите. Ожидается тот же вердикт за ≤$1 вместо около $3.
3. **Довести вариант C и замерить его вместе с мерами 3 и 6.**
   - Дайджест — ревьюерам; пробу проверяющего до планирования — ради качества каста, не ради денег.
   - Сравнить CS-2 с картой и без на одном коммите по стоимости, пересчитанной по токенам, по инструментам на вызов API и по `ctx_max` у plan и plan-review.
   - После этого — A/B effort (мера 8) на `blind-code` и `plan-review`.
