## Installation

1. Clonez Friday et ajoutez `bin` au `PATH`, ou définissez `FRIDAY_BIN`.
2. Installez les CLI dont les agents ont besoin : Claude Code (`claude`) pour les modèles Anthropic et Z.ai, Codex CLI (`codex`) pour les modèles OpenAI. Connectez-vous-y comme d'habitude.
3. Pour le gate et la recette dans le navigateur, installez Docker. La recette dans le navigateur nécessite aussi Chrome avec le port de débogage 9333 et une session ouverte dans l'environnement de test.
4. L'état est stocké dans `~/.local/share/friday` (modifiable avec `FRIDAY_HOME`). Les profils et les secrets n'entrent pas dans le dépôt : le dossier `profiles/` figure dans `.gitignore`.

### Plugin pour Codex et Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

Le plugin apprend à l'agent à lire `status` et `plan`. Le lancement d'une tâche, son approbation et les décisions restent de votre ressort.

## Déroulement d'une tâche

1. **`start`** crée la branche `<repository>/KEY` (par exemple `octis/31`) à partir d'un `origin/<base_branch>` à jour ainsi qu'un worktree, fige l'attribution des rôles et écrit le plan : des jalons de 2 à 5 étapes, les fichiers, une estimation de taille, des critères de code et de navigateur, et un condensé des règles du projet pour l'exécutant. Le plan est d'abord vérifié sans modèle (taille, fichiers, ordre, critères). Ensuite, un modèle d'un autre fournisseur le relit, et le planificateur répond une seule fois aux constats : il accepte chacun d'eux ou le rejette en donnant une raison.
   Avec `"toolset": {"plan": "project"}`, c'est le processus propre au projet qui écrit le plan ([ADR 0015](../adr/0015-project-toolset.md)) : Friday lance dans le worktree une session Claude Code ordinaire avec les réglages, hooks, skills, agents et MCP du projet, et lui transmet `project.plan_command` avec l'énoncé de la tâche. La session écrit le fichier de plan du projet (`project.plan_file`) et renvoie à Friday un résumé de ce même plan dans son schéma ; Friday vérifie le résumé sans modèle et ne lance aucune revue par un autre fournisseur, car le processus du projet a la sienne. La session s'exécute en mode de permission `auto` ; son résultat est la dernière réponse avant la fin du processus, car le processus du projet peut attendre une revue en arrière-plan.
2. **`plan`** affiche le plan, les questions, les constats rejetés et les chevauchements de fichiers avec les autres tâches actives.
3. **`approve`** approuve le plan et lance le pipeline en arrière-plan (`--no-run` se contente d'approuver ; lancez ensuite avec `run`).
   Avec `"toolset": {"execute": "project"}`, Friday exécute le processus propre au projet à la place des jalons ([ADR 0015](../adr/0015-project-toolset.md)) : une session Claude Code avec `project.execute_command` sur le modèle du rôle `develop`. La session fait un commit à chaque étape, avec son identifiant tiré du résumé du plan au début de l'objet (`M1.1: …`), et ne publie rien. Une question met fin à la session : la tâche s'arrête, la question apparaît dans `status`, et la réponse donnée avec `decide` reprend la même session en arrière-plan ; `resume` fait de même sans réponse. La session reçoit ce qui l'a arrêtée. Si la session s'est terminée sans question et que l'environnement a arrêté la tâche (l'image du gate, la connexion à l'environnement de test), `resume` ne réveille pas la session et ne refait que les vérifications qui suivent. Après la session, Friday vérifie que l'arbre est propre et que chaque étape a un commit dans les limites de `limits` (`git diff --numstat` de ses commits), lance le gate et la recette dans le navigateur des jalons qui touchent à l'interface, puis la vérification finale et le MR comme d'habitude ; dans ce mode, la revue finale lit d'abord `AGENTS.md` (ou `CLAUDE.md`) à la racine du dépôt et vérifie le diff par rapport aux sections des documents du projet, et pas seulement par rapport aux règles du plan. Toute divergence devient une question pour le propriétaire.
4. **Jalon.** L'exécutant travaille dans une session par jalon et fait un commit à chaque étape. Le gate s'exécute sur le commit. S'il échoue, l'exécutant ne reçoit que les sections du journal qui ont échoué ; quand une section dépasse la limite, son titre et ses lignes d'erreur avec leur contexte sont conservés, en commençant par les tests en échec au format TAP (`not ok …` avec leurs diagnostics). La revue de jalon examine le diff de ce jalon avec le résultat du gate. L'exécutant corrige les constats bloquants ou les conteste ; les constats contestés vous sont envoyés. Les jalons qui touchent à l'interface passent par la recette dans le navigateur, dans une preview isolée. Après deux échecs consécutifs, Friday relève le niveau de l'exécutant dans les limites de `executor_tiers` quand le profil fixe cette limite ; le remplaçant démarre une nouvelle session.
5. **Final.** Les rôles de `final_review_roles` vérifient l'ensemble du diff : par défaut, la revue finale et la vérification à l'aveugle s'exécutent en parallèle ; un profil peut ne garder que la revue finale. Les constats bloquants bénéficient d'un tour de corrections.
6. **MR en brouillon** : il est ouvert si le profil définit `delivery`. Sinon, son texte est enregistré dans `merge-request.md` dans le dossier de la tâche.

Le pipeline s'arrête si le gate n'a jamais réussi, si l'exécutant n'a rien fait, si l'environnement est indisponible, si les modèles autorisés par les règles sont épuisés ou si le budget configuré est épuisé. Les modifications parallèles qui se chevauchent, les branches conservées qui n'ont pas été intégrées et les entrées changeantes de la revue finale demandent aussi de l'attention avant que la tâche continue. Les désaccords en revue ne l'arrêtent pas. Un jalon que rien n'a vérifié (pas de gate, les contrôles de l'exécutant n'ont pas tourné, pas de recette dans le navigateur) se clôt comme « terminé, non vérifié » avec ses raisons, dans le statut, le journal et le MR ([ADR 0009](../adr/0009-unverified-is-not-done.md)) ; si les contrôles de l'exécutant n'ont pas pu tourner et qu'il n'y a pas de gate, le jalon est bloqué.

`decide KEY name "text" --reopen M2` enregistre votre décision. Tant que le plan de Friday attend l'approbation, `decide` le révise aussi ([ADR 0016](../adr/0016-decision-revises-the-plan.md)) : le planificateur réécrit dans une nouvelle session les jalons indiqués dans `--reopen`, et les autres sont repris tels quels ; sans `--reopen`, il choisit lui-même les jalons concernés. Un autre modèle ne relit que les jalons modifiés. `decide` affiche quels jalons ont été révisés dans le plan, lesquels ont été rouverts pour être relancés et lesquels n'ont reçu la décision que dans leur contexte ; `friday plan KEY --diff` montre la différence avec la révision précédente. Si la révision échoue, le plan reste tel qu'il était et attend l'approbation, et la décision est enregistrée : répétez le même `decide`. Tant qu'un plan du processus du projet attend l'approbation, `decide` reprend sa session avec votre réponse et affiche la nouvelle révision du plan. Chaque `decide` de ce type est une reprise distincte de la session : répondez donc à toutes les questions du plan dans un seul texte. De la même façon, `decide` répond à une question d'une session d'exécution arrêtée du processus du projet. Seuls les jalons indiqués et ceux qui en dépendent sont rouverts. Sans `--reopen`, les jalons suivants tiennent compte de la décision. `resume` reprend une tâche arrêtée ou en échec. `stop` arrête une tâche en cours : les agents se terminent avec leurs processus enfants.

L'énoncé d'origine de la tâche est conservé en entier et transmis aux exécutants et aux revues, si bien que les hachages et les URL exacts survivent au raccourcissement des faits par le plan. Pour une ancienne fiche sans énoncé enregistré, utilisez `resume KEY --brief task.md`. L'énoncé n'est rétabli que si le texte correspond à l'empreinte de la planification d'origine ; un autre texte demande un nouveau plan. L'approbation, les étapes et les compteurs du budget ne sont pas remis à zéro.

Quand un jalon en échec reprend, les commits déjà faits gardent la limite de revue d'origine ; aucun commit vide supplémentaire n'est nécessaire. L'exécutant reçoit l'échec précédent du gate, avec le corps complet d'une traceback Python dans la limite de la sortie de diagnostic.

## Profil

Un profil est un fichier JSON. La clé `extends` inclut un autre profil (par exemple, un catalogue de modèles partagé) ; les chemins sont relatifs au fichier du profil.

| Clé | Rôle |
| --- | --- |
| `name`, `repository` | Le nom du projet et le chemin de son dépôt |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | D'où créer la branche de la tâche et où la placer ; par défaut `<repository>/{key}`, un `branch_template` explicite prend un seul `{key}`, la disposition est `key` ou `branch` |
| `models`, `roles` | Le catalogue de modèles et les préférences de rôles (voir ci-dessous) |
| `engineering_policy` | Règles pour le planificateur, l'exécutant, les revues de jalon, la revue finale et les corrections |
| `project_lessons` | Pièges du projet que les revues finissent toujours par trouver : une liste de courts contrôles. L'exécutant, les revues de jalon, la revue finale et les corrections y confrontent le changement |
| `rules_docs` | Documents contenant les règles du projet. Friday en produit un condensé unique pour le planificateur et le relecteur du plan (par défaut `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). Le condensé est stocké par hachage du contenu et réutilisé par les tâches tant que les documents ne changent pas ; le planificateur ne lit pas les documents en entier. Les motifs se développent depuis la racine du dépôt, `**` descend dans les dossiers (`docs/**/*.md`, `src/**/README.md`) ; seuls les fichiers trouvés entrent dans l'empreinte. L'exécutant, les revues de jalon, la revue finale et les corrections reçoivent les règles choisies par le plan, la carte des documents du condensé et la révision de base de la tâche pour chercher des précédents ; l'exécutant cherche avec `bin/friday-precedent <base> <pattern> [<path>…]` (un wrapper autour de `git grep` qui ne laisse passer aucune option) |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | Une carte du dépôt dans le prompt du planificateur et du relecteur du plan, pour qu'ils n'explorent pas la structure à coups d'appels d'outils. `none` (par défaut) : pas de carte. `builtin` : les fichiers suivis avec leur nombre de lignes. `graphify` : en plus, les symboles de chaque fichier et le nombre de fichiers qui l'importent, tirés d'un graphe [graphify](https://github.com/Graphify-Labs/graphify) (`uv tool install 'graphifyy[mcp]==0.9.100'` ; il se contente d'analyser le code, aucun modèle n'est utilisé ; le graphe est stocké dans `FRIDAY_HOME/maps`, pas dans le dépôt). Lors d'une mesure sur CS-2, la carte n'a pas rendu la planification moins coûteuse (sans carte 6,19 $, `builtin` 7,08 $, `graphify` 7,97 $, une exécution chacun), elle est donc désactivée par défaut. La carte est mise en cache par commit. Si elle dépasse `repo_map_budget` caractères (60000), on la raccourcit d'abord en supprimant les symboles, puis en réduisant les dossiers. `repo_map_mcp: true` (uniquement avec `graphify`) donne aux deux rôles des requêtes sur le graphe : `query_graph`, `get_node`, `get_neighbors`, `shortest_path` ; non vérifié en conditions réelles sur Codex. Le relecteur du plan reçoit le texte actuel des fichiers cités dans le plan (jusqu'à 40000 caractères) |
| `approval` | `owner` (par défaut) : le plan attend `approve`. `auto` : le plan est approuvé automatiquement après la revue et le pipeline démarre aussitôt ; le journal indique que le plan a été approuvé automatiquement |
| `limits` | `stage_files` et `stage_lines` : les limites d'une étape (10 et 500) ; les `task_milestones` et `task_stages` facultatifs limitent l'ensemble du plan avant son exécution |
| `toolset`, `project` | Qui exécute une phase : `{"plan": "project", "execute": "friday"}` signifie que le processus du projet écrit le plan et que Friday l'exécute (les deux phases valent `friday` par défaut). `project` : `plan_command` avec `{statement}` est la commande de planification du projet, par exemple `"/plan-stages {statement}"` ; `plan_file` est le fichier de plan dans le worktree ; `execute_command` et `stage_argument` avec `{stages}` servent à la phase d'exécution ; `session_env` nomme les variables d'environnement que la session reçoit en plus des habituelles (par exemple `SSH_AUTH_SOCK` pour `git fetch`) ; `disallowed_tools` sont les outils fermés à la session (par exemple le navigateur du propriétaire : la recette est faite par le rôle `browser` de Friday) ; `timeouts` sont `idle`, `tool`, `total` en secondes ([ADR 0015](../adr/0015-project-toolset.md)) |
| `worktree_setup` | Commandes que Friday exécute dans un nouveau worktree avant la planification (dépendances et similaires) : des tableaux d'arguments avec les substitutions `{repository}` et `{worktree}` ; elles doivent pouvoir être rejouées sans effet de bord. Exemple pour npm sous macOS : `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Commandes que l'exécutant peut lancer lui-même, sous la forme exacte : `"python3 -m pytest"`, pas `python` |
| `executor_deny_read` | Chemins supplémentaires que le shell de l'exécutant ne peut pas lire |
| `executor_tiers` | Les niveaux autorisés pour tous les agents qui écrivent, par exemple `["strong", "efficient"]`. Sans ce champ, tous les niveaux sont autorisés. La complexité, l'escalade, le quota et les corrections finales respectent la limite |
| `milestone_rounds` | Combien de tours d'exécutant un jalon obtient (4) |
| `max_parallel_milestones` | Les jalons indépendants et prêts avec `parallel=true` qui s'exécutent en même temps (2) ; `1` les exécute l'un après l'autre |
| `budget` | `max_model_runs` et `max_milestone_runs` facultatifs et positifs : la limite des exécutions admises de tous les rôles par tâche et par jalon. La réservation est atomique ; les tentatives échouées et inachevées comptent, et `resume` et la réouverture ne remettent pas les compteurs à zéro. Quand il est épuisé, la tâche s'arrête avec `budget_exhausted` ; le budget se change explicitement dans le profil. Il limite les exécutions, pas le coût |
| `final_review_roles` | `["final-review", "blind-code"]` par défaut ; `["final-review"]` garde une seule vérification finale. Les résultats terminés sont enregistrés indépendamment et réutilisés seulement si les sources, le plan, les décisions, les réglages et les entrées du rôle sont inchangés |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | La commande de vérification dans Docker ; `git-diff` compare avec la base de la tâche. Le profil décrit comment construire l'image du gate sous forme d'étape (`steps`), et `gate_image_step` nomme cette étape. Si `gate_lockfile` dans l'image diffère de celui de la tâche, la tâche s'arrête : `status` affiche « Owner step needed » avec la commande de l'étape ; après l'étape, `resume` refait les vérifications et ne réveille pas une session d'exécution du processus du projet |
| `environment_errors` | Motifs de lignes de journal qui signalent une panne d'environnement, et non une panne du code |
| `browser`, `preview`, `behavior_test_policy` | L'environnement de test, la preview et les règles de la recette dans le navigateur. Les backends de preview incluent `storybook` (la vitrine issue de `stories` avec un instantané du kit à `mount`, [ADR 0008](../adr/0008-ui-kit-preview-and-design-check.md)). Pour `storybook`, tout ce qui est propre au projet est dans le profil : `command` (un tableau d'arguments qui lance la vitrine ; `{mount}` est le chemin du kit), `port`, `env`, `tmpfs` (chemins absolus du conteneur où l'écriture est permise), `links` (liens de l'instantané vers l'image, par exemple `{"node_modules": "/app/node_modules"}`) ; l'image est `stories.image` |
| `stories` | Le second dépôt de la tâche, une vitrine de composants (Storybook) qui contient le worktree du kit : `repository`, `base_branch`, `worktree_root`, `mount` (obligatoire : le chemin du kit à l'intérieur de la vitrine), `setup` (commandes dans un nouveau worktree ; `{repository}`, `{worktree}`, `{kit}`), `commands` (les contrôles de l'exécutant), `image` (l'image de la preview), `themes` (thèmes dans chacun desquels la recette dans le navigateur ouvre la story et compare les états du composant) et `theme_query` (obligatoire avec `themes` : le paramètre d'URL du thème avec `{theme}`). Les fichiers de la vitrine sont écrits dans le plan sous la forme `stories:src/stories/X.stories.ts` ; le résultat est une branche de tâche dans les deux dépôts |
| `steps` | Étapes du projet que Friday ne connaît pas par lui-même ; seul le propriétaire les exécute (`friday step NAME [KEY]`, sans nom la liste et l'état) ([ADR 0011](../adr/0011-profile-steps.md)) : `{"<name>": {"run": [...], "scope": "task" \| "profile", ...}}`. `run` est un tableau d'arguments exécuté sur l'hôte ; une étape de tâche reçoit `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`, toute étape reçoit `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}`, `{secret.<name>}`. `description`, `env` (sans valeurs secrètes), `cwd`. `lock` est une ressource partagée pendant la durée de l'étape : un chemin partage le verrou du dépôt, un nom est un verrou nommé. `commit: {"paths": [...], "message": "{key}: ..."}` fait que Friday fait le commit de ces chemins ; l'étape devient périmée quand la branche change en dehors d'eux après son commit. `required` (une étape de tâche) : tant que l'étape n'est pas faite ou est périmée, `status`, le journal et le texte du MR la rappellent avec sa commande. `check` (une étape de profil) est une commande de disponibilité pour `doctor` : 0 prête, 2 périmée (!), tout le reste manquante (✗). `secrets: {"<name>": "<path>"}` sont des fichiers que la commande reçoit par chemin ; Friday ne les lit pas. Placez une procédure complexe dans un script à côté du profil |
| `design` | Outils de design pour les tâches d'interface ([ADR 0007](../adr/0007-design-tools.md)). `figma: {"url": "http://127.0.0.1:3845/mcp"}` est le serveur MCP local du Dev Mode de Figma desktop ; `tools` restreint les outils de lecture (`get_metadata`, `get_design_context`, `get_screenshot`, `get_variable_defs`), les outils d'écriture ne sont pas acceptés. Quand le ticket contient un lien `figma.com/design/…?node-id=…`, `start` vérifie que le nœud est ouvert dans l'onglet Figma actif, et le planificateur et le relecteur du plan lisent le cadre et écrivent dans le plan une spécification mesurable. L'exécutant et les revues la reçoivent dans le prompt, sans accès à Figma. Friday enregistre des captures des cadres dans le dossier de la tâche ; la recette dans le navigateur compare la preview avec elles et mesure les styles (`computed_style`) : un écart par rapport à un nombre de la spécification bloque, un écart visible seulement à l'œil va dans les constats mineurs du MR. Si Figma ne répond pas ou si le nœud est introuvable, `start` s'arrête et dit quoi ouvrir ; `start --no-design` planifie sans la maquette. `impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` nomme des fichiers de `reference/` du skill /impeccable que Friday place dans le prompt des jalons d'interface ; `references` est obligatoire et associe aux rôles `develop`, `review`, `final-review` des listes de fichiers (par exemple `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API ou MCP), utilisé pour lire la description de la tâche |
| `journal` | Où écrire le journal de la tâche : `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]` ; `page` est le chemin de la page de la tâche dans `dir` (`{key}.md` par défaut), par exemple dans le dossier de la tâche dans Obsidian. `journal_dir` et `journal_page` sont une forme abrégée pour un seul journal markdown ; un `journal` défini dans le profil (ou hérité) l'emporte sur eux. Friday ne touche pas à une page qu'il n'a pas écrite (pas de `friday_generated` dans le front matter) : il indique qu'il l'a ignorée et écrit le reste |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` et la clé `github.repository` ou `gitlab.base_url` + `gitlab.project` |

Le nom du dépôt vient de l'URL de `origin` (HTTPS, SSH ou chemin local), sans `.git` ; sans `origin`, du nom du dépôt principal sur le disque, y compris quand on travaille depuis un worktree lié. Les caractères hors de `A–Z`, `a–z`, `0–9`, `_` et `-` deviennent `-`, et les `-` au début et à la fin sont supprimés. Un nom vide demande un `branch_template` explicite. La clé complète de la tâche est conservée : `31` donne `octis/31`, `OCTIS-031` donne `octis/OCTIS-031`. Une branche déjà enregistrée sur la fiche de la tâche est conservée quand la tâche continue ; un nouveau réglage s'applique aux nouvelles tâches. Une vitrine liée utilise le nom du dépôt principal de la tâche.

### Modèles et rôles

```json
"models": {
  "fable": {"model": "claude-fable-5-2", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver` : ce qui exécute le modèle, `claude` ou `codex`. Z.ai passe par Claude Code ; le jeton est lu dans un fichier accessible uniquement au propriétaire.
- `tier` : `frontier`, `strong` ou `efficient` ; `strength` ordonne les modèles au sein d'un niveau.
- `effort` : la profondeur de raisonnement (`low` … `max`) ; un même modèle peut être décrit plusieurs fois avec des efforts différents.
- `scarce` : un modèle coûteux ; il est utilisé une fois par tâche si les règles permettent de se passer de lui.
- `price` : le prix par million de tokens selon le type (`input`, `output`, `cache_read`, `cache_write`), utilisé pour estimer les dépenses quand le fournisseur ne communique pas de prix.

Rôles : `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. Les listes de `roles` sont des préférences : si la liste ne contient aucun modèle adapté, Friday en prend un autre dans le catalogue. Règles strictes : seuls les modèles `frontier` relisent le code, le relecteur n'est pas plus faible que l'auteur du travail, et la vérification à l'aveugle n'est pas faite par l'auteur du code. Règles souples, dans l'ordre : pas le même modèle que l'auteur ; un modèle coûteux une seule fois ; un fournisseur différent ; la vérification à l'aveugle pas par l'auteur du plan. Une règle souple ne peut être enfreinte que s'il n'y a pas d'autre solution, et l'infraction est consignée dans l'historique de la tâche.

Un exemple d'attribution des rôles se trouve dans [examples/models.json](../../examples/models.json).

Avec `executor_tiers`, un jalon complexe utilise le niveau autorisé le plus élevé, et un remplacement faute de quota garde le niveau requis dans la limite. Une ancienne attribution des rôles avec un exécutant interdit est remplacée par un exécutant autorisé ; une écriture par un modèle interdit, ou qui ne correspond pas au catalogue, est rejetée. Les niveaux et les noms viennent du catalogue du profil ; Friday ne les déduit pas du nom du modèle.

Les jalons parallèles ont leurs propres worktrees et sont intégrés dans l'ordre du plan. Friday vérifie le chevauchement des chemins déclarés avant le démarrage et celui des modifications réelles avant l'intégration. Le travail qui n'a pas pu être intégré est conservé dans sa branche et son worktree ; `parallel_recovery_required` les nomme avant que la tâche continue. Après avoir examiné le travail conservé, le contrôleur termine le transfert ou garde à part les commits nécessaires, puis supprime les worktrees et les branches de voie examinés avec des commandes Git ordinaires. Friday ne supprime pas automatiquement ces résultats pour réessayer.

Une revue finale enregistrée est liée à des worktrees propres, aux commits des deux dépôts, au plan, aux décisions, aux réglages des modèles et au texte exact de l'entrée du rôle. Un changement des entrées pendant la vérification renvoie `stale_evidence`. Quand le second rôle échoue, le premier, terminé, est conservé ; le `resume` suivant ne lance que les vérifications manquantes pour les mêmes entrées. Augmenter `budget` et changer `max_parallel_milestones` conservent une revue terminée : ces réglages commandent l'admission et l'ordonnancement, pas le contenu de la vérification.

## Journal

La fiche de la tâche est la seule source de vérité. Les journaux la reflètent et se mettent à jour après les événements importants : le plan est prêt et approuvé, un jalon est terminé ou en échec, une décision du propriétaire, la revue finale, le MR, un arrêt. Pour les mettre à jour à la main, lancez `friday journal KEY`.

Le temps est la somme des durées des exécutions, y compris parallèles, et non le temps calendaire. Pour les nouvelles exécutions sans durée fournie par le fournisseur, le runner la mesure lui-même. Une interruption avant le démarrage du runner enregistre un temps d'exécution nul ; une nouvelle exécution non mesurée garde une durée inconnue. Les anciens événements liés donnent une estimation explicitement signalée, qui peut inclure l'attente d'un créneau. Une exécution perdue sans mesure a une durée inconnue. Un prix inconnu est aussi affiché par rôle ; il ne devient pas un coût nul.

- `markdown` : une page `KEY.md` et une page de synthèse commune qui liste toutes les tâches. Pour Obsidian, indiquez le dossier du coffre (vault) : les pages ont un front matter (clé, état, dépenses, le tag `friday`) et les tâches sont reliées par des wiki links. Une page de tâche contient le plan avec ses hypothèses et ses constats non résolus, les jalons avec le résumé de l'exécutant et les commits, les constats contestés, les décisions, les dépenses par rôle et la chronologie.
- `jsonl` : tous les événements de la tâche, pour l'analyse dans des tableurs ou des tableaux de bord.

Les modèles sont du Markdown avec les substitutions `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. Friday prend le modèle dans le champ `template` de la cible, puis `.friday/task.md` dans le dépôt du projet, puis celui qui est intégré ([friday/templates](../../friday/templates)). Le texte entre `<!-- friday:notes -->` et `<!-- /friday:notes -->` vous appartient : il est conservé à chaque mise à jour. Friday n'écrase pas une page qu'il n'a pas écrite.

## Réglages de la machine

`FRIDAY_HOME/machine.json` définit les ressources partagées par toutes les tâches :

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

Par défaut, un gate et deux navigateurs tournent en même temps, et les fournisseurs ne sont pas limités. Les quotas des fournisseurs sont suivis automatiquement : une exécution qui atteint une limite enregistre quand le quota revient, et d'ici là le fournisseur est écarté lors du choix des modèles.

### File des tâches : `friday serve`

`friday serve` est un processus de longue durée qui tient une file de tâches approuvées par machine ([ADR 0014](../adr/0014-work-pool.md)). Tant qu'il tourne, `approve`, `resume` et une réponse donnée avec `decide` à une session d'exécution ne lancent pas la tâche eux-mêmes, mais la mettent en file ; sans lui, une tâche tourne comme avant dans un processus d'arrière-plan distinct, et `resume` s'exécute dans le terminal.

- Au plus `max_workers` tâches tournent en même temps (`machine.json`, 2 par défaut) ; les tâches lancées hors de la file comptent aussi.
- La file suit l'heure d'approbation du plan ; une tâche reprise après `decide` passe en premier. `friday status` affiche la file et l'état du serveur, `friday stop` retire une tâche de la file.
- Une tâche « running » dont le processus est mort (veille, redémarrage) est remise en file par le serveur comme `resume`.
- Quand une tâche s'arrête sur une question ou une étape du propriétaire, échoue ou est terminée, une notification système arrive (`osascript` sous macOS, `notify-send` sous Linux).

Pour le serveur, une tâche est un seul travail : les jalons ne sont pas découpés en travaux, et il n'y a pas encore de limite par tâche.

`friday service print|install|uninstall` installe le serveur comme service utilisateur : un agent launchd (`~/Library/LaunchAgents/local.friday.serve.plist`) ou une unité systemd. Un service démarre avec un environnement vide ; son fichier nomme donc tout lui-même : `PATH` à partir des dossiers de `claude`, `codex`, `docker`, `git` (et de `glab`, `gh`, `uvx`, `node`, `npx` s'ils sont présents), `FRIDAY_HOME`, `HOME`. `friday service check --profile P` lance `friday doctor` dans exactement cet environnement, de sorte que vous voyez avant l'installation ce que le service ne trouvera pas. Seule la première tâche lancée sous le service montre s'il trouve la connexion à l'abonnement Claude. Le service parle la langue enregistrée avec `friday config language`.

## Limites

- **Sandbox de l'exécutant.** Le shell de l'exécutant (Claude Code) s'exécute dans une sandbox : pas de réseau, pas de lecture de `~/.ssh`, `~/.aws`, `~/.config` et similaires, écriture uniquement dans le worktree et dans un dossier temporaire, et aucune exécution hors de la sandbox. Les commandes hors de `executor_commands`, les commandes git (`add`, `commit`, `status`, `diff`, `log`, `restore`) et `bin/friday-precedent` sont refusées. Codex s'exécute dans sa propre sandbox avec les mêmes limites.
- **Git dans Codex.** Friday place le Git installé et une copie séparée des métadonnées Git dans l'environnement d'exécution de la tâche. Les configurations Git globales et les profils shell des utilisateurs ne sont pas chargés ; les données de service du dépôt source ne sont pas exposées à l'agent. L'exécutant enregistre les étapes avec des commandes Git ordinaires. Une fois son processus terminé, Friday récupère les commits par un bundle vérifié et les rend à la branche source si son HEAD et son index n'ont pas changé. En cas de conflit d'état, le bundle reste dans le journal d'exécution sous le nom `git-recovery.bundle` ; rien n'est écrasé automatiquement. Un relecteur reçoit les métadonnées Git en lecture seule. `doctor` vérifie, sans appeler de modèle, le scénario réel de trois commits dans un worktree lié, ainsi que le respect des interdictions de lire les secrets et d'écrire pour le relecteur.
- **Les relecteurs** ne font que lire. La vérification à l'aveugle s'exécute dans un dossier vide.
- **Le gate** s'exécute dans un conteneur sans accès au réseau, sur un instantané du commit monté en lecture seule.
- **Le navigateur** ne reçoit que les outils de Friday pour une seule preview (dont `hover` et `computed_style`, qui lit les styles avec un script fixe, sans `evaluate_script`) ; contourner l'autorisation et lire les en-têtes des requêtes autorisées sont interdits.
- **Figma** n'est lu que par le planificateur et le relecteur du plan, et seulement avec les outils de lecture du serveur local de Figma desktop. Le skill /impeccable ne s'exécute pas à l'intérieur des rôles : Friday place ses textes dans le prompt.
- **Publication.** Friday ne pousse que la branche de sa propre tâche et n'ouvre qu'un MR/PR en brouillon. Il n'écrase pas la branche de quelqu'un d'autre, ne fusionne pas et ne déploie pas.
- **Pas encore vérifié en conditions réelles :** la recette dans le navigateur et la publication sur GitLab ont été vérifiées par des tests avec des agents factices. Git dans l'environnement Codex est aussi vérifié par un vrai laboratoire local, sans appel de modèle ; l'exécution d'un rôle par le modèle est vérifiée séparément sur chaque tâche.
