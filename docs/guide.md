# Friday — руководство

Friday — локальный помощник разработки. Он хранит карточки задач и доказательства, генерирует журнал, выполняет проверки и следит за GitLab. Модель и команды конкретного проекта подключаются через профиль. Для проекта с включённой автономной доставкой `home-stretch` также отправляет проверенную ветку и создаёт черновой MR.

В названиях основных команд — немного пятничного настроения:

| Команда | Что делает | Прежнее имя |
|---|---|---|
| `clock-in` | Заводит задачу и подготавливает рабочую копию | `new` |
| `take-stock` | Показывает задачи и то, что требует внимания | `today` |
| `home-stretch` | Выполняет этапы и настроенную автономную доставку | `go` |
| `long-weekend` | Запускает работу по проектной постановке и возобновляет её | — |
| `keep-watch` | Наблюдает за задачами и обрабатывает замечания | `eyes-up` |
| `wrap-up` | Показывает критерии приёмки и доказательства | `report` |
| `clear-desk` | Показывает или подтверждает уборку рабочей копии | `clean` |
| `send-off` | Выполняет ранее утверждённое внешнее действие | `suit-up` |

Прежние имена остаются алиасами: существующие скрипты и установленный фоновый наблюдатель продолжат работать.

## Установка и запуск

Нужен Python 3.9 или новее; сторонние Python-пакеты не требуются. Блокировки используют `flock`, поэтому текущая реализация рассчитана на macOS и Linux с локальной файловой системой. Для изолированного гейта нужен Docker.

Клонируйте репозиторий и из его каталога проверьте установку:

```sh
git clone git@github.com:avocawo/friday.git
cd friday
./bin/friday --help
./bin/friday --version
docker build -f Dockerfile.test -t friday-test:local .
./bin/test-offline
```

Для команды `friday` по имени в текущей оболочке:

```sh
export PATH="$(pwd)/bin:$PATH"
friday --help
```

### Плагин для Codex и Claude Code

Плагин добавляет навык работы с локальной Friday, но не заменяет установленный CLI и профили. Укажите `FRIDAY_BIN` с полным путём к `bin/friday`, добавьте `bin` в `PATH` или оставьте checkout в `~/Projects/friday`. Профили и секреты в пакет плагина не входят.

Из каталога checkout зарегистрируйте локальный каталог и установите плагин:

```sh
codex plugin marketplace add "$PWD"
codex plugin add friday@friday
claude plugin marketplace add "$PWD"
claude plugin install friday@friday --scope user
```

Начните новую сессию Codex или Claude Code после установки. Для обновления локальной версии плагина используйте соответствующую команду обновления клиента; обновление плагина не обновляет отдельный checkout Friday.

`test-offline` запускает синтетические тесты в контейнере без сети, с каталогом Friday только для чтения, без Docker-сокета и без передачи переменных окружения хоста. По умолчанию используется локальный образ `friday-test:local`; через `FRIDAY_TEST_IMAGE` можно указать другой локальный образ с Python и Git. Тесты, которым нужен Docker внутри Docker, пропускаются. Самостоятельный запуск `unittest` на хосте такой изоляции не предоставляет.

Состояние по умолчанию хранится в `~/.local/share/friday`; переменная `FRIDAY_HOME` задаёт другой каталог. Секреты не записываются в профили: интеграции читают их из переменных окружения или закрытых файлов.

## Профиль и задача

Профили конкретных проектов хранятся локально в `profiles/` и исключены из Git. Начните с [примера профиля](../examples/project-profile.json), скопируйте его и замените `repository` на путь к своему проекту. Пути разрешаются относительно файла профиля. Пример создаёт только локальную карточку; для автономной работы отдельно настройте рабочие копии, раннеры, гейт и браузер.

```sh
mkdir -p profiles
cp -n examples/project-profile.json profiles/example.json
# Укажите путь к своему проекту в profiles/example.json.
```

Токены интеграций передаются через переменные окружения или файлы, доступные только владельцу (`0600`); не помещайте их в профиль. Профили поддерживают наследование через `extends`: вложенные объекты объединяются, остальные значения заменяются.

`engineering_policy` — необязательный список проектных требований, который передаётся планировщику, исследователям, разработчикам и обычным ревьюерам. Его можно использовать для требований о правилах проекта, прецедентах и возможностях библиотек. Слепым проверкам политика не передаётся, чтобы они сохраняли ограниченный контекст. Изменение политики делает ранее составленный план и результаты активного агента устаревшими; план нужно пересоставить. Старый план без отпечатка политики также нельзя продолжить в профиле, где политика включена. Инструменты агентов ограничены рабочей копией; обращения к моделям идут к выбранным провайдерам. Если документация установленной библиотеки недоступна агенту, он должен указать это ограничение.

```sh
friday doctor --profile /полный/путь/к/friday/profiles/example.json
friday clock-in TASK-1234 --profile /полный/путь/к/friday/profiles/example.json
friday decide TASK-1234 naming "Согласованное решение"
friday status TASK-1234
friday take-stock
friday journal TASK-1234
```

Для чтения задач можно настроить Yandex Tracker MCP или HTTP-адаптер; GitLab поддерживает `glab` или HTTP. Учётные данные задаются локально через `FRIDAY_TRACKER_TOKEN`, `FRIDAY_TRACKER_ORG`, `FRIDAY_GITLAB_TOKEN` или соответствующие закрытые файлы. Адаптеры создания задачи и MR используют MCP и `glab`.

`doctor` проверяет файлы учётных данных Tracker и действия GitLab, а также состояние авторизации `glab` для чтения; права доступа к конкретным задачам или MR он не проверяет.

`clock-in` читает задачу из Трекера, когда он указан в профиле, и создаёт рабочую копию, когда заданы `worktree_root` и `base_branch`. Сначала выполняется `git fetch`; уже существующий путь не перезаписывается. Если создание рабочей копии не удалось после создания карточки, повторите `friday prepare TASK-1234`. Профиль без настроек Трекера и рабочей копии создаёт только локальную карточку.

### Проект по постановке

`long-weekend` принимает UTF-8-файл с постановкой проекта. Первая непустая строка становится названием, полный текст сохраняется в локальной карточке. Friday подготавливает отдельную рабочую копию, самостоятельно составляет план этапов и запускает настроенные модели, ревью и гейт. При настроенной автономной доставке команда также может отправить ветку и создать черновой MR, как `home-stretch`.

```sh
friday long-weekend start PROJECT-1 --profile /полный/путь/к/профилю.json --brief /полный/путь/к/постановке.md
friday long-weekend resume PROJECT-1
friday status PROJECT-1
friday long-weekend backlog --profile /полный/путь/к/профилю.json
friday long-weekend next --profile /полный/путь/к/профилю.json
friday long-weekend cruise --profile /полный/путь/к/профилю.json --interval 300
friday long-weekend service install --profile /полный/путь/к/профилю.json --interval 300
friday long-weekend service uninstall --profile /полный/путь/к/профилю.json
```

Для чтения списка открытых GitHub Issues нужен `gh` с локальной авторизацией и `github.repository` вида `owner/repository` в профиле. `backlog` возвращает только названия, номера, метки и ссылки, максимум 100 задач; `possibly_truncated` указывает, что список может быть неполным. Содержимое задач не передаётся моделям этой командой.

`next` выбирает одну открытую задачу GitHub по настроенным обязательным, исключённым и приоритетным меткам. Он пропускает задачи с открытыми зависимостями, назначенными исполнителями, связанными открытыми PR, похожими существующими ветками и ранее заведёнными карточками Friday. При неоднозначности или неполных данных выбор останавливается. Текст выбранной задачи попадает к настроенным моделям; простая проверка отвергает некоторые формы секретов и личных идентификаторов, но не является полноценным обнаружением личных данных. Храните в задачах только данные, разрешённые для передачи моделям.

Перед выбором новой задачи Friday продолжает свою незавершённую задачу или проверяет замечания к своему открытому PR. `cruise` повторяет этот цикл, пока процесс запущен, с интервалом не менее 60 секунд. Если подходящих задач нет, он ждёт; при ошибке повторяет чтение на следующем цикле. Для исполнения нужны `github.selection` (`key_prefix`, `required_labels`, `excluded_labels`, `priority_labels`) и `autonomous_delivery` с `transport: "github"`, `target_branch` и `ci_policy.workflow_tree` — проверенным Git-хешем каталога `.github/workflows`. `github.require_private: true` требует приватный репозиторий, а `github.require_no_webhooks: true` — отсутствие активных репозиторных вебхуков. Перед push и созданием PR Friday повторно сверяет настройки и целевую ветку; эти проверки не изолируют сторонние GitHub-приложения и не устраняют гонку изменения GitHub после проверки.

На macOS `long-weekend service install` устанавливает отдельный LaunchAgent для указанного профиля и периодически вызывает `next`; он может запускать модели, отправлять ветки и создавать черновые PR. Установка проверяет `doctor`, а `uninstall` удаляет только принадлежащий этому экземпляру Friday агент. Ошибки записываются в `project-*.log` внутри `FRIDAY_HOME`. Секреты в файл сервиса не записываются.

GitHub-доставка отправляет только принадлежащую задаче ветку и создаёт черновой PR. Незавершённую операцию создания Friday сверяет с GitHub перед повтором и не создаёт второй PR при неопределённом результате. Замечания из неразрешённых актуальных нитей, обзорных ревью и комментариев PR рассматриваются как непроверенные предложения; изменения проходят локальный гейт и ревью. Если замечание изменилось или было разрешено во время исправления, результат не публикуется. Friday не отвечает в обсуждениях, не объединяет PR и не выкладывает приложение.

Для режима нужен существующий Git-репозиторий и профиль с `worktree_root`, `base_branch`, модельными раннерами и остальными настройками автономной работы. Карточка создаётся локально без обращения в Трекер. При ошибке после создания карточки `resume` продолжает её с сохранённой постановкой; изменение файла постановки не меняет уже созданную карточку. Повторный `start` с тем же ключом не перезаписывает её.

Режим по постановке ведёт один план в одной рабочей копии и останавливается после его выполнения. GitHub-цикл может последовательно выбирать задачи из бэклога. Создание взаимосвязанных задач в Трекере, параллельная разработка в отдельных ветках и самостоятельное развёртывание не поддерживаются. Объём плана и стоимость вызовов моделей заранее не ограничены отдельным бюджетом; используйте постановку с ограниченной целью. Правила изоляции, лимиты этапов и ограничения автономной доставки остаются теми же, что у `home-stretch`.

Журнал — производный файл `<ключ>.md` в `journal_dir`. Friday перезаписывает только файл со своей меткой `friday:generated`; личные заметки храните в отдельном файле. При конфликте с существующим файлом Friday остановится.

## План и проверки

`research`, `brief` и `home-stretch` запускают только встроенные ограниченные адаптеры на macOS после проверки песочницы. Самостоятельная команда `preview` и сборка `release` пока недоступны. Гейт работает в Docker без сети.

Текущий адаптер Vite ожидает переменную `VITE_API_APOLLO_URI`. Для поведенческой проверки Friday поднимает снимок чистого коммита в контейнере `--network none`, без файлов `.env` и `.npmrc`. Локальный мост отдаёт страницу браузеру, а приложение в браузере может обращаться только к этому локальному адресу и заданному HTTPS-адресу staging. Перед проверкой Friday тестирует фильтр Chrome на двух локальных серверах и сверяет API-адрес собранного клиента. Стенд требует установленный Chrome DevTools MCP с поддержкой `--allowedUrlPattern` и Chrome 149 или новее; снимки с Git-подмодулями или символическими ссылками пока не поддерживаются.

Для полностью локального приложения профиль может выбрать `browser.mode: "local"` и `preview.backend: "docker-local"`. Тогда `preview.command` запускает сервер из локального `gate_image` в одноразовом контейнере без сети, `preview.port` задаёт его внутренний HTTP-порт, а необязательный `preview.api_port` — порт для запросов `/api`. Браузеру разрешён только случайный адрес локального моста; staging и заимствованная авторизация в этом режиме запрещены. В образе и команде стенда нужно самостоятельно предусмотреть тестовую БД, синтетические данные и проверку зависимостей; Friday не делает произвольную программу безопасной сам по себе. При остановке контейнер и его временные данные удаляются.

Если в профиле настроена браузерная авторизация, Friday ищет подходящую авторизованную вкладку локального стенда, сверяет staging API и проверяет сессию запросом на чтение. Действующая сессия передаётся только в отдельный браузерный контекст проверки и удаляется после неё; модели и журналу токен не передаётся. Если активной сессии нет, `doctor` и `home-stretch` сообщают об этом до запуска агентов.

```sh
friday plan TASK-1234 /путь/к/plan.json
friday research TASK-1234
friday approve-plan TASK-1234
friday ready TASK-1234
friday brief TASK-1234 implementation --role develop
friday brief TASK-1234 implementation --role review
friday brief TASK-1234 implementation --role blind-code
friday brief TASK-1234 implementation --role blind-behavior
friday gate TASK-1234 implementation
friday stage close TASK-1234 implementation --gate
friday home-stretch TASK-1234
friday wrap-up TASK-1234
```

Формат плана показан в [examples/plan.json](../examples/plan.json). Зависимости проверяются на циклы. Для каждого вида задания в профиль добавляется `runners`: объект с ключами `develop`, `review`, `blind-code`, `blind-behavior`; у каждого — строка `model` и массив аргументов `command`. Адаптер получает JSON-задание на stdin и пишет ответ в stdout. Ревью-адаптеры должны вернуть JSON с `"verdict": "pass"` или `"fail"`; их заявленная модель должна отличаться от модели разработки. Для `blind-behavior` передаются критерии, роль и модель, для `blind-code` добавляется diff. Это ограничение входных данных, а не системная песочница для адаптера.

Новые задачи по умолчанию утверждают загруженный план автоматически; `clock-in --manual` включает ручное утверждение командой `approve-plan`. `plan --replace` заменяет план, сохраняя старые этапы в истории и отменяя прежнее утверждение в ручном режиме. `decide` хранит устойчивое решение; при его изменении закрытые этапы открываются заново, а старые проверки и разовые разрешения перестают подходить к текущей версии решения.

`research` вызывает настроенный `plan` runner, передаёт ему постановку и рабочую копию, а при наличии ссылки на Figma — Definition of Ready из профиля. Модель сама выбирает решения при неопределённости и сохраняет их с обоснованием в допущениях карточки и журнала. Если она всё же вернула вопросы, Friday просит её пересмотреть план; после неудачной повторной попытки возвращается ошибка плана. Вопросы из старых карточек передаются исполнителю как контекст и не блокируют работу. `home-stretch` может сам запустить исследование, если плана ещё нет. Перед коммитом Friday проверяет предел в десять файлов и 500 добавленных строк; если план перечисляет файлы этапа, изменения вне списка останавливают выполнение.

### Автономная доставка и ревью

При включённой автономной доставке `friday clock-in KEY --profile ...` создаёт задачу в автоматическом режиме на базе ветки `base_branch` из профиля, а `friday home-stretch KEY` после успешных этапов может отправить ветку задачи и создать черновой MR в настроенную целевую ветку. Слияние, выкладка и ответы в обсуждениях не выполняются. Ручной режим `clock-in --manual` не включает автономную доставку.

Friday проверяет зарегистрированную рабочую копию, ветку, актуальность гейта и ревью, адрес push и целевую ветку. Чужую удалённую ветку он не занимает. Перед push он сверяет хеш `.gitlab-ci.yml` и коммит общего CI-шаблона с профилем; при расхождении останавливается. Политику CI и разрешённую целевую ветку нужно настроить и проверить для своего проекта. Это проверка конфигурации, а не изоляция сети GitLab CI: внешние сервисы и изменения шаблона между проверкой и запуском CI Friday не контролирует.

`keep-watch` и установленный через `service install` фоновый наблюдатель продолжают запущенные задачи и читают обсуждения созданных Friday MR. `service refresh` обновляет пути к установленным CLI в уже принадлежащем Friday наблюдателе. Новые и изменённые замечания других участников передаются модели как непроверенные предложения; обоснованные исправления проходят ревью и гейт перед очередным push. Обработанные замечания не повторяются, на них не отправляется ответ. При изменении или разрешении замечания во время обработки Friday не публикует устаревший результат. Прерванный push сверяется с удалённой веткой; при неопределённом создании MR Friday ищет совпадающий MR и не создаёт второй, пока результат неясен.

План может содержать `crew` — предложения модели о составе команды этапа; форма показана в [examples/team-plan.json](../examples/team-plan.json). Профиль задаёт каталог `agents` (у каждого `vendor`, `model`, разрешённые `roles` и `command`), каталог `skills` и `max_agents_per_stage` (по умолчанию 6, максимум 16). Каждое назначение содержит `id`, `agent`, `role`, `brief`, `skills` и `depends_on`. Friday проверяет каталог, предел, зависимости и заявленного другого поставщика для ревью, затем сохраняет предложения в карточке. Диспетчер исполняет назначения по зависимостям последовательно, передаёт результаты предшественников, записывает доказательства и не повторяет уже выполненные задания. Для `home-stretch` в команде обязательны роли `review`, `blind-code` и `blind-behavior`. Выбранный скилл должен быть явно указан в профиле с полем `path`; его текст передаётся модели. После прерывания запущенного задания Friday останавливается для проверки состояния. Параллельное выполнение команды ещё не реализовано.

Для Claude и GLM добавлен [адаптер Claude Code](../adapters/claude.py) в ограниченном режиме без shell и MCP. Он использует авторизацию Claude Code либо `FRIDAY_CLAUDE_API_KEY`; для GLM — `FRIDAY_ZAI_TOKEN` или файл с правами только владельца. Профиль может указать `token_file` и, для файла `KEY=VALUE`, `token_key`. Существующие глобальные настройки Claude не переписываются. На вымышленном временном проекте Claude проверен чтением, правкой, ревью и составлением плана, GLM — чтением и ревью; Codex проверен на ответе с отключёнными shell-инструментами. Эти проверки не подтверждают безопасность запуска на рабочих задачах.

Адаптер можно указать и непосредственно в `runners`: используйте `command: ["python3", "{claude_adapter}"]`, `vendor: "anthropic"` для Claude или `vendor: "zai"` для GLM. Для GLM поля `token_file` и `token_key` передаются через окружение как при исследовании, так и при ручном запуске роли.

Встроенный [адаптер Codex](../adapters/codex.py) вызывает установленную команду `codex exec`. Для него `command` в каждом runner — `["python3", "{codex_adapter}"]`, а `model` — имя доступной модели Codex. Профиль разрешений ограничивает доступ рабочей копией, запрещает файлы окружения и сеть для команд модели; модель получает только отдельный браузерный канал во время поведенческой проверки. Git-команды выполняются с выключенными hooks и проверкой внешних фильтров. Отправка данных модели происходит при вызове `research`, `brief` или `home-stretch`.

`home-stretch` последовательно выполняет готовые этапы в рабочей копии Friday: вызывает разработчика, создаёт локальный коммит, запускает ревью и слепые проверки, затем гейт и закрытие. При отрицательном ревью или провале гейта передаёт результат разработчику и повторяет цикл до трёх попыток. Недоступность среды, незнакомая ветка или неожиданное изменение рабочей копии останавливают процесс. После успешных этапов команда выполняет автономную доставку, если она включена в профиле. Если процесс прервётся во время работы модели, незакоммиченные изменения может потребоваться проверить вручную перед продолжением.

`wrap-up` показывает критерии и доказательства этапов. Он считает финальный гейт пройденным только для закрытого этапа `final`, если его снимок, команда и образ по-прежнему совпадают с текущими. Решение владельца и документ выводятся отдельно от гейта. Журнал также содержит таблицу критериев и записанных доказательств.

Гейт требует `gate` (массив аргументов) и `gate_image` (локальный Docker-образ) в профиле. Friday архивирует чистый коммит, проверяет, что архив содержит все отслеживаемые файлы без изменений, и монтирует его в контейнер на `/workspace` только для чтения. Сеть контейнера выключена. Подмодули, незакоммиченные изменения и `export-ignore` не поддерживаются; образ должен уже содержать необходимые зависимости. Режим `git-diff` создаёт временный Git-индекс от базы плана, чтобы команда внутри контейнера видела изменения всей задачи. Можно подключить находящийся в образе `node_modules` и потребовать совпадения lockfile с образом. Для закрытия запланированного этапа по гейту также требуются три положительных ревью текущего коммита. `--document ПУТЬ` принимает документ с последней непустой строкой `VERDICT: pass`; `--owner ТЕКСТ` записывает решение владельца. После недоступности среды успешный повторный гейт снимает блокировку в автоматическом режиме; в ручном режиме закрытие остаётся за владельцем.

Образ гейта должен быть собран для конкретного проекта и содержать необходимые зависимости. Приватные реестры и токены настраиваются локально, вне Git.

Если проверки проекта требуют отдельный путь `/private/tmp`, профиль может задать `gate_private_tmp: true`: Friday создаст там дополнительный временный раздел внутри контейнера. Это значение входит в отпечаток гейта.

При настроенном `gate_lockfile` Friday останавливается до запуска модели, если lockfile рабочей копии отличается от lockfile образа.

## Наблюдение и доставка

```sh
friday mr TASK-1234 123
friday watch TASK-1234 --once
friday keep-watch --once
friday keep-watch --interval 300
friday service install --interval 300
friday sentry TASK-1234 --period 24h
friday draft TASK-1234 publish --file /путь/к/черновику.txt
friday approve TASK-1234 ИДЕНТИФИКАТОР
friday send-off TASK-1234 ИДЕНТИФИКАТОР
friday clear-desk TASK-1234
friday clear-desk TASK-1234 --confirm ОТПЕЧАТОК
friday release TASK-1234 1.2.3
```

`keep-watch` опрашивает привязанные MR, уведомляет локально на macOS о завершении CI, вливании и новых обсуждениях; одинаковое состояние повторно не сообщает. Если в настройках `gitlab` указать `deployment_environment`, Friday также ищет MR среди связанных с последними 20 успешными выкладками этого окружения. Если связь не найдена, вывод не утверждает, что выкладки не было. Постоянный режим работает, пока запущен процесс. Ошибки чтения он повторяет на следующем цикле. `service install` устанавливает macOS LaunchAgent с периодическим запуском; `service uninstall` удаляет только принадлежащий этому экземпляру агент. Секреты в LaunchAgent не записываются: для GitLab через `glab` используется его авторизация, для HTTP — `token_file`. О новой ошибке наблюдения агент уведомляет один раз и пишет её в `watch.log` внутри `FRIDAY_HOME`.

`sentry` читает события и ищет совпадения строк стеков с добавленными строками между базой плана и текущим коммитом. Для этого добавьте в профиль `sentry` с полями `base_url`, `organization`, `project` и необязательным `token_env`; токен по умолчанию берётся из `FRIDAY_SENTRY_TOKEN`. Команда требует чистую рабочую копию и загруженный план. Она проверяет не более десяти страниц событий, сообщая `truncated`, если есть ещё страницы. Совпадение означает наличие кадра на изменённой строке, а не доказанную причину ошибки; без корректных source maps совпадения могут быть пропущены. `keep-watch` также опрашивает Sentry для задач с настроенным профилем и планом и уведомляет о новых совпадениях один раз.

Для доставки профиль задаёт `actions`: имя действия → массив аргументов программы либо объект с `command`, списками `bound_env` и `bound_files`. Программа получает текст черновика на stdin. Аргументы `{key}`, `{worktree}`, `{branch}`, `{mr}`, `{head}` подставляются целиком; разрешение учитывает получившиеся аргументы, содержимое исполняемых файлов и файлы, переданные как аргументы или перечисленные в `bound_files`, значения `bound_env`, текст и коммит. `draft` показывает команду и ничего не отправляет, `approve` фиксирует разрешение, `send-off` использует его один раз. Если процесс прервался или вернул ошибку, статус остаётся неопределённым: автоматически повторять действие нельзя, сначала проверьте результат во внешней системе. Зависимости адаптера и переменные, не указанные в профиле, не входят в отпечаток; в частности, версия MCP зафиксирована в команде, но содержимое кэша `uvx` не хешируется.

В своём профиле можно настроить действия `tracker-create` и `gitlab-draft`. Целевую ветку MR задаёт решение `target_branch`: это может быть предыдущая ветка цепочки. Адреса, проект и файлы учётных данных подставляются из профиля; изменение токена или текста после утверждения требует нового черновика.

[Адаптер GitLab](../adapters/gitlab.py) создаёт черновой MR через `glab api`. Для создания stdin должен содержать JSON с `title` и `description`, а аргументы команды — `--base`, `--project`, `--source`, `--target`; токен можно задать через `--token-file`. В другом профиле настройте команду в `actions` и проверьте целевую ветку. Friday не сохраняет вывод команды доставки, поэтому созданный MR пока нужно привязать вручную через `friday mr`. Слияние заблокировано: GitLab проверяет SHA исходной ветки, но не предоставляет здесь атомарной проверки целевой ветки. Готового адаптера выкладки пока нет.

[Адаптер Tracker](../adapters/tracker.py) создаёт задачу через MCP по утверждённому JSON, где обязательны строковые `queue` и `summary`. Дополнительные поля передаются в MCP напрямую или как дополнительные поля Tracker; вложенный ключ `fields` в черновике не принимается. Токен и организацию можно указать файлами через `--token-file` и `--org-file`. Он также подключается через `actions`, `draft`, `approve` и `send-off`. Планировщик может предложить отдельные задачи, но Friday пока не превращает эти предложения в заполненные черновики автоматически.

`clear-desk` без `--confirm` показывает путь, коммит и игнорируемые файлы рабочей копии вместе с отпечатком. Второй вызов удаляет именно эту зарегистрированную рабочую копию, только если проверенный снимок не изменился. Незакоммиченные изменения блокируют очистку. Чтение и хеширование больших игнорируемых файлов может занять время. Блокировка координирует процессы Friday; внешние программы и ручное редактирование она не останавливает.

Если Git отказал в удалении и копия осталась на месте, `friday clear-desk КЛЮЧ --cancel` снимает незавершённое намерение; затем можно получить новый снимок. Если удаление произошло, но запись результата прервалась, повторите команду с прежним `--confirm`.

`release` пока недоступен: изоляция сборки и сетевых действий для выпуска ещё не реализована.

## Границы текущей версии

Ещё не реализованы автоматическая выкладка, прямое чтение макета Figma, автоматический вынос задач в Трекер и параллельное выполнение этапов в отдельных копиях. Настоящая слепая проверка через браузер ещё не подтверждена на рабочей задаче; ограничения моделей не подтверждены для рабочих задач. Не используйте текущую версию для автоматической доставки без проверки адаптера.

Успешный рабочий ответ — JSON в stdout; ошибка — JSON в stderr и ненулевой код. `--help`, `-h` и вызов без аргументов выводят текстовую справку. [Правила разработки](../CONTRIBUTING.md), [исследование](research.md), [MIT](../LICENSE).
