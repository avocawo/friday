# Руководство Friday

## Установка

1. Клонируйте Friday и добавьте `bin` в `PATH` или задайте `FRIDAY_BIN`.
2. Установите нужные агентам CLI: Claude Code (`claude`) для моделей Anthropic и Z.ai, Codex CLI (`codex`) для моделей OpenAI. Войдите в них как обычно.
3. Для гейта и браузерной приёмки установите Docker. Для браузерной приёмки нужен Chrome с отладочным портом 9333 и вход в стенд.
4. Состояние хранится в `~/.local/share/friday` (переопределяется через `FRIDAY_HOME`). Профили и секреты в репозиторий не попадают: папка `profiles/` в `.gitignore`.

### Плагин для Codex и Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

Плагин учит агента читать `status` и `plan`, а запуск, утверждение и решения оставляет вам.

## Как идёт задача

1. **`start`** создаёт ветку `<репозиторий>/KEY` (например, `octis/31`) от свежего `origin/<base_branch>` и рабочую копию, фиксирует раскладку моделей и пишет план: вехи из 2–5 этапов, файлы, оценку объёма, кодовые и браузерные критерии, выжимку правил проекта для исполнителя. План проверяется без модели (объём, файлы, порядок, критерии), потом его проверяет модель другого вендора, и планировщик один раз отвечает на замечания: принимает или отклоняет с обоснованием.
2. **`plan`** показывает план, вопросы, отклонённые замечания и пересечения файлов с другими активными задачами.
3. **`approve`** утверждает план и запускает конвейер в фоне (`--no-run` — только утвердить, потом `run`).
4. **Веха.** Исполнитель работает в одной сессии на веху и коммитит каждый этап. Гейт запускается на коммите; при провале исполнитель получает только упавшие секции лога. Ревью смотрит дифф этой вехи вместе с результатом гейта. Блокирующие находки исполнитель исправляет или оспаривает; оспоренные уходят вам. Вехи с интерфейсом проходят браузерную приёмку в изолированном preview. После двух провалов подряд Friday повышает уровень исполнителя в пределах `executor_tiers`, если профиль задаёт это ограничение; замена начинает новую сессию.
5. **Финал.** Роли из `final_review_roles` проверяют весь дифф: по умолчанию финальное ревью и слепая проверка идут параллельно; профиль может оставить одно финальное ревью. Блокирующие находки получают один раунд исправлений.
6. **Черновой MR** открывается, если в профиле задан `delivery`; иначе его текст сохраняется в `merge-request.md` в папке задачи.

Конвейер останавливается, когда гейт так и не прошёл, исполнитель ничего не сделал, среда недоступна, кончились модели по правилам или исчерпан настроенный бюджет. Пересечение параллельных изменений, сохранённые неинтегрированные ветки и дрейф входов финального ревью также требуют разбора перед продолжением. Разногласия ревью его не останавливают. Веха, которую ничто не проверило (нет гейта, проверки исполнителя не запускались, браузерной приёмки не было), закрывается как «готова, не проверена» с причинами — в статусе, журнале и MR ([ADR 0009](adr/0009-unverified-is-not-done.md)); если без гейта проверки исполнителя не смогли запуститься, веха блокируется.

`decide KEY name "текст" --reopen M2` записывает ваше решение. Переоткрываются только названные вехи и зависящие от них; без `--reopen` решение учитывают следующие вехи. `resume` продолжает остановленную или упавшую задачу, `stop` останавливает идущую: агенты завершаются вместе с дочерними процессами.

Исходная постановка сохраняется целиком и передаётся исполнителям и ревью: сокращение фактов в плане не теряет точные хеши и URL. Для старой карточки без сохранённой постановки используйте `resume KEY --brief task.md`. Восстановление допускается только при совпадении текста с отпечатком исходного планирования; другой текст требует нового плана. Утверждение, этапы и счётчики бюджета не сбрасываются.

## Профиль

Профиль — JSON-файл. Ключ `extends` подключает другой профиль (например, общий каталог моделей); пути считаются от файла профиля.

| Ключ | Назначение |
| --- | --- |
| `name`, `repository` | Имя и путь к репозиторию проекта |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | Откуда и где создавать ветку задачи; по умолчанию `<репозиторий>/{key}`, явный `branch_template` принимает один `{key}`, раскладка `key` или `branch` |
| `models`, `roles` | Каталог моделей и предпочтения по ролям (ниже) |
| `engineering_policy` | Правила для планировщика и ревью |
| `rules_docs` | Документы с правилами проекта, по которым Friday один раз делает дайджест для планировщика и проверяющего план (по умолчанию `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). Дайджест хранится по хешу содержимого и переиспользуется задачами, пока документы не меняются; планировщик не читает их целиком |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | Карта репозитория в промпте планировщика и проверяющего план, чтобы они не разведывали структуру вызовами: `none` (по умолчанию) — без карты; `builtin` — отслеживаемые файлы с числом строк; `graphify` — плюс символы каждого файла и сколько файлов его импортируют, по графу [graphify](https://github.com/Graphify-Labs/graphify) (`uv tool install 'graphifyy[mcp]==0.9.100'`, только разбор кода, без модели; граф лежит в `FRIDAY_HOME/maps`, не в репозитории). На замере CS-2 карта не удешевила планирование (без карты $6.19, `builtin` $7.08, `graphify` $7.97 — по одному прогону), поэтому выключена по умолчанию. Карта кэшируется по коммиту; длиннее `repo_map_budget` символов (60000) — сначала без символов, потом со свёрнутыми папками. `repo_map_mcp: true` (только с `graphify`) даёт обеим ролям запросы к графу: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`; на Codex не проверено вживую. Проверяющий план получает текущий текст файлов плана (до 40000 символов) |
| `approval` | `owner` (по умолчанию) — план ждёт `approve`; `auto` — план утверждается сам после проверки и конвейер сразу запускается, в журнал уходит «План утверждён автоматически» |
| `limits` | `stage_files` и `stage_lines` — лимиты этапа (10 и 500); необязательные `task_milestones` и `task_stages` ограничивают весь план до реализации |
| `worktree_setup` | Команды, которые Friday запускает в новой рабочей копии до планирования (зависимости и подобное): массивы аргументов с подстановкой `{repository}` и `{worktree}`; должны быть повторяемыми. Пример для npm на macOS: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Команды, которые исполнитель может запускать сам, точной формой: `"python3 -m pytest"`, а не `python` |
| `executor_deny_read` | Дополнительные пути, которые shell исполнителя не может читать |
| `executor_tiers` | Разрешённые уровни всех пишущих агентов, например `["strong", "efficient"]`. Без поля разрешены все уровни. Сложность, эскалация, квота и финальные исправления соблюдают ограничение |
| `milestone_rounds` | Сколько раундов исполнителя на веху (4) |
| `max_parallel_milestones` | Одновременно выполняемые независимые готовые вехи с `parallel=true` (2); `1` выполняет их последовательно |
| `budget` | Необязательные положительные `max_model_runs` и `max_milestone_runs`: предел допущенных вызовов всех ролей на задачу и на веху. Резервирование атомарное; неудачные и незавершённые попытки считаются, `resume` и повторное открытие счётчики не сбрасывают. При исчерпании — `budget_exhausted`; бюджет меняют явно в профиле. Это предел вызовов, не стоимости |
| `final_review_roles` | `["final-review", "blind-code"]` по умолчанию; `["final-review"]` оставляет одну финальную проверку. Готовые результаты сохраняются независимо и повторно используются только при неизменных исходниках, плане, решениях, настройках и входах роли |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | Команда проверки в Docker; `git-diff` сравнивает с базой задачи. Как собрать образ гейта, профиль описывает шагом (`steps`) |
| `environment_errors` | Шаблоны строк лога, означающих сбой среды, а не кода |
| `browser`, `preview`, `behavior_test_policy` | Стенд, preview и правила браузерной приёмки. Бэкенды preview: `docker-vite` (Vite в gate-образе без сети; с `browser.mode: local` — без стенда API), `docker-local`, `storybook` (витрина из `stories` со снимком кита в `mount`, [ADR 0008](adr/0008-ui-kit-preview-and-design-check.md)). У `storybook` всё проектное — в профиле: `command` (массив аргументов, который поднимает витрину; `{mount}` — путь кита), `port`, `env`, `tmpfs` (абсолютные пути в контейнере, доступные на запись), `links` (ссылки из снимка в образ, например `{"node_modules": "/app/node_modules"}`); образ — `stories.image` |
| `stories` | Второй репозиторий задачи — витрина компонентов (Storybook), внутри которой лежит рабочая копия кита: `repository`, `base_branch`, `worktree_root`, `mount` (обязателен: путь кита внутри витрины), `setup` (команды в новой рабочей копии; `{repository}`, `{worktree}`, `{kit}`), `commands` (проверки исполнителя), `image` (образ для preview), `themes` (темы, в каждой из которых браузерная приёмка открывает историю и сравнивает состояния компонента между собой) и `theme_query` (обязателен при `themes`: параметр URL темы с `{theme}`). Файлы витрины в плане пишутся как `stories:src/stories/X.stories.ts`; итог — ветка задачи в обоих репозиториях |
| `steps` | Шаги проекта, о которых Friday ничего не знает сам; запускает их только владелец (`friday step NAME [KEY]`, без имени — список и состояние) ([ADR 0011](adr/0011-profile-steps.md)): `{"<имя>": {"run": [...], "scope": "task" \| "profile", ...}}`. `run` — массив аргументов, выполняется на хосте; подстановки у шага задачи `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`, у любого шага `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}`, `{secret.<имя>}`. `description`, `env` (без значений секретов), `cwd`. `lock` — общий ресурс на время шага: путь делит блокировку репозитория, имя — именованная блокировка. `commit: {"paths": [...], "message": "{key}: ..."}` — Friday коммитит эти пути; шаг устаревает, когда ветка после его коммита меняется вне них. `required` (шаг задачи) — пока шаг не выполнен или устарел, `status`, журнал и текст MR напоминают о нём с командой. `check` (шаг профиля) — команда готовности для `doctor`: 0 — готово, 2 — устарело (!), другое — нет (✗). `secrets: {"<имя>": "<путь>"}` — файлы, которые команда получает путём; Friday их не читает. Сложную процедуру кладите скриптом рядом с профилем |
| `design` | Дизайн-инструменты для UI-задач ([ADR 0007](adr/0007-design-tools.md)). `figma: {"url": "http://127.0.0.1:3845/mcp"}` — локальный Dev Mode MCP-сервер Figma desktop; `tools` сужает список инструментов чтения (`get_metadata`, `get_design_context`, `get_screenshot`, `get_variable_defs`), пишущие инструменты не принимаются. Если в тикете есть ссылка `figma.com/design/…?node-id=…`, `start` проверяет, что узел открыт в активной вкладке Figma, а планировщик и проверяющий план читают фрейм и записывают в план измеримую спецификацию (раздел «Макет»). Исполнитель и ревью получают её в промпте, без доступа к Figma. Скриншоты фреймов Friday сохраняет в папку задачи; браузерная приёмка сравнивает с ними preview и замеряет стили (`computed_style`): расхождение с числом спецификации блокирует, расхождение на глаз уходит в «Мелкие замечания» MR. Если Figma не отвечает или узла нет, `start` останавливается и говорит, что открыть; `start --no-design` планирует без макета. `impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` — файлы `reference/` скилла /impeccable, которые Friday вкладывает в промпт UI-вех; `references` обязателен и сопоставляет ролям `develop`, `review`, `final-review` списки файлов (например, `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API или MCP) для чтения постановки |
| `journal` | Куда писать журнал задачи: `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]`; `page` — путь страницы задачи внутри `dir` (по умолчанию `{key}.md`), например в папку задачи в Obsidian. `journal_dir` и `journal_page` — короткая запись одного markdown-журнала; заданный в профиле (или унаследованный) `journal` важнее неё. Страницу, которую написал не Friday (нет `friday_generated` в front matter), Friday не трогает: печатает «Пропущено» и пишет остальное |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` и ключ `github.repository` или `gitlab.base_url` + `gitlab.project` |

Имя репозитория берётся из URL `origin` (HTTPS, SSH или локальный путь),
без `.git`; если `origin` отсутствует — из имени основного репозитория на диске,
в том числе при работе из связанного worktree. Символы вне `A–Z`, `a–z`, `0–9`,
`_` и `-` заменяются на `-`, крайние `-` убираются. Пустое имя требует явного
`branch_template`. Полный ключ задачи сохраняется: `31` даёт `octis/31`,
`OCTIS-031` — `octis/OCTIS-031`. Ветка, уже записанная на карточке задачи,
сохраняется при продолжении; новая настройка действует на новые задачи.
Связанный showcase использует имя основного репозитория задачи.

### Модели и роли

```json
"models": {
  "fable": {"model": "claude-fable-5-1", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver` — чем запускать: `claude` или `codex`. Z.ai идёт через Claude Code; токен читается из файла только с правами владельца.
- `tier` — `frontier`, `strong` или `efficient`; `strength` упорядочивает модели внутри уровня.
- `effort` — глубина рассуждения (`low` … `max`); одну модель можно описать несколько раз с разным effort.
- `scarce` — дорогая модель: используется один раз на задачу, если правила позволяют обойтись без неё.
- `price` — цена за миллион токенов по видам (`input`, `output`, `cache_read`, `cache_write`) для оценки расхода, когда вендор цену не сообщает.

Роли: `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. Списки в `roles` — предпочтения: если подходящей модели в списке нет, Friday берёт другую из каталога. Жёсткие правила: код смотрят только `frontier`-модели, ревьюер не слабее автора работы, слепую проверку делает не автор кода. Мягкие правила (по порядку): не та же модель, что автор; дорогая модель один раз; другой вендор; слепая проверка не от автора плана. Нарушение мягкого правила возможно, только если иначе нельзя, и попадает в историю задачи.

Пример раскладки — [examples/models.json](../examples/models.json).

При ограничении `executor_tiers` сложная веха использует самый высокий разрешённый
уровень, а замена при квоте сохраняет требуемый уровень внутри ограничения.
Старая раскладка с запрещённым исполнителем заменяется допустимым; запись
от имени запрещённой или не соответствующей каталогу модели отклоняется.
Уровни и имена берутся из каталога профиля, а не определяются Friday по имени модели.

Параллельные вехи получают отдельные worktree и интегрируются в порядке плана.
Friday проверяет пересечения заявленных путей до старта и фактических изменений
перед интеграцией. Работа, которую не удалось интегрировать, сохраняется в своей
ветке и worktree; `parallel_recovery_required` указывает их перед продолжением.
После разбора сохранённой работы контроллер завершает её перенос или сохраняет
нужные коммиты отдельно, затем удаляет разобранные lane worktree и ветки обычными
Git-командами. Friday не удаляет такие результаты автоматически ради повтора.

Сохранённое финальное ревью связано с чистыми рабочими копиями, коммитами обоих
репозиториев, планом, решениями, настройками моделей и точным текстом входа роли.
Изменение входов во время проверки возвращает `stale_evidence`. При сбое второй
роли уже завершённая первая сохраняется; следующий `resume` запускает только
недостающие проверки для тех же входов. Повышение `budget` и изменение
`max_parallel_milestones` сохраняют готовое ревью: эти настройки управляют
допуском и расписанием, а не содержимым проверки.

## Журнал

Карточка задачи — единственный источник правды; журналы её отображают и обновляются сами после значимых событий: план готов и утверждён, веха готова или упала, решение владельца, финал, MR, остановка. Вручную — `friday journal KEY`.

Время — сумма длительностей вызовов, включая параллельные, а не календарное время.
Для новых вызовов без длительности провайдера runner измеряет её сам. Прерывание
до старта runner записывает нулевое время исполнения; новое неизмеренное
исполнение сохраняет неизвестную длительность. Старые
связанные события дают явно отмеченную оценку, которая может включать ожидание
слота. У потерянного вызова без измерения длительность неизвестна. Неизвестная
цена показывается также по ролям; она не превращается в нулевую стоимость.

- `markdown` — страница `KEY.md` и общая страница «Friday — сейчас» со всеми задачами. Для Obsidian укажите папку хранилища: у страниц front matter (ключ, состояние, расход, тег `friday`), задачи связаны wiki-ссылками. На странице задачи — план с допущениями и несогласованными замечаниями, вехи со сводкой исполнителя и коммитами, спорные находки, решения, расход по ролям и хронология.
- `jsonl` — все события задачи для анализа в таблицах или дашбордах.

Шаблоны — Markdown с подстановками `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. Friday берёт шаблон из поля `template` получателя, затем `.friday/task.md` в репозитории проекта, затем встроенный ([friday/templates](../friday/templates)). Текст между `<!-- friday:notes -->` и `<!-- /friday:notes -->` — ваш: он сохраняется при каждом обновлении. Страницу, которую писал не Friday, он не перезаписывает.

## Настройки машины

`FRIDAY_HOME/machine.json` задаёт общие ресурсы для всех задач:

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

По умолчанию один гейт и два браузера одновременно, вендоры не ограничены. Квоты вендоров учитываются автоматически: запуск, упёршийся в лимит, записывает, когда квота вернётся, и до этого вендор при подборе пропускается.

## Границы

- **Песочница исполнителя.** Shell исполнителя (Claude Code) работает в песочнице: без сети, без чтения `~/.ssh`, `~/.aws`, `~/.config` и подобных, запись только в рабочую копию и временную папку, без запуска вне песочницы. Команды вне `executor_commands` и git-команд отклоняются. Codex работает в своей песочнице с теми же границами.
- **Git в Codex.** Friday помещает установленный Git и отдельную копию Git-метаданных в runtime задачи. Глобальные Git configs и пользовательские shell-профили не загружаются; служебные данные исходного репозитория агенту не открываются. Исполнитель сохраняет этапы обычными Git-командами. После завершения его процесса Friday получает коммиты через проверенный bundle и возвращает их в исходную ветку, если её HEAD и индекс не изменились. При конфликте состояния bundle остаётся в журнале запуска как `git-recovery.bundle`; автоматической перезаписи состояния нет. Ревьюер получает Git-метаданные только на чтение. `doctor` проверяет реальный сценарий трёх коммитов в linked worktree без вызова модели, а также сохранение запретов чтения секретов и записи для ревьюера.
- **Ревьюеры** только читают. Слепая проверка запускается в пустой папке.
- **Гейт** работает в контейнере без сети на снимке коммита, смонтированном только для чтения.
- **Браузер** получает только инструменты Friday для одного preview (включая `hover` и `computed_style` — чтение стилей фиксированным скриптом, без `evaluate_script`); обход авторизации и чтение заголовков авторизованных запросов запрещены.
- **Figma** читают только планировщик и проверяющий план, и только инструментами чтения локального сервера Figma desktop. Скилл /impeccable внутри ролей не запускается: его тексты Friday кладёт в промпт.
- **Публикация.** Friday пушит только ветку своей задачи и открывает только черновой MR/PR, не перезаписывает чужую ветку, не сливает и не развёртывает.
- **Что ещё не проверено вживую:** браузерная приёмка и публикация в GitLab проверены тестами с фейками. Git в среде Codex дополнительно проверяется настоящей локальной лабораторией без вызова модели; модельное выполнение роли проверяется отдельно на каждой задаче.
