## Installation

1. Clone Friday and add `bin` to `PATH`, or set `FRIDAY_BIN`.
2. Install the CLIs that the agents need: Claude Code (`claude`) for Anthropic and Z.ai models, Codex CLI (`codex`) for OpenAI models. Sign in to them as usual.
3. For the gate and browser acceptance, install Docker. Browser acceptance also needs Chrome with the debugging port 9333 and a signed-in session in the test environment.
4. State is stored in `~/.local/share/friday` (override it with `FRIDAY_HOME`). Profiles and secrets do not enter the repository: the `profiles/` folder is in `.gitignore`.

### Plugin for Codex and Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

The plugin teaches the agent to read `status` and `plan`. Starting a task, approving it and making decisions are left to you.

## How a task runs

1. **`start`** creates the branch `<repository>/KEY` (for example `octis/31`) from a fresh `origin/<base_branch>` and a worktree, locks in the role assignment, and writes the plan: milestones of 2–5 stages, files, a size estimate, code and browser criteria, and a digest of the project rules for the executor. The plan is first checked without a model (size, files, order, criteria). Then a model from a different vendor reviews it, and the planner answers the findings once: it accepts each one or rejects it with a reason.
   With `"toolset": {"plan": "project"}` the project's own process writes the plan ([ADR 0015](adr/0015-project-toolset.md)): Friday starts an ordinary Claude Code session in the worktree with the project's settings, hooks, skills, agents and MCP, and passes it `project.plan_command` with the task statement. The session writes the project's plan file (`project.plan_file`) and returns Friday a summary of the same plan in its schema; Friday checks the summary without a model and runs no review by another vendor, because the project's process has its own. The session runs in the `auto` permission mode; its result is the last answer before the process exits, because the project's process may wait for a background review.
2. **`plan`** shows the plan, the questions, the rejected findings, and the file overlaps with other active tasks.
3. **`approve`** approves the plan and starts the pipeline in the background (`--no-run` only approves; run it later with `run`).
   With `"toolset": {"execute": "project"}` Friday runs the project's own process instead of milestones ([ADR 0015](adr/0015-project-toolset.md)): one Claude Code session with `project.execute_command` on the model of the `develop` role. The session commits each stage with its id from the plan summary at the start of the subject (`M1.1: …`) and publishes nothing. A question ends the session: the task stops, the question shows in `status`, and the answer given with `decide` continues the same session in the background; `resume` does the same without an answer. The session receives what stopped it. If the session finished without questions and the environment stopped the task (the gate image, the sign-in to the test environment), `resume` does not wake the session and only repeats the checks after it. After the session Friday checks that the tree is clean, that every stage has a commit within `limits` (`git diff --numstat` of its commits), runs the gate and the browser acceptance of milestones with an interface, then the final check and the MR as usual; the final review in this mode first reads `AGENTS.md` (or `CLAUDE.md`) at the repository root and checks the diff against the sections of the project documents, not only against the plan's rules. Any mismatch becomes a question for the owner.
4. **Milestone.** The executor works in one session per milestone and commits each stage. The gate runs on the commit. If it fails, the executor receives only the failed sections of the log; when a section is longer than the limit, its heading and its error lines with context are kept, failed tests in TAP format (`not ok …` with their diagnostics) first. The milestone review looks at the diff of this milestone together with the gate result. The executor fixes or disputes the blocking findings; disputed findings are sent to you. Milestones with an interface go through browser acceptance in an isolated preview. After two failures in a row, Friday raises the executor's tier within `executor_tiers` when the profile sets that limit; the replacement starts a new session.
5. **Final.** The roles in `final_review_roles` check the whole diff: by default the final review and the blind check run in parallel; a profile can keep only the final review. Blocking findings get one round of fixes.
6. **Draft MR** is opened if the profile sets `delivery`. Otherwise its text is saved in `merge-request.md` in the task folder.

The pipeline stops when the gate never passed, the executor did nothing, the environment is unavailable, the models allowed by the rules are used up, or the configured budget is exhausted. Overlapping parallel changes, retained branches that were not integrated and drifting inputs of the final review also need attention before the task continues. Disagreements in review do not stop it. A milestone that nothing checked (no gate, the executor's checks did not run, no browser acceptance) closes as "done, not verified" with its reasons, in the status, the journal and the MR ([ADR 0009](adr/0009-unverified-is-not-done.md)); if the executor's checks could not run and there is no gate, the milestone is blocked.

`decide KEY name "text" --reopen M2` records your decision. While Friday's plan awaits approval, `decide` also revises it ([ADR 0016](adr/0016-decision-revises-the-plan.md)): the planner rewrites the milestones named in `--reopen` in a new session and the others are carried over as they were; without `--reopen` it chooses the affected milestones itself. Another model reviews only the changed milestones. `decide` prints which milestones were revised in the plan, which were reopened to run again and which only got the decision in their context; `friday plan KEY --diff` shows the difference from the previous revision. If the revision fails, the plan stays as it was and waits for approval, and the decision is recorded: repeat the same `decide`. While a plan of the project's process awaits approval, `decide` continues its session with your answer and shows the new revision of the plan. Each such `decide` is a separate continuation of the session, so answer all the plan's questions in one text. In the same way `decide` answers a question of a stopped execution session of the project's process. Only the named milestones and the milestones that depend on them are reopened. Without `--reopen`, the following milestones take the decision into account. `resume` continues a stopped or failed task. `stop` stops a running task: the agents end together with their child processes.

The original task statement is kept in full and passed to the executors and the reviews, so exact hashes and URLs survive the plan's shortening of facts. For an old card without a saved statement use `resume KEY --brief task.md`. The statement is restored only when the text matches the fingerprint of the original planning; another text needs a new plan. Approval, stages and budget counters are not reset.

When a failed milestone continues, the commits already made keep the original review boundary; no empty extra commit is needed. The executor gets the previous gate failure, with the full body of a Python traceback within the limit of the diagnostic output.

## Profile

A profile is a JSON file. The `extends` key includes another profile (for example, a shared model catalog); paths are relative to the profile file.

| Key | Purpose |
| --- | --- |
| `name`, `repository` | The name of the project and the path to its repository |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | Where to create the task branch from and where to put it; by default `<repository>/{key}`, an explicit `branch_template` takes one `{key}`, the layout is `key` or `branch` |
| `models`, `roles` | The model catalog and the role preferences (see below) |
| `engineering_policy` | Rules for the planner, the executor, the milestone reviews, the final review and the fixes |
| `project_lessons` | Pitfalls of the project that reviews keep finding: a list of short checks. The executor, the milestone reviews, the final review and the fixes check the change against it |
| `rules_docs` | Documents with the project rules. Friday makes one digest of them for the planner and the plan reviewer (default `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). The digest is stored by content hash and reused by tasks while the documents do not change; the planner does not read the documents in full. Patterns expand from the repository root, `**` descends into folders (`docs/**/*.md`, `src/**/README.md`); only the files found enter the fingerprint. The executor, the milestone reviews, the final review and the fixes get the rules the plan chose, the document map of the digest and the task's base revision to search for precedents; the executor searches with `bin/friday-precedent <base> <pattern> [<path>…]` (a wrapper over `git grep` that lets no options through) |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | A repository map in the prompt of the planner and the plan reviewer, so that they do not explore the structure with tool calls. `none` (default): no map. `builtin`: the tracked files with their line counts. `graphify`: also the symbols of each file and how many files import it, taken from a [graphify](https://github.com/Graphify-Labs/graphify) graph (`uv tool install 'graphifyy[mcp]==0.9.100'`; it only parses code, no model is used; the graph is stored in `FRIDAY_HOME/maps`, not in the repository). In a measurement on CS-2 the map did not make planning cheaper (no map $6.19, `builtin` $7.08, `graphify` $7.97, one run each), so it is off by default. The map is cached by commit. If it is longer than `repo_map_budget` characters (60000), it is first shortened by dropping the symbols, then by collapsing folders. `repo_map_mcp: true` (only with `graphify`) gives both roles graph queries: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`; not verified live on Codex. The plan reviewer receives the current text of the files named in the plan (up to 40000 characters) |
| `approval` | `owner` (default): the plan waits for `approve`. `auto`: the plan is approved automatically after review and the pipeline starts at once; the journal records that the plan was approved automatically |
| `limits` | `stage_files` and `stage_lines`: the limits of a stage (10 and 500); the optional `task_milestones` and `task_stages` limit the whole plan before it runs |
| `toolset`, `project` | Who runs a phase: `{"plan": "project", "execute": "friday"}` means the project's process writes the plan and Friday runs it (both phases are `friday` by default). `project`: `plan_command` with `{statement}` is the project's planning command, for example `"/plan-stages {statement}"`; `plan_file` is the plan file in the worktree; `execute_command` and `stage_argument` with `{stages}` are for the execution phase; `session_env` names environment variables the session gets on top of the usual ones (for example `SSH_AUTH_SOCK` for `git fetch`); `disallowed_tools` are tools closed to the session (for example the owner's browser: acceptance is done by Friday's `browser` role); `timeouts` are `idle`, `tool`, `total` in seconds ([ADR 0015](adr/0015-project-toolset.md)) |
| `worktree_setup` | Commands that Friday runs in a new worktree before planning (dependencies and similar): argument arrays with the substitutions `{repository}` and `{worktree}`; they must be repeatable. Example for npm on macOS: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Commands that the executor may run itself, in the exact form: `"python3 -m pytest"`, not `python` |
| `executor_deny_read` | Additional paths that the executor's shell cannot read |
| `executor_tiers` | The tiers allowed for all writing agents, for example `["strong", "efficient"]`. Without the field all tiers are allowed. Complexity, escalation, quota and final fixes respect the limit |
| `milestone_rounds` | How many executor rounds a milestone gets (4) |
| `max_parallel_milestones` | Independent ready milestones with `parallel=true` that run at the same time (2); `1` runs them one after another |
| `budget` | Optional positive `max_model_runs` and `max_milestone_runs`: the limit of admitted runs of all roles per task and per milestone. Reservation is atomic; failed and unfinished attempts count, and `resume` and reopening do not reset the counters. When it is exhausted the task stops with `budget_exhausted`; the budget is changed explicitly in the profile. It limits runs, not cost |
| `final_review_roles` | `["final-review", "blind-code"]` by default; `["final-review"]` keeps a single final check. Finished results are saved independently and reused only when the sources, the plan, the decisions, the settings and the role's inputs are unchanged |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | The check command in Docker; `git-diff` compares with the task base. The profile describes how to build the gate image as a step (`steps`), and `gate_image_step` names that step. If `gate_lockfile` in the image differs from the task's, the task stops: `status` shows "Owner step needed" with the step's command; after the step `resume` repeats the checks and does not wake an execution session of the project's process |
| `environment_errors` | Patterns of log lines that mean an environment failure, not a code failure |
| `browser`, `preview`, `behavior_test_policy` | The test environment, the preview and the rules of browser acceptance. Preview backends include `storybook` (the showcase from `stories` with a snapshot of the kit at `mount`, [ADR 0008](adr/0008-ui-kit-preview-and-design-check.md)). For `storybook` everything project-specific is in the profile: `command` (an argument array that starts the showcase; `{mount}` is the kit's path), `port`, `env`, `tmpfs` (absolute container paths that may be written), `links` (links from the snapshot into the image, for example `{"node_modules": "/app/node_modules"}`); the image is `stories.image` |
| `stories` | The task's second repository, a component showcase (Storybook) that holds the kit's worktree: `repository`, `base_branch`, `worktree_root`, `mount` (required: the kit's path inside the showcase), `setup` (commands in a new worktree; `{repository}`, `{worktree}`, `{kit}`), `commands` (the executor's checks), `image` (the preview image), `themes` (themes in each of which browser acceptance opens the story and compares the component's states) and `theme_query` (required with `themes`: the theme's URL parameter with `{theme}`). Showcase files are written in the plan as `stories:src/stories/X.stories.ts`; the result is a task branch in both repositories |
| `steps` | Project steps Friday knows nothing about by itself; only the owner runs them (`friday step NAME [KEY]`, without a name the list and the state) ([ADR 0011](adr/0011-profile-steps.md)): `{"<name>": {"run": [...], "scope": "task" \| "profile", ...}}`. `run` is an argument array that runs on the host; a task step gets `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`, any step gets `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}`, `{secret.<name>}`. `description`, `env` (no secret values), `cwd`. `lock` is a shared resource for the step's duration: a path shares the repository's lock, a name is a named lock. `commit: {"paths": [...], "message": "{key}: ..."}` makes Friday commit these paths; the step goes stale when the branch changes outside them after its commit. `required` (a task step): while the step is not done or stale, `status`, the journal and the MR text remind of it with its command. `check` (a profile step) is a readiness command for `doctor`: 0 ready, 2 stale (!), anything else missing (✗). `secrets: {"<name>": "<path>"}` are files the command gets by path; Friday does not read them. Put a complex procedure in a script next to the profile |
| `design` | Design tools for UI tasks ([ADR 0007](adr/0007-design-tools.md)). `figma: {"url": "http://127.0.0.1:3845/mcp"}` is the local Dev Mode MCP server of Figma desktop; `tools` narrows the read tools (`get_metadata`, `get_design_context`, `get_screenshot`, `get_variable_defs`), write tools are not accepted. When the ticket has a `figma.com/design/…?node-id=…` link, `start` checks that the node is open in the active Figma tab, and the planner and the plan reviewer read the frame and write a measurable specification into the plan. The executor and the reviews get it in the prompt, without access to Figma. Friday saves screenshots of the frames in the task folder; browser acceptance compares the preview with them and measures styles (`computed_style`): a difference from a number of the specification blocks, a difference seen only by eye goes to the minor findings of the MR. If Figma does not answer or the node is missing, `start` stops and says what to open; `start --no-design` plans without the mockup. `impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` names files in `reference/` of the /impeccable skill that Friday puts into the prompt of UI milestones; `references` is required and maps the roles `develop`, `review`, `final-review` to lists of files (for example `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API or MCP), used to read the task description |
| `journal` | Where to write the task journal: `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]`; `page` is the path of the task page inside `dir` (`{key}.md` by default), for example into the task's folder in Obsidian. `journal_dir` and `journal_page` are a short form for a single markdown journal; a `journal` set in the profile (or inherited) wins over them. Friday does not touch a page it did not write (no `friday_generated` in the front matter): it prints that it skipped the page and writes the rest |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` and the key `github.repository` or `gitlab.base_url` + `gitlab.project` |

The repository name comes from the URL of `origin` (HTTPS, SSH or a local path), without `.git`; when there is no `origin`, from the name of the main repository on disk, also when working from a linked worktree. Characters outside `A–Z`, `a–z`, `0–9`, `_` and `-` become `-`, and leading and trailing `-` are removed. An empty name needs an explicit `branch_template`. The full task key is kept: `31` gives `octis/31`, `OCTIS-031` gives `octis/OCTIS-031`. A branch already recorded on the task card is kept when the task continues; a new setting applies to new tasks. A linked showcase uses the name of the task's main repository.

### Models and roles

```json
"models": {
  "fable": {"model": "claude-fable-5-2", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver`: what runs the model, `claude` or `codex`. Z.ai goes through Claude Code; the token is read from a file that only the owner can access.
- `tier`: `frontier`, `strong` or `efficient`; `strength` orders the models within a tier.
- `effort`: the depth of reasoning (`low` … `max`); one model can be described several times with different effort.
- `scarce`: an expensive model; it is used once per task if the rules allow the task to go without it.
- `price`: the price per million tokens by kind (`input`, `output`, `cache_read`, `cache_write`), used to estimate spending when the vendor does not report a price.

Roles: `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. The lists in `roles` are preferences: if the list has no suitable model, Friday takes another one from the catalog. Hard rules: only `frontier` models review code, the reviewer is not weaker than the author of the work, and the blind check is not done by the author of the code. Soft rules, in order: not the same model as the author; an expensive model once; a different vendor; the blind check not by the author of the plan. A soft rule can be broken only when there is no other way, and the violation is recorded in the task history.

An example role assignment is in [examples/models.json](../examples/models.json).

With `executor_tiers` a complex milestone uses the highest allowed tier, and a replacement on quota keeps the required tier within the limit. An old role assignment with a forbidden executor is replaced with an allowed one; a write by a forbidden model, or one that does not match the catalog, is rejected. Tiers and names come from the profile's catalog; Friday does not infer them from the model name.

Parallel milestones get their own worktrees and are integrated in plan order. Friday checks the overlap of the declared paths before the start and of the actual changes before integration. Work that could not be integrated is kept in its branch and worktree; `parallel_recovery_required` names them before the task continues. After reviewing the retained work, the controller finishes moving it or keeps the needed commits separately, then removes the reviewed lane worktrees and branches with ordinary Git commands. Friday does not delete such results automatically to retry.

A saved final review is bound to clean worktrees, the commits of both repositories, the plan, the decisions, the model settings and the exact text of the role's input. A change of the inputs during the check returns `stale_evidence`. When the second role fails, the finished first one is kept; the next `resume` runs only the missing checks for the same inputs. Raising `budget` and changing `max_parallel_milestones` keep a finished review: these settings control admission and scheduling, not the content of the check.

## Journal

The task card is the only source of truth. The journals show it and update themselves after significant events: the plan is ready and approved, a milestone is done or failed, an owner decision, the final review, the MR, a stop. To update them by hand, run `friday journal KEY`.

Time is the sum of the durations of runs, parallel ones included, not calendar time. For new runs without a duration from the provider the runner measures it itself. An interruption before the runner starts records zero execution time; a new unmeasured run keeps an unknown duration. Old linked events give an explicitly marked estimate that may include waiting for a slot. A lost run without a measurement has an unknown duration. An unknown price is also shown per role; it does not become zero cost.

- `markdown`: a page `KEY.md` and a shared overview page that lists all tasks. For Obsidian, set the vault folder: the pages have front matter (key, state, spending, the tag `friday`), and tasks are linked with wiki links. A task page contains the plan with its assumptions and unresolved findings, the milestones with the executor summary and the commits, the disputed findings, the decisions, the spending by role, and the timeline.
- `jsonl`: all events of the task, for analysis in spreadsheets or dashboards.

Templates are Markdown with the substitutions `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. Friday takes the template from the `template` field of the target, then `.friday/task.md` in the project repository, then the built-in one ([friday/templates](../friday/templates)). The text between `<!-- friday:notes -->` and `<!-- /friday:notes -->` is yours: it is kept at every update. Friday does not overwrite a page that it did not write.

## Machine settings

`FRIDAY_HOME/machine.json` sets the shared resources for all tasks:

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

By default, one gate and two browsers run at the same time, and vendors are not limited. Vendor quotas are tracked automatically: a run that hits a limit records when the quota returns, and until then the vendor is skipped when models are chosen.

### Task queue: `friday serve`

`friday serve` is a long-running process with one queue of approved tasks per machine ([ADR 0014](adr/0014-work-pool.md)). While it runs, `approve`, `resume` and an answer given with `decide` to an execution session do not start the task themselves but queue it; without it a task runs as a separate background process as before, and `resume` runs in the terminal.

- At most `max_workers` tasks run at the same time (`machine.json`, 2 by default); tasks started outside the queue count too.
- The queue follows the time the plan was approved; a task continued after `decide` goes first. `friday status` shows the queue and the server's state, `friday stop` removes a task from the queue.
- A task "running" whose process died (sleep, restart) is put back into the queue by the server as `resume`.
- When a task stops on a question or an owner step, fails or is done, a system notification arrives (`osascript` on macOS, `notify-send` on Linux).

For the server a task is one job: milestones are not split into jobs, and there is no per-task limit yet.

`friday service print|install|uninstall` installs the server as a user service: a launchd agent (`~/Library/LaunchAgents/local.friday.serve.plist`) or a systemd unit. A service starts with an empty environment, so its file names everything itself: `PATH` from the directories of `claude`, `codex`, `docker`, `git` (and `glab`, `gh`, `uvx`, `node`, `npx` when present), `FRIDAY_HOME`, `HOME`. `friday service check --profile P` runs `friday doctor` in exactly that environment, so you see before installing what the service will not find. Whether the service finds the Claude subscription sign-in only the first task under it shows. The service speaks the language saved with `friday config language`.

## Boundaries

- **Executor sandbox.** The executor's shell (Claude Code) runs in a sandbox: no network, no reading of `~/.ssh`, `~/.aws`, `~/.config` and similar, writing only to the worktree and a temporary folder, and no running outside the sandbox. Commands outside `executor_commands`, the git commands (`add`, `commit`, `status`, `diff`, `log`, `restore`) and `bin/friday-precedent` are rejected. Codex runs in its own sandbox with the same boundaries.
- **Git in Codex.** Friday puts the installed Git and a separate copy of the Git metadata into the task's runtime. Global Git configs and user shell profiles are not loaded; the service data of the source repository is not exposed to the agent. The executor saves stages with ordinary Git commands. After its process ends, Friday takes the commits through a verified bundle and returns them to the source branch if its HEAD and index did not change. On a state conflict the bundle stays in the run log as `git-recovery.bundle`; nothing is overwritten automatically. A reviewer gets the Git metadata read-only. `doctor` checks the real scenario of three commits in a linked worktree without calling a model, and that the bans on reading secrets and on writing for the reviewer hold.
- **Reviewers** only read. The blind check runs in an empty folder.
- **The gate** runs in a container without network access, on a snapshot of the commit mounted read-only.
- **The browser** receives only Friday's tools for one preview (including `hover` and `computed_style`, which reads styles with a fixed script, and `element_attributes`, which reads `aria-*`, `data-*` and a few markup attributes the same way, all without `evaluate_script`; for a local preview also the preview tab's console, `list_console_messages`); bypassing authorization and reading the headers of authorized requests are forbidden.
- **Figma** is read only by the planner and the plan reviewer, and only with the read tools of the local Figma desktop server. The /impeccable skill does not run inside the roles: Friday puts its texts into the prompt.
- **Publishing.** Friday pushes only the branch of its own task and opens only a draft MR/PR. It does not overwrite someone else's branch, merge, or deploy.
- **Not yet verified live:** browser acceptance and publishing to GitLab have been verified by tests with fakes. Git in the Codex environment is also checked by a real local lab without calling a model; the model's run of a role is checked separately on each task.
