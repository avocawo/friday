## インストール

1. Friday をクローンして `bin` を `PATH` に追加するか、`FRIDAY_BIN` を設定します。
2. エージェントが必要とする CLI をインストールします。Anthropic と Z.ai のモデルには Claude Code (`claude`)、OpenAI のモデルには Codex CLI (`codex`) を使います。どちらも通常どおりサインインしてください。
3. ゲートとブラウザ受け入れ確認のために、Docker をインストールします。ブラウザ受け入れ確認には、デバッグポート 9333 を開いた Chrome と、テスト環境にサインイン済みのセッションも必要です。
4. 状態は `~/.local/share/friday` に保存されます (`FRIDAY_HOME` で上書きできます)。プロファイルとシークレットはリポジトリには入りません。`profiles/` フォルダーは `.gitignore` に含まれています。

### Codex と Claude Code 用のプラグイン

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

このプラグインは、エージェントに `status` と `plan` の読み方を教えます。タスクの開始、承認、決定の記録は、あなたの手に残されます。

## タスクの流れ

1. **`start`** は、最新の `origin/<base_branch>` からブランチ `<repository>/KEY` (例: `octis/31`) とワークツリーを作成し、ロール割り当て (role assignment) を確定して、計画を書きます。計画の内容は、2〜5 ステージのマイルストーン、ファイル、規模の見積もり、コードとブラウザの基準、そしてエグゼキューター向けのプロジェクトルールの要約です。計画はまずモデルを使わずに検査されます (規模、ファイル、順序、基準)。その後、別のベンダーのモデルがレビューし、プランナーは指摘に一度だけ回答します。各指摘を受け入れるか、理由を添えて却下します。
   `"toolset": {"plan": "project"}` を指定すると、プロジェクト独自のプロセスが計画を書きます ([ADR 0015](../adr/0015-project-toolset.md))。Friday はワークツリーで、プロジェクトの設定、フック、スキル、エージェント、MCP を使う通常の Claude Code セッションを起動し、タスクの記述とともに `project.plan_command` を渡します。セッションはプロジェクトの計画ファイル (`project.plan_file`) を書き、同じ計画の要約を Friday のスキーマで Friday に返します。Friday は要約をモデルを使わずに検査し、別のベンダーによるレビューは行いません。プロジェクトのプロセスに独自のレビューがあるためです。セッションは `auto` の権限モードで動き、その結果はプロセスが終了する前の最後の回答です。プロジェクトのプロセスがバックグラウンドのレビューを待つことがあるためです。
2. **`plan`** は、計画、質問、却下された指摘、ほかのアクティブなタスクとのファイルの重なりを表示します。
3. **`approve`** は計画を承認し、バックグラウンドでパイプラインを開始します (`--no-run` は承認のみを行います。あとで `run` で実行してください)。
   `"toolset": {"execute": "project"}` を指定すると、Friday はマイルストーンの代わりにプロジェクト独自のプロセスを実行します ([ADR 0015](../adr/0015-project-toolset.md))。`develop` ロールのモデルで、`project.execute_command` を使う Claude Code セッションが 1 つ動きます。セッションはステージごとにコミットし、コミットの件名の先頭に、計画の要約にあるステージの id を付けます (`M1.1: …`)。何も公開しません。質問が出るとセッションは終了します。タスクは停止し、質問は `status` に表示され、`decide` で与えた回答は、バックグラウンドで同じセッションを続行します。`resume` は回答なしで同じことを行います。セッションは、自分を止めた原因を受け取ります。セッションが質問なしで終了し、環境がタスクを止めた場合 (ゲートのイメージ、テスト環境へのサインイン) は、`resume` はセッションを起こさず、その後のチェックだけを繰り返します。セッションの後、Friday は、ツリーがクリーンであること、すべてのステージに `limits` の範囲内のコミットがあること (そのコミットの `git diff --numstat`) を確認し、ゲートと、インターフェースを伴うマイルストーンのブラウザ受け入れ確認を実行します。その後は通常どおり、最終チェックと MR に進みます。このモードの最終レビューは、まずリポジトリのルートにある `AGENTS.md` (または `CLAUDE.md`) を読み、差分を計画のルールだけでなく、プロジェクトのドキュメントの各節とも照らして確認します。食い違いはすべて、オーナーへの質問になります。
4. **マイルストーン。** エグゼキューターは、マイルストーンごとに 1 つのセッションで作業し、ステージごとにコミットします。ゲートはそのコミットに対して実行されます。ゲートが失敗した場合、エグゼキューターが受け取るのは、ログのうち失敗したセクションだけです。セクションが上限より長い場合は、その見出しと、前後の文脈を含むエラー行が残され、TAP 形式の失敗したテスト (`not ok …` とその診断) が先頭に置かれます。マイルストーンレビューは、このマイルストーンの差分とゲートの結果を合わせて確認します。エグゼキューターは、ブロッキングの指摘を修正するか、異議を唱えます。異議を唱えた指摘 (争点となった指摘) はあなたに送られます。インターフェースを伴うマイルストーンは、隔離されたプレビューでブラウザ受け入れ確認を通ります。2 回連続で失敗すると、プロファイルが `executor_tiers` という上限を設定している場合は、Friday がその範囲内でエグゼキューターのティアを上げます。交代したエグゼキューターは新しいセッションを始めます。
5. **最終。** `final_review_roles` のロールが差分全体を確認します。既定では最終レビューとブラインドチェックが並行して実行され、プロファイルで最終レビューだけにすることもできます。ブロッキングの指摘には、修正の機会が 1 回与えられます。
6. **ドラフト MR** は、プロファイルに `delivery` が設定されていれば作成されます。設定されていなければ、その本文はタスクフォルダーの `merge-request.md` に保存されます。

パイプラインが止まるのは、ゲートが一度も通らなかったとき、エグゼキューターが何もしなかったとき、環境が利用できないとき、ルールで許可されたモデルを使い切ったとき、設定された予算を使い切ったときです。並列の変更の重なり、統合されずに残ったブランチ、最終レビューの入力のずれも、タスクを続行する前に対処が必要です。レビューでの意見の相違では止まりません。何にも検査されなかったマイルストーン (ゲートがない、エグゼキューターのチェックが実行されなかった、ブラウザ受け入れ確認がない) は、理由とともに「完了、未検証」として閉じられ、その内容はステータス、ジャーナル、MR に記されます ([ADR 0009](../adr/0009-unverified-is-not-done.md))。エグゼキューターのチェックを実行できず、ゲートもない場合、そのマイルストーンはブロックされます。

`decide KEY name "text" --reopen M2` は、あなたの決定を記録します。Friday の計画が承認待ちの間は、`decide` は計画も改訂します ([ADR 0016](../adr/0016-decision-revises-the-plan.md))。プランナーは `--reopen` で指定されたマイルストーンを新しいセッションで書き直し、それ以外はそのまま引き継がれます。`--reopen` がなければ、影響を受けるマイルストーンをプランナー自身が選びます。別のモデルがレビューするのは、変更されたマイルストーンだけです。`decide` は、計画のうち改訂されたマイルストーン、再実行のために再開されたマイルストーン、決定がコンテキストに加わっただけのマイルストーンを表示します。`friday plan KEY --diff` は、前の改訂との差分を表示します。改訂に失敗した場合、計画は元のまま承認待ちになり、決定は記録されています。同じ `decide` をもう一度実行してください。プロジェクトのプロセスの計画が承認待ちの間は、`decide` はあなたの回答でそのセッションを続行し、計画の新しい改訂を表示します。このような `decide` の 1 回 1 回が、セッションの別々の続行になるため、計画のすべての質問には 1 つのテキストで答えてください。同じように、`decide` は、プロジェクトのプロセスの、停止した実行セッションの質問にも答えます。再開されるのは、指定したマイルストーンと、それに依存するマイルストーンだけです。`--reopen` を付けない場合は、以降のマイルストーンがその決定を考慮に入れます。`resume` は、停止したタスクや失敗したタスクを続行します。`stop` は実行中のタスクを停止します。エージェントは子プロセスとともに終了します。

元のタスクの記述は全文が保存され、エグゼキューターとレビューに渡されます。そのため、計画で事実が短くまとめられても、正確なハッシュや URL は失われません。保存された記述がない古いカードには、`resume KEY --brief task.md` を使います。記述が復元されるのは、そのテキストが最初の計画時のフィンガープリントと一致する場合だけです。別のテキストの場合は、新しい計画が必要です。承認、ステージ、予算のカウンターはリセットされません。

失敗したマイルストーンが続行されるとき、すでに作られたコミットは元のレビュー境界を保ちます。空の追加コミットは必要ありません。エグゼキューターは、前回のゲートの失敗内容を受け取ります。Python のトレースバックは、診断出力の上限の範囲内で全文が含まれます。

## プロファイル

プロファイルは JSON ファイルです。`extends` キーで別のプロファイル (たとえば共有のモデルカタログ) を取り込めます。パスはプロファイルファイルからの相対パスです。

| キー | 用途 |
| --- | --- |
| `name`, `repository` | プロジェクト名と、そのリポジトリのパス |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | タスクのブランチをどこから作成し、どこに置くか。既定は `<repository>/{key}` で、明示的な `branch_template` には `{key}` を 1 つだけ含められます。レイアウトは `key` または `branch` です |
| `models`, `roles` | モデルカタログと、ロールの優先設定 (後述) |
| `engineering_policy` | プランナー、エグゼキューター、マイルストーンレビュー、最終レビュー、修正に適用するルール |
| `project_lessons` | レビューで繰り返し見つかる、プロジェクト固有の落とし穴。短いチェック項目のリストです。エグゼキューター、マイルストーンレビュー、最終レビュー、修正は、変更をこのリストと照らして確認します |
| `rules_docs` | プロジェクトのルールを記したドキュメント。Friday はこれらからプランナーと計画レビュアー向けの要約を 1 つ作ります (既定は `AGENTS.md`、`CLAUDE.md`、`docs/*.md`)。要約は内容のハッシュで保存され、ドキュメントが変わらない限りタスク間で再利用されます。プランナーはドキュメントを全文では読みません。パターンはリポジトリのルートから展開され、`**` はフォルダーの中まで下ります (`docs/**/*.md`、`src/**/README.md`)。フィンガープリントに入るのは、見つかったファイルだけです。エグゼキューター、マイルストーンレビュー、最終レビュー、修正は、計画が選んだルール、要約にあるドキュメントのマップ、先例を探すためのタスクのベースリビジョンを受け取ります。エグゼキューターは `bin/friday-precedent <base> <pattern> [<path>…]` で検索します (`git grep` のラッパーで、オプションは一切通しません) |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | プランナーと計画レビュアーのプロンプトに入れるリポジトリマップです。ツール呼び出しで構造を調べずに済むようにします。`none` (既定): マップなし。`builtin`: 追跡対象のファイルと行数。`graphify`: さらに、各ファイルのシンボルと、そのファイルを import しているファイルの数を、[graphify](https://github.com/Graphify-Labs/graphify) のグラフから取得します (`uv tool install 'graphifyy[mcp]==0.9.100'`。コードを解析するだけで、モデルは使いません。グラフはリポジトリではなく `FRIDAY_HOME/maps` に保存されます)。CS-2 での計測では、マップによって計画のコストは下がりませんでした (マップなし $6.19、`builtin` $7.08、`graphify` $7.97、いずれも 1 回ずつの実行)。そのため、既定ではオフです。マップはコミット単位でキャッシュされます。`repo_map_budget` の文字数 (60000) を超える場合は、まずシンボルを省き、次にフォルダーをまとめて短縮します。`repo_map_mcp: true` (`graphify` と併用する場合のみ) にすると、両方のロールがグラフに問い合わせられるようになります (`query_graph`、`get_node`、`get_neighbors`、`shortest_path`)。Codex での実機検証は未実施です。計画レビュアーは、計画に名前の挙がっているファイルの現在のテキスト (最大 40000 文字) を受け取ります |
| `approval` | `owner` (既定): 計画は `approve` を待ちます。`auto`: レビューのあとに計画が自動で承認され、すぐにパイプラインが始まります。計画が自動で承認されたことはジャーナルに記録されます |
| `limits` | `stage_files` と `stage_lines`: ステージの上限 (10 と 500)。任意の `task_milestones` と `task_stages` は、実行前に計画全体を制限します |
| `toolset`, `project` | あるフェーズを誰が実行するか。`{"plan": "project", "execute": "friday"}` は、プロジェクトのプロセスが計画を書き、Friday がそれを実行することを意味します (既定では両方のフェーズが `friday` です)。`project`: `{statement}` を含む `plan_command` はプロジェクトの計画コマンドで、たとえば `"/plan-stages {statement}"` です。`plan_file` はワークツリー内の計画ファイルです。`{stages}` を含む `execute_command` と `stage_argument` は実行フェーズ用です。`session_env` は、セッションが通常の環境変数に加えて受け取る環境変数の名前です (たとえば `git fetch` 用の `SSH_AUTH_SOCK`)。`disallowed_tools` はセッションに対して閉じられるツールです (たとえばオーナーのブラウザ。受け入れ確認は Friday の `browser` ロールが行います)。`timeouts` は `idle`、`tool`、`total` で、単位は秒です ([ADR 0015](../adr/0015-project-toolset.md)) |
| `worktree_setup` | 計画の前に、新しいワークツリーで Friday が実行するコマンド (依存関係のインストールなど)。`{repository}` と `{worktree}` を置換できる引数の配列で、繰り返し実行しても問題のないものにしてください。macOS で npm を使う例: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | エグゼキューターが自分で実行してよいコマンド。正確な形で書きます。`python` ではなく `"python3 -m pytest"` のようにします |
| `executor_deny_read` | エグゼキューターのシェルが読めない追加のパス |
| `executor_tiers` | コードを書くすべてのエージェントに許可するティア。たとえば `["strong", "efficient"]` です。このフィールドがなければ、すべてのティアが許可されます。複雑さ、エスカレーション、クォータ、最終修正は、この上限を守ります |
| `milestone_rounds` | 1 つのマイルストーンに与えられるエグゼキューターのラウンド数 (4) |
| `max_parallel_milestones` | `parallel=true` を持つ、独立していて準備の整ったマイルストーンのうち、同時に実行する数 (2)。`1` なら 1 つずつ順に実行します |
| `budget` | 任意の正の値 `max_model_runs` と `max_milestone_runs`。タスクごと、マイルストーンごとに受け付けるすべてのロールの実行数の上限です。予約はアトミックです。失敗した試行や未完了の試行も数えられ、`resume` や再開ではカウンターはリセットされません。使い切るとタスクは `budget_exhausted` で停止します。予算を変更するには、プロファイルで明示的に変更します。制限されるのは実行数であり、コストではありません |
| `final_review_roles` | 既定は `["final-review", "blind-code"]` です。`["final-review"]` にすると、最終チェックは 1 つだけになります。完了した結果は個別に保存され、ソース、計画、決定、設定、そのロールの入力が変わっていない場合にのみ再利用されます |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | Docker で実行するチェックコマンド。`git-diff` はタスクのベースと比較します。ゲートのイメージをどうビルドするかは、プロファイルがステップ (`steps`) として記述し、`gate_image_step` がそのステップを指定します。イメージ内の `gate_lockfile` がタスクのものと異なる場合、タスクは停止します。`status` には、そのステップのコマンドとともに "Owner step needed" と表示されます。ステップの後、`resume` はチェックを繰り返し、プロジェクトのプロセスの実行セッションは起こしません |
| `environment_errors` | コードの失敗ではなく、環境の失敗を意味するログ行のパターン |
| `browser`, `preview`, `behavior_test_policy` | テスト環境、プレビュー、ブラウザ受け入れ確認のルール。プレビューのバックエンドには `storybook` があります (`stories` のショーケースで、`mount` にキットのスナップショットを置きます。[ADR 0008](../adr/0008-ui-kit-preview-and-design-check.md))。`storybook` では、プロジェクト固有のものはすべてプロファイルに書きます。`command` (ショーケースを起動する引数の配列。`{mount}` はキットのパス)、`port`、`env`、`tmpfs` (書き込みを許可するコンテナー内の絶対パス)、`links` (スナップショットからイメージへのリンク。たとえば `{"node_modules": "/app/node_modules"}`) です。イメージは `stories.image` です |
| `stories` | タスクの 2 つ目のリポジトリで、キットのワークツリーを保持するコンポーネントのショーケース (Storybook)。`repository`、`base_branch`、`worktree_root`、`mount` (必須: ショーケース内でのキットのパス)、`setup` (新しいワークツリーで実行するコマンド。`{repository}`、`{worktree}`、`{kit}`)、`commands` (エグゼキューターのチェック)、`image` (プレビューのイメージ)、`themes` (ブラウザ受け入れ確認が、それぞれのテーマでストーリーを開いてコンポーネントの状態を比較するテーマ)、`theme_query` (`themes` とともに必須: `{theme}` を含む、テーマの URL パラメーター)。ショーケースのファイルは、計画では `stories:src/stories/X.stories.ts` のように書きます。結果は、両方のリポジトリのタスクブランチです |
| `steps` | Friday 自身は知らない、プロジェクトのステップ。実行できるのはオーナーだけです (`friday step NAME [KEY]`。名前を省略すると、一覧と状態を表示します) ([ADR 0011](../adr/0011-profile-steps.md))。`{"<name>": {"run": [...], "scope": "task" \| "profile", ...}}`。`run` はホストで実行される引数の配列です。タスクステップには `{key}`、`{worktree}`、`{branch}`、`{base}`、`{head}`、`{showcase}` が、どのステップにも `{profile_dir}`、`{repository}`、`{base_branch}`、`{stories_repository}`、`{secret.<name>}` が渡されます。`description`、`env` (シークレットの値は含めない)、`cwd`。`lock` はステップの実行中に共有されるリソースです。パスはリポジトリのロックを共有し、名前は名前付きロックです。`commit: {"paths": [...], "message": "{key}: ..."}` は、Friday にこれらのパスをコミットさせます。コミットの後、ブランチがこれらのパス以外で変わると、そのステップは古くなります。`required` (タスクステップ): そのステップが未完了または古い間、`status`、ジャーナル、MR の本文が、そのコマンドとともに知らせます。`check` (プロファイルステップ) は `doctor` 用の準備確認コマンドです。0 は準備完了、2 は古い (!)、それ以外は不足 (✗) を意味します。`secrets: {"<name>": "<path>"}` は、コマンドがパスで受け取るファイルです。Friday はそれを読みません。複雑な手順は、プロファイルの隣のスクリプトに置いてください |
| `design` | UI タスク用のデザインツール ([ADR 0007](../adr/0007-design-tools.md))。`figma: {"url": "http://127.0.0.1:3845/mcp"}` は、Figma デスクトップのローカルの Dev Mode MCP サーバーです。`tools` は読み取りツール (`get_metadata`、`get_design_context`、`get_screenshot`、`get_variable_defs`) を絞り込みます。書き込みツールは受け付けられません。チケットに `figma.com/design/…?node-id=…` のリンクがあると、`start` は、そのノードがアクティブな Figma のタブで開かれているかを確認し、プランナーと計画レビュアーがフレームを読み、計測可能な仕様を計画に書き込みます。エグゼキューターとレビューは、その仕様をプロンプトで受け取り、Figma にはアクセスしません。Friday はフレームのスクリーンショットをタスクフォルダーに保存します。ブラウザ受け入れ確認は、プレビューをそれらと比較し、スタイル (`computed_style`) を計測します。仕様の数値との差はブロックし、目で見てわかるだけの差は MR の軽微な指摘に回ります。Figma が応答しない場合やノードが見つからない場合、`start` は停止し、何を開くべきかを伝えます。`start --no-design` は、モックアップなしで計画します。`impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` は、/impeccable スキルの `reference/` にあるファイルを指定し、Friday はそれを UI マイルストーンのプロンプトに入れます。`references` は必須で、ロール `develop`、`review`、`final-review` をファイルのリストに対応づけます (たとえば `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API または MCP)。タスクの説明を読むために使います |
| `journal` | タスクのジャーナルの書き込み先: `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]`。`page` は `dir` の中でのタスクページのパス (既定は `{key}.md`) で、たとえば Obsidian のタスクのフォルダーを指します。`journal_dir` と `journal_page` は、Markdown ジャーナルを 1 つだけ使う場合の短縮形です。プロファイルに設定された (または継承された) `journal` が、それらより優先されます。Friday は、自分が書いていないページ (フロントマターに `friday_generated` がないページ) には触れません。そのページを飛ばしたことを表示し、残りを書き込みます |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` と、キー `github.repository`、または `gitlab.base_url` + `gitlab.project` |

リポジトリ名は `origin` の URL (HTTPS、SSH、またはローカルパス) から取られ、`.git` は含まれません。`origin` がない場合は、ディスク上のメインリポジトリの名前から取られます。これは、リンクされたワークツリーから作業している場合も同じです。`A–Z`、`a–z`、`0–9`、`_`、`-` 以外の文字は `-` になり、先頭と末尾の `-` は取り除かれます。名前が空になる場合は、明示的な `branch_template` が必要です。タスクのキーは完全な形で保たれます。`31` は `octis/31` に、`OCTIS-031` は `octis/OCTIS-031` になります。タスクのカードにすでに記録されているブランチは、タスクの続行時にそのまま使われます。新しい設定が適用されるのは、新しいタスクだけです。リンクされたショーケースは、タスクのメインリポジトリの名前を使います。

### モデルとロール

```json
"models": {
  "fable": {"model": "claude-fable-5-2", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver`: モデルを動かすもの。`claude` または `codex` です。Z.ai は Claude Code を通して動かします。トークンは、オーナーだけがアクセスできるファイルから読み込まれます。
- `tier`: `frontier`、`strong`、`efficient` のいずれかです。`strength` は、同じティア内でモデルの順序を決めます。
- `effort`: 推論の深さ (`low` … `max`)。1 つのモデルを、異なる effort で複数回記述できます。
- `scarce`: 高価なモデルを表します。ルール上、そのモデルなしでタスクを進められる場合は、1 つのタスクで 1 回だけ使われます。
- `price`: 種類別 (`input`、`output`、`cache_read`、`cache_write`) の 100 万トークンあたりの価格です。ベンダーが価格を報告しない場合に、コストの見積もりに使われます。

ロールは `plan`、`plan-review`、`develop`、`review`、`final-review`、`blind-code`、`browser` です。`roles` のリストは優先設定です。リストに適したモデルがなければ、Friday はカタログから別のモデルを選びます。厳格なルールは次のとおりです。コードをレビューするのは `frontier` のモデルだけ、レビュアーはその作業の作成者より弱くない、ブラインドチェックはコードの作成者が行わない。緩やかなルールは、優先順に次のとおりです。作成者と同じモデルでない、高価なモデルは 1 回だけ、別のベンダー、ブラインドチェックは計画の作成者が行わない。緩やかなルールを破れるのは、ほかに方法がない場合だけで、違反はタスクの履歴に記録されます。

ロール割り当ての例は [examples/models.json](../../examples/models.json) にあります。

`executor_tiers` がある場合、複雑なマイルストーンは許可された最も高いティアを使い、クォータによる交代でも、上限の範囲内で必要なティアが保たれます。許可されていないエグゼキューターを含む古いロール割り当ては、許可されたものに置き換えられます。許可されていないモデルによる書き込み、またはカタログと一致しないモデルによる書き込みは拒否されます。ティアと名前はプロファイルのカタログから取られ、Friday がモデル名から推測することはありません。

並列のマイルストーンにはそれぞれ専用のワークツリーが与えられ、計画の順序で統合されます。Friday は、開始前に宣言されたパスの重なりを、統合前に実際の変更の重なりを確認します。統合できなかった作業は、そのブランチとワークツリーに残されます。タスクを続行する前に、`parallel_recovery_required` がそれらを示します。残された作業を確認したら、コントローラーが移し替えを済ませるか、必要なコミットを別に保管し、そのうえで、確認済みの並列ワークツリーとブランチを通常の Git コマンドで削除します。Friday は、再試行のためにこうした結果を自動で削除することはありません。

保存された最終レビューは、クリーンなワークツリー、両方のリポジトリのコミット、計画、決定、モデルの設定、そしてそのロールの入力の正確なテキストに結び付けられます。チェック中に入力が変わると、`stale_evidence` が返されます。2 つ目のロールが失敗しても、完了した 1 つ目は保持されます。次の `resume` は、同じ入力に対して不足しているチェックだけを実行します。`budget` を引き上げたり `max_parallel_milestones` を変更したりしても、完了したレビューは保持されます。これらの設定が制御するのは受け付けとスケジューリングであり、チェックの内容ではありません。

## ジャーナル

タスクのカードが唯一の信頼できる情報源です。ジャーナルはカードの内容を表示するもので、重要なイベントの後に自動で更新されます。対象は、計画の完成と承認、マイルストーンの完了と失敗、オーナーの決定、最終レビュー、MR、停止です。手動で更新するには、`friday journal KEY` を実行します。

時間は、並列のものを含む実行時間の合計であり、カレンダー上の時間ではありません。プロバイダーが実行時間を返さない新しい実行については、ランナーが自分で計測します。ランナーが起動する前の中断は、実行時間ゼロとして記録されます。計測されなかった新しい実行は、実行時間が不明のままです。古い、関連付けられたイベントからは、明示的にそうとわかる推定値が得られ、枠の空きを待つ時間が含まれることがあります。計測のない、失われた実行の実行時間は不明です。不明な価格もロールごとに表示されます。ゼロコストになることはありません。

- `markdown`: ページ `KEY.md` と、すべてのタスクを一覧にした共通の概要ページ。Obsidian では、Vault のフォルダーを指定します。ページにはフロントマター (キー、状態、コスト、タグ `friday`) があり、タスク同士は wiki リンクで結ばれます。タスクのページには、前提条件と未解決の指摘を含む計画、エグゼキューターの要約とコミットを含むマイルストーン、争点となった指摘、決定、ロール別のコスト、タイムラインが含まれます。
- `jsonl`: タスクのすべてのイベント。スプレッドシートやダッシュボードでの分析に使えます。

テンプレートは Markdown で、置換には `{{key}}`、`{{state}}`、`{{status}}`、`{{plan}}`、`{{milestones}}`、`{{disputes}}`、`{{decisions}}`、`{{costs}}`、`{{timeline}}`、`{{notes}}` を使えます。Friday は、対象の `template` フィールド、プロジェクトリポジトリの `.friday/task.md`、組み込みのテンプレート ([friday/templates](../../friday/templates)) の順にテンプレートを探します。`<!-- friday:notes -->` と `<!-- /friday:notes -->` の間のテキストはあなたのものです。更新のたびに保持されます。Friday は、自分が書いていないページを上書きしません。

## マシンの設定

`FRIDAY_HOME/machine.json` は、すべてのタスクが共有するリソースを設定します。

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

既定では、ゲートは 1 つ、ブラウザは 2 つが同時に動き、ベンダーごとの制限はありません。ベンダーのクォータは自動で追跡されます。上限に達した実行はクォータが戻る時刻を記録し、それまでの間、モデルの選択ではそのベンダーが飛ばされます。

### タスクキュー: `friday serve`

`friday serve` は、マシンごとに、承認済みタスクのキューを 1 つ持つ、長時間動くプロセスです ([ADR 0014](../adr/0014-work-pool.md))。これが動いている間、`approve`、`resume`、そして実行セッションへの `decide` による回答は、タスクを自分で開始せずキューに入れます。動いていなければ、これまでどおりタスクは別のバックグラウンドプロセスとして動き、`resume` はターミナルで実行されます。

- 同時に動くタスクは最大 `max_workers` 個です (`machine.json`、既定は 2)。キューの外で開始されたタスクも数えられます。
- キューは計画が承認された時刻の順に並びます。`decide` の後に続行されるタスクが先頭になります。`friday status` はキューとサーバーの状態を表示し、`friday stop` はタスクをキューから外します。
- プロセスが死んだ (スリープ、再起動) 「実行中」のタスクは、サーバーが `resume` としてキューに戻します。
- タスクが質問やオーナーのステップで停止したとき、失敗したとき、完了したときは、システム通知が届きます (macOS では `osascript`、Linux では `notify-send`)。

サーバーにとってタスクは 1 つのジョブです。マイルストーンは別々のジョブには分割されず、タスクごとの上限もまだありません。

`friday service print|install|uninstall` は、サーバーをユーザーサービスとしてインストールします。launchd エージェント (`~/Library/LaunchAgents/local.friday.serve.plist`) か、systemd のユニットです。サービスは空の環境で起動するため、そのファイルがすべてを自分で指定します。`PATH` は `claude`、`codex`、`docker`、`git` (および、あれば `glab`、`gh`、`uvx`、`node`、`npx`) のあるディレクトリから作られ、そのほかに `FRIDAY_HOME` と `HOME` があります。`friday service check --profile P` は、まさにその環境で `friday doctor` を実行するので、インストールの前に、サービスが何を見つけられないかがわかります。サービスが Claude のサブスクリプションのサインインを見つけられるかどうかは、その下で動く最初のタスクで初めてわかります。サービスは、`friday config language` で保存された言語を使います。

## 境界

- **エグゼキューターのサンドボックス。** エグゼキューターのシェル (Claude Code) はサンドボックス内で動きます。ネットワークなし、`~/.ssh`、`~/.aws`、`~/.config` などの読み取りなし、書き込みはワークツリーと一時フォルダーのみ、サンドボックス外での実行なし、です。`executor_commands` に含まれないコマンド、git コマンド (`add`、`commit`、`status`、`diff`、`log`、`restore`)、`bin/friday-precedent` のいずれでもないコマンドは拒否されます。Codex は、同じ境界を持つ独自のサンドボックスで動きます。
- **Codex での Git。** Friday は、インストール済みの Git と、Git メタデータの別個のコピーを、タスクのランタイムに置きます。グローバルな Git の設定とユーザーのシェルプロファイルは読み込まれません。元のリポジトリのサービスデータは、エージェントには公開されません。エグゼキューターは、通常の Git コマンドでステージを保存します。そのプロセスが終了した後、Friday は検証済みのバンドルを通してコミットを取り出し、元のブランチの HEAD とインデックスが変わっていなければ、そこへ戻します。状態の競合が起きた場合、バンドルは `git-recovery.bundle` として実行ログに残され、自動で上書きされるものはありません。レビュアーは Git メタデータを読み取り専用で受け取ります。`doctor` は、モデルを呼び出さずに、リンクされたワークツリーでの 3 つのコミットという実際のシナリオと、シークレットの読み取りの禁止、およびレビュアーへの書き込みの禁止が守られていることを確認します。
- **レビュアー** は読み取り専用です。ブラインドチェックは、空のフォルダーで実行されます。
- **ゲート** は、ネットワークのないコンテナーで、読み取り専用でマウントしたコミットのスナップショットに対して実行されます。
- **ブラウザ** が受け取るのは、1 つのプレビュー用の Friday のツールだけです (`hover` と、固定のスクリプトでスタイルを読み取る `computed_style`、同じ方法で `aria-*`・`data-*` といくつかのマークアップ属性を読み取る `element_attributes` を含み、`evaluate_script` は含みません。ローカルのプレビューではプレビューのタブのコンソール `list_console_messages` も含みます)。認可の回避や、認可済みリクエストのヘッダーの読み取りは禁止されています。
- **Figma** を読むのは、プランナーと計画レビュアーだけで、ローカルの Figma デスクトップサーバーの読み取りツールだけを使います。/impeccable スキルはロールの内部では動きません。Friday がそのテキストをプロンプトに入れます。
- **公開。** Friday がプッシュするのは自分のタスクのブランチだけで、作成するのはドラフトの MR/PR だけです。他人のブランチの上書き、マージ、デプロイは行いません。
- **実機では未検証:** ブラウザ受け入れ確認と GitLab への公開は、偽のエージェントを使ったテストで検証されています。Codex 環境での Git も、モデルを呼び出さない実際のローカル検証環境で確認されています。モデルによるロールの実行は、タスクごとに別途確認されます。
