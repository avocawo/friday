## Instalação

1. Clone o Friday e adicione `bin` ao `PATH`, ou defina `FRIDAY_BIN`.
2. Instale as CLIs de que os agentes precisam: Claude Code (`claude`) para os modelos da Anthropic e da Z.ai, Codex CLI (`codex`) para os modelos da OpenAI. Faça login nelas como de costume.
3. Para o gate e a aceitação no navegador, instale o Docker. A aceitação no navegador também precisa do Chrome com a porta de depuração 9333 e de uma sessão autenticada no ambiente de teste.
4. O estado fica em `~/.local/share/friday` (altere com `FRIDAY_HOME`). Perfis e segredos não entram no repositório: a pasta `profiles/` está no `.gitignore`.

### Plugin para Codex e Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

O plugin ensina o agente a ler `status` e `plan`. Iniciar uma tarefa, aprová-la e tomar decisões ficam por sua conta.

## Como uma tarefa é executada

1. **`start`** cria a branch `<repository>/KEY` (por exemplo `octis/31`) a partir de um `origin/<base_branch>` atualizado e um worktree, fixa a atribuição de papéis e escreve o plano: marcos de 2 a 5 etapas, arquivos, uma estimativa de tamanho, critérios de código e de navegador, e um resumo das regras do projeto para o executor. O plano é verificado primeiro sem modelo (tamanho, arquivos, ordem, critérios). Em seguida, um modelo de outro fornecedor o revisa, e o planejador responde aos achados uma única vez: aceita cada um ou o rejeita com uma justificativa.
   Com `"toolset": {"plan": "project"}`, o processo próprio do projeto escreve o plano ([ADR 0015](../adr/0015-project-toolset.md)): o Friday inicia uma sessão comum do Claude Code no worktree com as configurações, os hooks, os skills, os agentes e o MCP do projeto, e passa a ela `project.plan_command` com o enunciado da tarefa. A sessão escreve o arquivo de plano do projeto (`project.plan_file`) e devolve ao Friday um resumo desse mesmo plano no esquema dele; o Friday verifica o resumo sem modelo e não executa a revisão por outro fornecedor, porque o processo do projeto tem a sua. A sessão roda no modo de permissão `auto`; o resultado dela é a última resposta antes de o processo terminar, porque o processo do projeto pode esperar uma revisão em segundo plano.
2. **`plan`** mostra o plano, as perguntas, os achados rejeitados e as sobreposições de arquivos com outras tarefas ativas.
3. **`approve`** aprova o plano e inicia o pipeline em segundo plano (`--no-run` apenas aprova; execute depois com `run`).
   Com `"toolset": {"execute": "project"}`, o Friday executa o processo próprio do projeto no lugar dos marcos ([ADR 0015](../adr/0015-project-toolset.md)): uma sessão do Claude Code com `project.execute_command` no modelo do papel `develop`. A sessão faz commit de cada etapa com o id dela, tirado do resumo do plano, no início do assunto (`M1.1: …`) e não publica nada. Uma pergunta encerra a sessão: a tarefa para, a pergunta aparece em `status`, e a resposta dada com `decide` continua a mesma sessão em segundo plano; `resume` faz o mesmo sem resposta. A sessão recebe o que a interrompeu. Se a sessão terminou sem perguntas e o ambiente parou a tarefa (a imagem do gate, o login no ambiente de teste), `resume` não acorda a sessão e apenas repete as verificações posteriores. Depois da sessão, o Friday verifica que a árvore está limpa, que cada etapa tem um commit dentro de `limits` (`git diff --numstat` dos commits dela), roda o gate e a aceitação no navegador dos marcos com interface, e depois a verificação final e o MR como de costume; a revisão final nesse modo primeiro lê `AGENTS.md` (ou `CLAUDE.md`) na raiz do repositório e confere o diff com as seções dos documentos do projeto, não apenas com as regras do plano. Qualquer divergência vira uma pergunta para o dono.
4. **Marco.** O executor trabalha em uma sessão por marco e faz commit de cada etapa. O gate roda sobre o commit. Se falhar, o executor recebe apenas as seções do log que falharam; quando uma seção passa do limite, ficam o cabeçalho dela e as linhas de erro com contexto, e antes de tudo os testes que falharam em formato TAP (`not ok …` com seus diagnósticos). A revisão do marco analisa o diff desse marco junto com o resultado do gate. O executor corrige ou contesta os achados bloqueantes; os achados contestados são enviados a você. Marcos com interface passam pela aceitação no navegador em um preview isolado. Após duas falhas seguidas, o Friday sobe o nível do executor dentro de `executor_tiers` quando o perfil define esse limite; a substituição inicia uma nova sessão.
5. **Final.** Os papéis em `final_review_roles` verificam o diff inteiro: por padrão, a revisão final e a verificação cega rodam em paralelo; um perfil pode manter apenas a revisão final. Os achados bloqueantes têm uma rodada de correções.
6. **O MR em rascunho** é aberto se o perfil define `delivery`. Caso contrário, o texto dele é salvo em `merge-request.md` na pasta da tarefa.

O pipeline para quando o gate nunca passou, o executor não fez nada, o ambiente está indisponível, os modelos permitidos pelas regras se esgotaram ou o orçamento configurado acabou. Mudanças paralelas que se sobrepõem, branches retidas que não foram integradas e entradas instáveis da revisão final também exigem atenção antes de a tarefa continuar. Divergências na revisão não o interrompem. Um marco que nada verificou (sem gate, sem que as verificações do executor rodassem, sem aceitação no navegador) fecha como "feito, não verificado" com os motivos, no status, no diário e no MR ([ADR 0009](../adr/0009-unverified-is-not-done.md)); se as verificações do executor não puderam rodar e não há gate, o marco fica bloqueado.

`decide KEY name "text" --reopen M2` registra a sua decisão. Enquanto o plano do Friday aguarda aprovação, `decide` também o revisa ([ADR 0016](../adr/0016-decision-revises-the-plan.md)): o planejador reescreve em uma nova sessão os marcos indicados em `--reopen` e os demais são mantidos como estavam; sem `--reopen`, ele mesmo escolhe os marcos afetados. Outro modelo revisa apenas os marcos alterados. `decide` imprime quais marcos foram revisados no plano, quais foram reabertos para rodar de novo e quais apenas receberam a decisão no contexto; `friday plan KEY --diff` mostra a diferença em relação à revisão anterior. Se a revisão falha, o plano fica como estava e aguarda aprovação, e a decisão fica registrada: repita o mesmo `decide`. Enquanto o plano do processo do projeto aguarda aprovação, `decide` continua a sessão dele com a sua resposta e mostra a nova revisão do plano. Cada `decide` desse tipo é uma continuação separada da sessão, então responda a todas as perguntas do plano em um único texto. Do mesmo modo, `decide` responde a uma pergunta de uma sessão de execução interrompida do processo do projeto. Apenas os marcos indicados e os que dependem deles são reabertos. Sem `--reopen`, os marcos seguintes levam a decisão em conta. `resume` continua uma tarefa interrompida ou com falha. `stop` interrompe uma tarefa em execução: os agentes terminam junto com seus processos filhos.

O enunciado original da tarefa é mantido por inteiro e passado aos executores e às revisões, de modo que hashes e URLs exatos sobrevivem ao encurtamento dos fatos no plano. Para um card antigo sem enunciado salvo, use `resume KEY --brief task.md`. O enunciado é restaurado apenas quando o texto coincide com a impressão digital do planejamento original; outro texto exige um novo plano. A aprovação, as etapas e os contadores do orçamento não são zerados.

Quando um marco que falhou continua, os commits já feitos mantêm o limite de revisão original; não é preciso nenhum commit vazio adicional. O executor recebe a falha anterior do gate, com o corpo completo de um traceback do Python dentro do limite da saída de diagnóstico.

## Perfil

Um perfil é um arquivo JSON. A chave `extends` inclui outro perfil (por exemplo, um catálogo de modelos compartilhado); os caminhos são relativos ao arquivo do perfil.

| Chave | Finalidade |
| --- | --- |
| `name`, `repository` | O nome do projeto e o caminho do repositório dele |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | De onde criar a branch da tarefa e onde colocá-la; por padrão `<repository>/{key}`, um `branch_template` explícito aceita um único `{key}`, o layout é `key` ou `branch` |
| `models`, `roles` | O catálogo de modelos e as preferências de papéis (veja abaixo) |
| `engineering_policy` | Regras para o planejador, o executor, as revisões dos marcos, a revisão final e as correções |
| `project_lessons` | Armadilhas do projeto que as revisões continuam encontrando: uma lista de verificações curtas. O executor, as revisões dos marcos, a revisão final e as correções conferem a mudança com ela |
| `rules_docs` | Documentos com as regras do projeto. O Friday gera com eles um resumo único para o planejador e o revisor do plano (por padrão `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). O resumo é guardado pelo hash do conteúdo e reutilizado pelas tarefas enquanto os documentos não mudam; o planejador não lê os documentos por inteiro. Os padrões se expandem a partir da raiz do repositório, `**` desce pelas pastas (`docs/**/*.md`, `src/**/README.md`); só os arquivos encontrados entram na impressão digital. O executor, as revisões dos marcos, a revisão final e as correções recebem as regras que o plano escolheu, o mapa de documentos do resumo e a revisão base da tarefa para buscar precedentes; o executor busca com `bin/friday-precedent <base> <pattern> [<path>…]` (um wrapper sobre `git grep` que não deixa passar opções) |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | Um mapa do repositório no prompt do planejador e do revisor do plano, para que não explorem a estrutura com chamadas de ferramentas. `none` (padrão): sem mapa. `builtin`: os arquivos versionados com o número de linhas. `graphify`: também os símbolos de cada arquivo e quantos arquivos o importam, tirados de um grafo do [graphify](https://github.com/Graphify-Labs/graphify) (`uv tool install 'graphifyy[mcp]==0.9.100'`; ele apenas analisa o código, nenhum modelo é usado; o grafo fica em `FRIDAY_HOME/maps`, não no repositório). Em uma medição no CS-2, o mapa não tornou o planejamento mais barato (sem mapa US$ 6,19, `builtin` US$ 7,08, `graphify` US$ 7,97, uma execução cada), por isso vem desativado por padrão. O mapa é mantido em cache por commit. Se for maior que `repo_map_budget` caracteres (60000), ele é primeiro reduzido removendo os símbolos e depois recolhendo as pastas. `repo_map_mcp: true` (somente com `graphify`) dá aos dois papéis consultas ao grafo: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`; não verificado ao vivo no Codex. O revisor do plano recebe o texto atual dos arquivos citados no plano (até 40000 caracteres) |
| `approval` | `owner` (padrão): o plano espera por `approve`. `auto`: o plano é aprovado automaticamente após a revisão e o pipeline começa de imediato; o diário registra que o plano foi aprovado automaticamente |
| `limits` | `stage_files` e `stage_lines`: os limites de uma etapa (10 e 500); os opcionais `task_milestones` e `task_stages` limitam todo o plano antes de ele rodar |
| `toolset`, `project` | Quem executa uma fase: `{"plan": "project", "execute": "friday"}` significa que o processo do projeto escreve o plano e o Friday o executa (as duas fases são `friday` por padrão). `project`: `plan_command` com `{statement}` é o comando de planejamento do projeto, por exemplo `"/plan-stages {statement}"`; `plan_file` é o arquivo do plano no worktree; `execute_command` e `stage_argument` com `{stages}` servem à fase de execução; `session_env` nomeia as variáveis de ambiente que a sessão recebe além das usuais (por exemplo `SSH_AUTH_SOCK` para `git fetch`); `disallowed_tools` são as ferramentas fechadas à sessão (por exemplo o navegador do dono: a aceitação é feita pelo papel `browser` do Friday); `timeouts` são `idle`, `tool`, `total` em segundos ([ADR 0015](../adr/0015-project-toolset.md)) |
| `worktree_setup` | Comandos que o Friday executa em um novo worktree antes de planejar (dependências e similares): arrays de argumentos com as substituições `{repository}` e `{worktree}`; precisam ser repetíveis. Exemplo para npm no macOS: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Comandos que o executor pode rodar sozinho, na forma exata: `"python3 -m pytest"`, não `python` |
| `executor_deny_read` | Caminhos adicionais que o shell do executor não pode ler |
| `executor_tiers` | Os níveis permitidos para todos os agentes que escrevem, por exemplo `["strong", "efficient"]`. Sem o campo, todos os níveis são permitidos. Complexidade, escalonamento, cota e correções finais respeitam o limite |
| `milestone_rounds` | Quantas rodadas do executor um marco recebe (4) |
| `max_parallel_milestones` | Marcos independentes e prontos com `parallel=true` que rodam ao mesmo tempo (2); `1` os executa um após o outro |
| `budget` | `max_model_runs` e `max_milestone_runs` opcionais e positivos: o limite de execuções admitidas de todos os papéis por tarefa e por marco. A reserva é atômica; tentativas que falharam e as inacabadas contam, e `resume` e a reabertura não zeram os contadores. Quando se esgota, a tarefa para com `budget_exhausted`; o orçamento é alterado explicitamente no perfil. Limita execuções, não custo |
| `final_review_roles` | `["final-review", "blind-code"]` por padrão; `["final-review"]` mantém uma única verificação final. Os resultados concluídos são salvos de forma independente e só são reutilizados quando as fontes, o plano, as decisões, as configurações e as entradas do papel não mudaram |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | O comando de verificação no Docker; `git-diff` compara com a base da tarefa. O perfil descreve como montar a imagem do gate como um passo (`steps`), e `gate_image_step` nomeia esse passo. Se o `gate_lockfile` da imagem difere do da tarefa, a tarefa para: `status` mostra "Owner step needed" com o comando do passo; depois do passo, `resume` repete as verificações e não acorda uma sessão de execução do processo do projeto |
| `environment_errors` | Padrões de linhas de log que indicam falha de ambiente, não falha de código |
| `browser`, `preview`, `behavior_test_policy` | O ambiente de teste, o preview e as regras da aceitação no navegador. Os backends de preview incluem `storybook` (a vitrine de `stories` com um snapshot do kit em `mount`, [ADR 0008](../adr/0008-ui-kit-preview-and-design-check.md)). Para `storybook`, tudo o que é específico do projeto está no perfil: `command` (um array de argumentos que inicia a vitrine; `{mount}` é o caminho do kit), `port`, `env`, `tmpfs` (caminhos absolutos do contêiner em que se pode escrever), `links` (links do snapshot para a imagem, por exemplo `{"node_modules": "/app/node_modules"}`); a imagem é `stories.image` |
| `stories` | O segundo repositório da tarefa, uma vitrine de componentes (Storybook) que guarda o worktree do kit: `repository`, `base_branch`, `worktree_root`, `mount` (obrigatório: o caminho do kit dentro da vitrine), `setup` (comandos em um novo worktree; `{repository}`, `{worktree}`, `{kit}`), `commands` (as verificações do executor), `image` (a imagem do preview), `themes` (temas em cada um dos quais a aceitação no navegador abre a story e compara os estados do componente) e `theme_query` (obrigatório com `themes`: o parâmetro de URL do tema com `{theme}`). Os arquivos da vitrine são escritos no plano como `stories:src/stories/X.stories.ts`; o resultado é uma branch da tarefa nos dois repositórios |
| `steps` | Passos do projeto que o Friday não conhece por si; só o dono os executa (`friday step NAME [KEY]`, sem nome a lista e o estado) ([ADR 0011](../adr/0011-profile-steps.md)): `{"<name>": {"run": [...], "scope": "task" \| "profile", ...}}`. `run` é um array de argumentos que roda no host; um passo de tarefa recebe `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`, qualquer passo recebe `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}`, `{secret.<name>}`. `description`, `env` (sem valores secretos), `cwd`. `lock` é um recurso compartilhado pela duração do passo: um caminho compartilha o lock do repositório, um nome é um lock nomeado. `commit: {"paths": [...], "message": "{key}: ..."}` faz o Friday dar commit nesses caminhos; o passo fica desatualizado quando a branch muda fora deles depois do commit. `required` (um passo de tarefa): enquanto o passo não está feito ou está desatualizado, `status`, o diário e o texto do MR o lembram com o comando dele. `check` (um passo de perfil) é um comando de prontidão para o `doctor`: 0 pronto, 2 desatualizado (!), qualquer outro ausente (✗). `secrets: {"<name>": "<path>"}` são arquivos que o comando recebe por caminho; o Friday não os lê. Coloque um procedimento complexo em um script ao lado do perfil |
| `design` | Ferramentas de design para tarefas de UI ([ADR 0007](../adr/0007-design-tools.md)). `figma: {"url": "http://127.0.0.1:3845/mcp"}` é o servidor MCP local do Dev Mode do Figma desktop; `tools` restringe as ferramentas de leitura (`get_metadata`, `get_design_context`, `get_screenshot`, `get_variable_defs`), ferramentas de escrita não são aceitas. Quando o ticket tem um link `figma.com/design/…?node-id=…`, `start` verifica que o nó está aberto na aba ativa do Figma, e o planejador e o revisor do plano leem o frame e escrevem uma especificação mensurável no plano. O executor e as revisões a recebem no prompt, sem acesso ao Figma. O Friday salva capturas dos frames na pasta da tarefa; a aceitação no navegador compara o preview com elas e mede estilos (`computed_style`): uma diferença em relação a um número da especificação bloqueia, uma diferença vista apenas a olho vai para os achados menores do MR. Se o Figma não responde ou o nó não existe, `start` para e diz o que abrir; `start --no-design` planeja sem o mockup. `impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` nomeia arquivos de `reference/` do skill /impeccable que o Friday coloca no prompt dos marcos de UI; `references` é obrigatório e associa os papéis `develop`, `review`, `final-review` a listas de arquivos (por exemplo `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API ou MCP), usado para ler a descrição da tarefa |
| `journal` | Onde gravar o diário da tarefa: `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]`; `page` é o caminho da página da tarefa dentro de `dir` (`{key}.md` por padrão), por exemplo na pasta da tarefa no Obsidian. `journal_dir` e `journal_page` são uma forma curta para um único diário markdown; um `journal` definido no perfil (ou herdado) prevalece sobre eles. O Friday não mexe em uma página que não escreveu (sem `friday_generated` no front matter): imprime que a pulou e escreve o resto |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` e a chave `github.repository` ou `gitlab.base_url` + `gitlab.project` |
O nome do repositório vem da URL do `origin` (HTTPS, SSH ou um caminho local), sem `.git`; quando não há `origin`, do nome do repositório principal em disco, também ao trabalhar a partir de um worktree vinculado. Os caracteres fora de `A–Z`, `a–z`, `0–9`, `_` e `-` viram `-`, e os `-` iniciais e finais são removidos. Um nome vazio exige um `branch_template` explícito. A chave completa da tarefa é mantida: `31` dá `octis/31`, `OCTIS-031` dá `octis/OCTIS-031`. Uma branch já registrada no card da tarefa é mantida quando a tarefa continua; uma nova configuração vale para as novas tarefas. Uma vitrine vinculada usa o nome do repositório principal da tarefa.

### Modelos e papéis

```json
"models": {
  "fable": {"model": "claude-fable-5-2", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver`: o que executa o modelo, `claude` ou `codex`. A Z.ai passa pelo Claude Code; o token é lido de um arquivo que só o dono pode acessar.
- `tier`: `frontier`, `strong` ou `efficient`; `strength` ordena os modelos dentro de um nível.
- `effort`: a profundidade do raciocínio (`low` … `max`); um mesmo modelo pode ser descrito várias vezes com esforços diferentes.
- `scarce`: um modelo caro; é usado uma vez por tarefa se as regras permitirem que a tarefa siga sem ele.
- `price`: o preço por milhão de tokens por tipo (`input`, `output`, `cache_read`, `cache_write`), usado para estimar o gasto quando o fornecedor não informa o preço.

Papéis: `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. As listas em `roles` são preferências: se a lista não tem um modelo adequado, o Friday escolhe outro do catálogo. Regras rígidas: só modelos `frontier` revisam código, o revisor não é mais fraco que o autor do trabalho, e a verificação cega não é feita pelo autor do código. Regras flexíveis, em ordem: não o mesmo modelo do autor; um modelo caro uma única vez; um fornecedor diferente; a verificação cega não feita pelo autor do plano. Uma regra flexível só pode ser quebrada quando não há outra saída, e a violação é registrada no histórico da tarefa.

Um exemplo de atribuição de papéis está em [examples/models.json](../../examples/models.json).
Com `executor_tiers`, um marco complexo usa o nível mais alto permitido, e uma substituição por cota mantém o nível necessário dentro do limite. Uma atribuição de papéis antiga com um executor proibido é substituída por um permitido; uma escrita feita por um modelo proibido, ou que não corresponde ao catálogo, é rejeitada. Os níveis e os nomes vêm do catálogo do perfil; o Friday não os deduz do nome do modelo.

Os marcos em paralelo têm seus próprios worktrees e são integrados na ordem do plano. O Friday verifica a sobreposição dos caminhos declarados antes do início e das mudanças reais antes da integração. O trabalho que não pôde ser integrado fica guardado em sua branch e em seu worktree; `parallel_recovery_required` os nomeia antes de a tarefa continuar. Depois de revisar o trabalho retido, o controlador termina de movê-lo ou guarda separadamente os commits necessários, e em seguida remove os worktrees e as branches das faixas revisadas com comandos comuns do Git. O Friday não apaga esses resultados automaticamente para tentar de novo.

Uma revisão final salva está vinculada a worktrees limpos, aos commits dos dois repositórios, ao plano, às decisões, às configurações dos modelos e ao texto exato da entrada do papel. Uma mudança nas entradas durante a verificação devolve `stale_evidence`. Quando o segundo papel falha, o primeiro, já concluído, é mantido; o próximo `resume` executa apenas as verificações que faltam para as mesmas entradas. Aumentar `budget` e alterar `max_parallel_milestones` mantêm uma revisão concluída: essas configurações controlam a admissão e o agendamento, não o conteúdo da verificação.

## Diário

O card da tarefa é a única fonte da verdade. Os diários o refletem e se atualizam após eventos importantes: o plano ficou pronto e foi aprovado, um marco foi concluído ou falhou, uma decisão do dono, a revisão final, o MR, uma interrupção. Para atualizá-los manualmente, execute `friday journal KEY`.
O tempo é a soma das durações das execuções, inclusive as paralelas, não o tempo do calendário. Para as novas execuções sem duração informada pelo provedor, o runner a mede por conta própria. Uma interrupção antes de o runner iniciar registra tempo de execução zero; uma nova execução sem medição mantém uma duração desconhecida. Eventos antigos vinculados dão uma estimativa marcada explicitamente que pode incluir a espera por um slot. Uma execução perdida sem medição tem duração desconhecida. Um preço desconhecido também é mostrado por papel; ele não vira custo zero.

- `markdown`: uma página `KEY.md` e uma página de visão geral compartilhada que lista todas as tarefas. Para o Obsidian, defina a pasta do vault: as páginas têm front matter (chave, estado, gasto, a tag `friday`), e as tarefas são ligadas por wiki links. A página de uma tarefa contém o plano com suas premissas e achados não resolvidos, os marcos com o resumo do executor e os commits, os achados contestados, as decisões, o gasto por papel e a linha do tempo.
- `jsonl`: todos os eventos da tarefa, para análise em planilhas ou dashboards.

Os templates são Markdown com as substituições `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. O Friday usa o template do campo `template` do destino, depois `.friday/task.md` no repositório do projeto, depois o embutido ([friday/templates](../../friday/templates)). O texto entre `<!-- friday:notes -->` e `<!-- /friday:notes -->` é seu: ele é preservado a cada atualização. O Friday não sobrescreve uma página que ele não escreveu.

## Configurações da máquina

`FRIDAY_HOME/machine.json` define os recursos compartilhados por todas as tarefas:

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

Por padrão, rodam ao mesmo tempo um gate e dois navegadores, e os fornecedores não têm limite. As cotas dos fornecedores são acompanhadas automaticamente: uma execução que atinge um limite registra quando a cota volta e, até lá, o fornecedor é ignorado na escolha dos modelos.
### Fila de tarefas: `friday serve`

`friday serve` é um processo de longa duração com uma fila de tarefas aprovadas por máquina ([ADR 0014](../adr/0014-work-pool.md)). Enquanto ele roda, `approve`, `resume` e uma resposta dada com `decide` a uma sessão de execução não iniciam a tarefa por conta própria, mas a colocam na fila; sem ele, uma tarefa roda como um processo separado em segundo plano, como antes, e `resume` roda no terminal.

- No máximo `max_workers` tarefas rodam ao mesmo tempo (`machine.json`, 2 por padrão); tarefas iniciadas fora da fila também contam.
- A fila segue a hora em que o plano foi aprovado; uma tarefa que continua depois de `decide` vai primeiro. `friday status` mostra a fila e o estado do servidor, `friday stop` tira uma tarefa da fila.
- Uma tarefa "em execução" cujo processo morreu (suspensão, reinício) é devolvida à fila pelo servidor como `resume`.
- Quando uma tarefa para por uma pergunta ou por um passo do dono, falha ou termina, chega uma notificação do sistema (`osascript` no macOS, `notify-send` no Linux).

Para o servidor, uma tarefa é um único trabalho: os marcos não são divididos em trabalhos, e ainda não há limite por tarefa.

`friday service print|install|uninstall` instala o servidor como um serviço de usuário: um agente do launchd (`~/Library/LaunchAgents/local.friday.serve.plist`) ou uma unit do systemd. Um serviço começa com um ambiente vazio, então o arquivo dele nomeia tudo por conta própria: `PATH` com os diretórios de `claude`, `codex`, `docker`, `git` (e `glab`, `gh`, `uvx`, `node`, `npx` quando existem), `FRIDAY_HOME`, `HOME`. `friday service check --profile P` executa `friday doctor` exatamente nesse ambiente, de modo que você vê antes de instalar o que o serviço não vai encontrar. Se o serviço encontra o login da assinatura do Claude, só a primeira tarefa sob ele mostra. O serviço fala o idioma salvo com `friday config language`.

## Limites

- **Sandbox do executor.** O shell do executor (Claude Code) roda em um sandbox: sem rede, sem leitura de `~/.ssh`, `~/.aws`, `~/.config` e similares, com escrita apenas no worktree e em uma pasta temporária, e sem execução fora do sandbox. Comandos fora de `executor_commands`, os comandos do git (`add`, `commit`, `status`, `diff`, `log`, `restore`) e `bin/friday-precedent` são rejeitados. O Codex roda em seu próprio sandbox com os mesmos limites.
- **Git no Codex.** O Friday coloca o Git instalado e uma cópia separada dos metadados do Git no ambiente de execução da tarefa. As configurações globais do Git e os perfis de shell do usuário não são carregados; os dados de serviço do repositório de origem não são expostos ao agente. O executor salva as etapas com commits comuns do Git. Quando o processo dele termina, o Friday pega os commits por meio de um bundle verificado e os devolve à branch de origem se o HEAD e o índice dela não mudaram. Em caso de conflito de estado, o bundle fica no log da execução como `git-recovery.bundle`; nada é sobrescrito automaticamente. Um revisor recebe os metadados do Git somente para leitura. `doctor` verifica o cenário real de três commits em um worktree vinculado sem chamar um modelo, e que as proibições de ler segredos e de escrever para o revisor valem.
- **Os revisores** apenas leem. A verificação cega roda em uma pasta vazia.
- **O gate** roda em um contêiner sem acesso à rede, sobre um snapshot do commit montado como somente leitura.
- **O navegador** recebe apenas as ferramentas do Friday para um preview (incluindo `hover` e `computed_style`, que lê estilos com um script fixo, sem `evaluate_script`); contornar a autorização e ler os cabeçalhos de requisições autorizadas é proibido.
- **O Figma** só é lido pelo planejador e pelo revisor do plano, e só com as ferramentas de leitura do servidor local do Figma desktop. O skill /impeccable não roda dentro dos papéis: o Friday coloca os textos dele no prompt.
- **Publicação.** O Friday faz push apenas da branch da própria tarefa e abre apenas um MR/PR em rascunho. Ele não sobrescreve a branch de outra pessoa, não faz merge nem deploy.
- **Ainda não verificado ao vivo:** a aceitação no navegador e a publicação no GitLab foram verificadas por testes com simulações. O Git no ambiente do Codex também é verificado por um laboratório local real sem chamar um modelo; a execução de um papel pelo modelo é verificada separadamente em cada tarefa.
