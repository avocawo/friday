# Friday: почему долго и дорого и что менять в процессах

Разбор по итогам пилота на фронтенд-проекте (задачи A и B, 29–30.10.2026). Источники: карточки задач Friday, локальный журнал проблем пилота (вне репозитория), код Friday на 02.11.2026.

## 1. Что показали цифры

| | Задача A | Задача B |
| --- | --- | --- |
| Этапов в плане | 22 | 17 |
| Закрытий этапов | 58 (каждый ≈2,6 раза) | 26 |
| Запусков моделей | 246 | 112 |
| из них разработка | 79 (32%) | 24 (21%) |
| из них проверки (review, blind-code, blind-behavior) | 167 | 88 |
| Вердикт `unverifiable` (работа без результата) | 18 | 33 (29% всех запусков) |
| Запусков гейта | 102 | 50 |
| Решений `decide` / замен плана | 11 / 10 | 22 / 8 |

Минимум на этап — 3 тяжёлые операции: разработка, гейт, ревью. Фактически вышло ≈16 на этап в задаче A и ≈10 в задаче B. Деньги и время уходят не на саму разработку, а на **повторы × число ролей × размер контекста**. На разработку приходится 21–32% запусков; остальное — проверки, причём треть проверок в задаче B не дала вердикта.

Оценка времени по промежуткам между событиями карточки (включает ожидание человека, поэтому только порядок величин): в задаче B разработка ≈1 ч, проверки и гейт ≈7,5 ч, из них браузерная роль ≈3,3 ч при 14 из 22 запусков `unverifiable`.

## 2. Почему долго и дорого: механизмы в коде

**Каждая проверка читает всю задачу заново.** Ревьюер получает дифф от `plan_base` до HEAD (`workflow.py`, `review_diff`), а не дифф этапа. Этап 15 получает изменения этапов 1–14, и так у каждой из трёх ролей, на каждой попытке. Расход растёт квадратично от числа этапов.

**Каждый запуск — холодный агент.** `claude -p --no-session-persistence` (`adapters/claude.py`) и аналог в Codex: агент каждый раз заново читает `AGENTS.md`, `ARCHITECTURE.md` и документацию — этого прямо требует `engineering_policy` профиля. Повтор разработчика после замечания не продолжает прежнюю сессию и не попадает в кэш промпта.

**Мелкие этапы с фиксированной ценой.** Лимит 10 файлов / 500 строк (`autopilot.check_size`, `workflow.load_plan`) дробит задачу на 17–22 этапа. Каждый этап платит полный круг: коммит → Docker-гейт → до трёх последовательных ревьюеров → закрытие. Браузерная роль на каждом вызове поднимает свой изолированный Vite preview (`isolated_preview.open_preview` внутри `invoke`), отсюда потери сессии и 401.

**Любое решение сбрасывает всё.** `decisions.py` переоткрывает все закрытые этапы, `plan --replace` создаёт все этапы заново. В задаче A одно решение `target_branch` переоткрыло 20 этапов.

**Разработчик слеп.** У него нет shell (`claude.py`: только `Read,Glob,Grep,Edit,Write`), тесты и типы он узнаёт только от гейта. А гейт отдаёт ему последние 10 000 символов лога (`gate.feedback`), где ошибок ESLint и vue-tsc нет вовсе (п. 16 журнала). Каждая опечатка — полный круг разработчик → гейт.

**Четвёртый вызов вместо третьего.** Если `blind-code` вернул `unverifiable`, автопилот сразу зовёт ещё одно `review` (`autopilot.py`, ветка `fallback_for`).

**Всё последовательно.** Глобальные блокировки `gate:global`, `resource:browser:global` и блокировка ветки сериализуют даже чтение неизменного коммита.

## 3. Почему непрозрачно

- `subprocess.run(..., stdout=PIPE, timeout=1800)` в `workflow.invoke` и адаптерах: до выхода процесса нет ни строчки. 30 минут тишины — штатное поведение, а не сбой.
- В карточке нет текущей фазы с временем начала: `take-stock` не может сказать «этап 3b, ревью Sol, идёт 12 минут».
- Адаптеры выбрасывают из ответа `claude -p --output-format json` поля `usage`, `total_cost_usd`, `duration_ms`, `num_turns`. Friday в принципе не знает, сколько стоил этап. Ощущение «тратит больше, чем я сам» сейчас нечем ни подтвердить, ни опровергнуть.
- stderr раннера не сохраняется, дочерний процесс не убивается вместе с адаптером (`setsid`/`killpg` нигде нет) — п. 9 и 11 журнала.

## 4. Почему делегирование неудобно

- Роли заданы на весь профиль, а не на задачу (п. 17). Смена модели из-за лимитов задевает соседние задачи.
- Независимость ревьюера — сравнение строк модели (`autopilot.py:56`). `glm-5.2` против `glm-5.3` проходит, хотя это один вендор. А схему «GLM пишет всё, одна сильная модель смотрит в конце» выразить нельзя: на каждом этапе обязательны все роли.
- Нет понятия «план готов, исполнитель дешёвый». Дешёвая модель получает те же короткие брифы, без shell и без внятной обратной связи — и платит за это повторами сильных ревьюеров.

## 6. Предложение: новый конвейер

*Предложение до обсуждения. Принятые решения — раздел 8 и `docs/adr/`; в частности, гейт идёт на веху, а не на каждый этап, а слепая проверка кода — только в финале.*

Цель остаётся прежней: конвейер без ручного вмешательства и перекрёстная проверка моделями другого вендора. Меняется место, где тратятся сильные модели.

### Принцип

Дешёвая обратная связь — часто и сразу, дорогая — редко и на крупных кусках.

```text
план (сильная модель, один раз)
  → вехи по 2–5 этапов
      этап: разработка (дешёвая модель, с быстрыми проверками у себя) → гейт → коммит
      веха: одно ревью сильной моделью другого вендора по диффу вехи
            + браузерная приёмка, если веха меняет интерфейс
  → финальное ревью по всему диффу (режим strict: три роли)
  → черновой MR
```

### Конкретные изменения

1. **Разработчик проверяет себя сам.** Дать роли `develop` ограниченный `Bash` на команды из профиля (`lint`, `typecheck`, тесты затронутых файлов) или запускать быстрый гейт перед коммитом. Ошибки компиляции и линтера должны исправляться внутри одной сессии разработчика, без круга через Friday.
2. **Гейт отдаёт ошибки, а не хвост.** Блоки проваленных проверок `validate:diff`, затем строки `error`/`FAIL`, затем остаток.
3. **Ревью по вехе, а не по этапу.** Этап остаётся единицей коммита и гейта, но не единицей ревью. Ревью получает дифф вехи (`review_base` = начало вехи), а не всей задачи. При 17 этапах и вехах по 4 это ~5 ревью вместо ~50.
4. **Слепые роли — по запросу плана, а не по умолчанию.** `blind-code` — только на финальном проходе или на рискованных вехах. `blind-behavior` — на вехах с поведенческими критериями, на одном долгоживущем preview на всю задачу.
5. **Повторы продолжают сессию.** Разработчик после замечания или гейта продолжает свою сессию (`--resume` в Claude Code, аналог в Codex) — кэш промпта и уже прочитанные документы сохраняются. Тяжёлое чтение `AGENTS.md`/`ARCHITECTURE` делает планировщик один раз и кладёт выжимку правил в бриф.
6. **Точечная инвалидация.** Решение или замена плана переоткрывает только этапы, у которых пересекаются файлы или критерии с изменением, и их зависимых. Если пересечение не доказать — текущее поведение.
7. **Роли на задачу.** `clock-in --runners …` или `decide KEY runners …` фиксирует раскладку в карточке на старте прогона. Независимость проверяется по вендору и по фактической модели разработчика этапа.
8. **Режимы конвейера вместо одного.** *Не принято: по решению 02.11.2026 конвейер один, слепая проверка только в финале (ADR 0001).*
   - `fast` — дешёвая модель пишет, гейт на этапе, одно сильное ревью на веху и финал. Для задач с готовым планом — сценарий ZCode/GLM.
   - `standard` — то же плюс браузерная приёмка UI-вех.
   - `strict` — нынешнее поведение: три роли на каждом этапе. Для рискованных задач и финала.

### Прозрачность — до всего остального

9. **Учёт расхода.** Сохранять в каждом `model_run` `usage`, `total_cost_usd`, `duration_ms`, `num_turns`, модель и вендор. `take-stock KEY` показывает стоимость и время по ролям и этапам. Без этого невозможно сравнить новый конвейер со старым.
10. **Живой статус.** Читать stdout раннера потоком (`--output-format stream-json`), писать в карточку фазу, модель, время начала и последний признак жизни. `take-stock` показывает «идёт 12 мин, последнее действие 20 с назад». Таймаут по отсутствию активности, а не только по общему времени.
11. **Надёжный раннер.** Отдельная группа процессов, убийство группы при любом выходе, stderr в доказательства, список изменённых файлов после `runner_failed`.

Заменено решением пересобрать ядро (раздел 8, `docs/adr/0001`–`0006`). Порядок реализации нового ядра:

*Статус на 02.11.2026: шаги 1–9 сделаны, старое ядро удалено; впереди пилот на реальной задаче.*

1. **Раннер агентов.** Запуск Claude Code и Codex с чтением вывода потоком, своя группа процессов, таймаут по бездействию, stderr и расход (`usage`, стоимость, длительность) в событие, продолжение сессии, набор инструментов исполнителя. Готово, когда тест на фейковом агенте показывает живой статус и корректно убивает зависший процесс.
2. **Карточка v2 и `friday status`.** Задача, вехи, этапы, события, расход; статус по всем активным задачам на машине.
3. **Политика моделей.** Уровни, раскладка ролей в карточке, жёсткие и мягкие правила, резервы, учёт квот вендоров (ADR 0002).
4. **План.** Планировщик, проверка плана другим вендором, утверждение; проверки выполнимости (объём, критерии в пределах этапа, проверяемость); пересечение файлов с другими задачами.
5. **Исполнение вехи.** Сессия на веху, гейт с обратной связью блоками упавших проверок, ревью вехи по её диффу, эскалация уровня, спорные находки, точечная инвалидация (ADR 0001, 0003, 0004).
6. **Общие ресурсы.** Места для гейта и браузера, порты preview, параллельные вехи в отдельных worktree (ADR 0005).
7. **Финал.** Браузерная приёмка UI-вех, финальное ревью со слепой проверкой кода, черновой MR.
8. **Журнал Obsidian.** Шаблоны в `templates/`, сборка из событий, страница «Friday — сейчас» (ADR 0006).
9. **Удаление старого ядра.** Старые команды и модули, обновление `README.md` и `docs/guide.md`.
10. **Пилот.** Реальная задача на проекте пилота; сравнение запусков, времени и стоимости с задачей B.

Сохраняются и переиспользуются: профили, изолированный гейт в Docker, worktree и изоляция, браузерная сессия и preview, интеграции с Трекером, GitLab и GitHub, хранение секретов.

## 8. Обсуждение 02.11.2026: решения и уточнения

Решено: ядро пересобираем, старые команды сносим вместе с ним. Конвейер: план (сильная модель) → проверка плана другой сильной моделью → утверждение владельцем → исполнение по вехам → гейт → ревью вехи → финальное ревью со слепой проверкой кода → черновой MR. Браузерная приёмка — только на вехах с интерфейсом. Исполнитель получает минимальный набор инструментов без запросов разрешений. Конвейер не останавливается: спорные находки уходят в журнал Obsidian, владелец разбирает их на MR. Журнал ведётся по шаблонам Friday.

### Политика моделей: уровни вместо имён

Что говорят вендоры:
- Anthropic: «Most workloads start with Claude Opus 5.5»; настройка effort «often a better lever than switching models». Оркестратор с дешёвыми исполнителями окупается только при работе, которая расходится на независимые части или не влезает в один контекст. Для одной зависимой цепочки одна модель с меньшим effort «came out ahead in every case measured». Мультиагентные системы тратят ~15× токенов чата; для кода параллельных подзадач мало. Источники: platform.claude.com/docs/en/about-claude/models/choosing-a-model, …/optimizing-for-cost-and-intelligence, anthropic.com/engineering/multi-agent-research-system.
- OpenAI (Codex): Astra — для сложной сквозной работы, 6.1 Sol — «near-Astra performance… at a lower cost» для повторяющейся длинной работы, Luna — для узкого кодинга, Terra — не для кода. Effort начинать с умолчания и повышать для задач с планированием и проверкой. Источник: learn.chatgpt.com/docs/models.
- Z.ai: GLM-5.3 — флагман для кода и длинных задач, 1M контекста, effort по умолчанию `max`. По данным вендора на уровне High близок к Opus 4.8, ниже Fable 5. В GLM Coding Plan доступны только GLM-5.3 и GLM-5.3-Flash, квота общая для всех инструментов, окна 5 часов и 7 дней, ночью расход вдвое ниже. ZCode — среда с Goal Mode (план → исполнение → проверка); по сторонним источникам открыт CLI с `--prompt`, официально не подтверждено. Источники: docs.z.ai/guides/llm/glm-5.3, docs.z.ai/devpack/faq, docs.z.ai/devpack/tool/zcode.

Предложение. В профиле у каждой модели — вендор и уровень (`frontier` / `strong` / `efficient`). Роли задаются уровнем, Friday подбирает конкретную модель по правилам и фиксирует раскладку в карточке до утверждения плана:

| Правило | Строгость |
| --- | --- |
| Уровень ревьюера ≥ уровня исполнителя, чей код он смотрит | жёстко |
| Ревью вехи и финал — другой вендор, чем исполнитель | мягко: если вендор недоступен, тот же вендор другой моделью того же или выше уровня, с пометкой в журнале |
| Проверка плана — другой вендор, чем планировщик | мягко, как выше |
| Финальная слепая проверка — `frontier`, не исполнитель и по возможности не планировщик | жёстко по уровню |
| Исполнитель — `efficient`/`strong` для вех, которые план пометил как ясные; `frontier` для помеченных сложными | по плану |
| Эскалация: два провала гейта или ревью подряд — следующая попытка вехи моделью уровнем выше | автоматически |
| Лимит вендора исчерпан — замена внутри уровня по списку резервов, запись в журнал | автоматически |

Пример уровней на сегодня: `frontier` — Fable 5.1, Opus 5.5, gpt-6-astra; `strong` — Sonnet 5.5, gpt-6.1-sol, GLM-5.3; `efficient` — Haiku 5.5, gpt-6-luna, GLM-5.3-Flash.

Замечание по профилю проекта пилота: ревью-роли настроены на `glm-5.2` при разработке на `glm-5.3` — это ревью слабее исполнителя, а по FAQ Coding Plan `glm-5.2` в плане недоступна. Проверить.

### Несколько задач одновременно

Каждая задача — своя карточка, ветка и worktree (как сейчас). Меняется управление общими ресурсами:

- **Слоты вместо глобальных замков.** `gate:global` и `resource:browser:global` заменяются семафорами с ёмкостью из профиля машины: гейтов параллельно N (в пилоте два тяжёлых гейта исчерпали ресурсы — по умолчанию 1–2), браузерных проверок — по числу вкладок, каждая задача в своей вкладке и на своём порту preview. Короткий замок на репозиторий только для `git fetch` и `worktree add`.
- **Квоты вендоров.** Учёт параллельных вызовов и окон квоты на вендора (общая квота z.ai для всех задач). Исчерпана — замена внутри уровня или ожидание, и статус пишет «ждёт окна z.ai до 15:40».
- **Пересечения задач.** При утверждении плана Friday сверяет файлы плана с файлами других активных задач и предупреждает о будущих конфликтах.
- **Один статус на всё.** `friday status`: задача, веха, фаза, модель, время в фазе, последняя активность, стоимость. В Obsidian — страница «Friday — сейчас» со списком активных задач и ссылками на их журналы.
- **Тот же механизм для параллельных вех внутри задачи.**

## 10. Универсальность, журнал, связь между моделями

### Процесс проекта — данные, а не код

Каркас конвейера фиксированный (план → проверка плана → утверждение → вехи → финал → MR): это даёт предсказуемость. Всё, что отличается между проектами, описывает профиль, а реализуют сменные адаптеры с одним контрактом (JSON через stdin/stdout, как сейчас):

| Что отличается | Где описано | Адаптер |
| --- | --- | --- |
| Проверки | наборы проверок: команда, образ, сервисы (полный CI проекта — набор с сервисами, например PostgreSQL, а не отдельный модуль), где запускать — у исполнителя, на вехе, в финале | `checks` |
| Стенд и браузер | рецепт preview, адрес API, авторизация | `preview` |
| Трекер | Yandex Tracker, GitHub Issues, Jira | `tracker` |
| Хостинг кода | GitLab, GitHub; черновой MR или только ветка | `vcs` |
| Модели | каталог: вендор, уровень, резервы, способ запуска | `harness` |
| Журнал | куда и по каким шаблонам писать | `journal` |
| Правила | инженерная политика, ветки, переключатели этапов каркаса (проверка плана, браузерная приёмка) | — |

Общий движок процессов (произвольные графы шагов) сознательно не делаем: он возвращает непредсказуемость, от которой уходим.

### Журнал: канонический источник плюс получатели

Карточка задачи с событиями всегда хранится локально и остаётся единственным источником истины. Журналы — это получатели, которые её отображают; в профиле их можно указать несколько:
- `markdown` — папка с Markdown по шаблонам. Obsidian — частный случай: папка хранилища плюс шаблоны с wiki-ссылками;
- `tracker-comment` — сводка вехи комментарием в задачу трекера;
- `mr-description` — итог и спорные находки в описании чернового MR;
- `jsonl` — сырые события и расход для анализа (таблицы, дашборды).

Шаблоны ищутся сначала в проекте, потом в профиле, потом берутся встроенные шаблоны Friday.

### Связь между моделями

Принцип: модели не переписываются друг с другом напрямую. Независимость ревью держит Friday, иначе ревью превращается в сговор и сжигает токены (мультиагентные схемы ~15× токенов чата, по данным Anthropic). Friday даёт каждому агенту свой MCP-сервер `friday` с инструментами:
- `ask_advisor(вопрос)` — исполнитель советуется с сильной моделью другого вендора, когда застрял (схема executor + advisor из рекомендаций Anthropic). Ответ и расход пишутся в карточку;
- `run_check(имя)` — запуск разрешённой проверки из профиля;
- `dispute(находка, правило, цитата)` — оспорить замечание ревью;
- `progress(заметка)` — признак жизни и заметка для статуса.

MCP поддерживают все рассматриваемые среды (Claude Code, Codex, OpenCode), так что канал не привязан к одной среде.

### OpenCode как общая среда исполнения

Что подтверждено документацией:
- работает с OpenAI по входу ChatGPT Plus/Pro и с Z.ai Coding Plan, и OpenCode есть в списке официально поддерживаемых Coding Plan инструментов;
- Anthropic — только по API-ключу: подписки Pro/Max в сторонних средах Anthropic запрещает, плагины для них убраны в 1.3.0;
- `opencode serve` — HTTP API: создание сессии, сообщение с выбором модели на запрос, поток событий SSE, `abort`, ответ на запросы разрешений;
- права на агента, включая белый список команд `bash`.

Вывод: у раннера Friday два драйвера. OpenCode server — для OpenAI и GLM: одна среда, единые сессии, поток событий и права. Claude Code — для Anthropic по подписке. Codex CLI остаётся резервным драйвером. Расход токенов в API OpenCode на странице сервера не описан, это нужно проверить на прототипе до выбора.
