## Instalasi

1. Clone Friday dan tambahkan `bin` ke `PATH`, atau atur `FRIDAY_BIN`.
2. Pasang CLI yang dibutuhkan agen: Claude Code (`claude`) untuk model Anthropic dan Z.ai, Codex CLI (`codex`) untuk model OpenAI. Login ke keduanya seperti biasa.
3. Untuk gate dan akseptasi di browser, pasang Docker. Akseptasi di browser juga memerlukan Chrome dengan port debugging 9333 dan sesi yang sudah login di lingkungan uji.
4. State disimpan di `~/.local/share/friday` (ubah dengan `FRIDAY_HOME`). Profil dan rahasia tidak masuk ke repositori: folder `profiles/` ada di `.gitignore`.

### Plugin untuk Codex dan Claude Code

```sh
codex plugin marketplace add "$PWD" && codex plugin add friday@friday
claude plugin marketplace add "$PWD" && claude plugin install friday@friday --scope user
```

Plugin ini mengajari agen membaca `status` dan `plan`. Memulai tugas, menyetujuinya, dan mengambil keputusan tetap menjadi urusan Anda.

## Cara tugas berjalan

1. **`start`** membuat branch `<repository>/KEY` (misalnya `octis/31`) dari `origin/<base_branch>` yang segar beserta worktree, mengunci penugasan peran, lalu menulis rencana: milestone yang terdiri dari 2–5 tahap, berkas, perkiraan ukuran, kriteria kode dan browser, serta ringkasan aturan proyek untuk eksekutor. Rencana lebih dulu diperiksa tanpa model (ukuran, berkas, urutan, kriteria). Setelah itu model dari vendor lain mereviewnya, dan perencana menjawab temuan satu kali: menerima tiap temuan atau menolaknya disertai alasan.
   Dengan `"toolset": {"plan": "project"}`, proses milik proyek sendiri yang menulis rencana ([ADR 0015](../adr/0015-project-toolset.md)): Friday memulai sesi Claude Code biasa di worktree dengan pengaturan, hook, skill, agen, dan MCP proyek, lalu meneruskan `project.plan_command` beserta pernyataan tugas kepadanya. Sesi menulis berkas rencana proyek (`project.plan_file`) dan mengembalikan kepada Friday ringkasan rencana yang sama dalam skemanya; Friday memeriksa ringkasan tanpa model dan tidak menjalankan review oleh vendor lain, karena proses proyek memiliki review sendiri. Sesi berjalan dalam mode izin `auto`; hasilnya adalah jawaban terakhir sebelum proses berakhir, karena proses proyek dapat menunggu review di latar belakang.
2. **`plan`** menampilkan rencana, pertanyaan, temuan yang ditolak, dan tumpang tindih berkas dengan tugas aktif lainnya.
3. **`approve`** menyetujui rencana dan menjalankan pipeline di latar belakang (`--no-run` hanya menyetujui; jalankan nanti dengan `run`).
   Dengan `"toolset": {"execute": "project"}`, Friday menjalankan proses milik proyek sebagai ganti milestone ([ADR 0015](../adr/0015-project-toolset.md)): satu sesi Claude Code dengan `project.execute_command` pada model peran `develop`. Sesi melakukan commit pada setiap tahap dengan id-nya dari ringkasan rencana di awal subjek (`M1.1: …`) dan tidak memublikasikan apa pun. Sebuah pertanyaan mengakhiri sesi: tugas berhenti, pertanyaan tampil di `status`, dan jawaban yang diberikan dengan `decide` melanjutkan sesi yang sama di latar belakang; `resume` melakukan hal yang sama tanpa jawaban. Sesi menerima apa yang menghentikannya. Jika sesi selesai tanpa pertanyaan dan lingkungan yang menghentikan tugas (image gate, login ke lingkungan uji), `resume` tidak membangunkan sesi dan hanya mengulang pemeriksaan setelahnya. Setelah sesi, Friday memeriksa bahwa pohon kerja bersih, bahwa setiap tahap memiliki commit dalam `limits` (`git diff --numstat` dari commit-nya), menjalankan gate dan akseptasi di browser untuk milestone yang memiliki antarmuka, lalu pemeriksaan akhir dan MR seperti biasa; review akhir dalam mode ini lebih dulu membaca `AGENTS.md` (atau `CLAUDE.md`) di akar repositori dan memeriksa diff terhadap bagian dokumen proyek, bukan hanya terhadap aturan rencana. Setiap ketidakcocokan menjadi pertanyaan untuk pemilik.
4. **Milestone.** Eksekutor bekerja dalam satu sesi per milestone dan melakukan commit pada setiap tahap. Gate berjalan pada commit tersebut. Jika gagal, eksekutor hanya menerima bagian log yang gagal; jika sebuah bagian lebih panjang dari batas, judulnya dan baris galatnya beserta konteks dipertahankan, dengan tes gagal dalam format TAP (`not ok …` beserta diagnosisnya) di urutan pertama. Review milestone memeriksa diff milestone ini bersama hasil gate. Eksekutor memperbaiki atau membantah temuan yang memblokir; temuan yang dibantah dikirim kepada Anda. Milestone yang memiliki antarmuka melewati akseptasi di browser dalam preview yang terisolasi. Setelah dua kegagalan berturut-turut, Friday menaikkan tingkat eksekutor dalam batas `executor_tiers` jika profil menetapkan batas itu; penggantinya memulai sesi baru.
5. **Akhir.** Peran dalam `final_review_roles` memeriksa seluruh diff: secara bawaan review akhir dan pemeriksaan buta berjalan paralel; profil dapat mempertahankan hanya review akhir. Temuan yang memblokir mendapat satu putaran perbaikan.
6. **Draft MR** dibuka jika profil menetapkan `delivery`. Jika tidak, teksnya disimpan di `merge-request.md` dalam folder tugas.

Pipeline berhenti jika gate tidak pernah lulus, eksekutor tidak melakukan apa pun, lingkungan tidak tersedia, model yang diizinkan oleh aturan sudah habis, atau anggaran yang ditetapkan habis. Perubahan paralel yang tumpang tindih, branch yang dipertahankan tetapi belum diintegrasikan, dan masukan review akhir yang bergeser juga memerlukan perhatian sebelum tugas dilanjutkan. Perbedaan pendapat dalam review tidak menghentikannya. Milestone yang tidak diperiksa oleh apa pun (tanpa gate, pemeriksaan eksekutor tidak berjalan, tanpa akseptasi di browser) ditutup sebagai "selesai, belum diverifikasi" beserta alasannya, di status, jurnal, dan MR ([ADR 0009](../adr/0009-unverified-is-not-done.md)); jika pemeriksaan eksekutor tidak dapat berjalan dan tidak ada gate, milestone diblokir.

`decide KEY name "text" --reopen M2` mencatat keputusan Anda. Selama rencana Friday menunggu persetujuan, `decide` juga merevisinya ([ADR 0016](../adr/0016-decision-revises-the-plan.md)): perencana menulis ulang milestone yang disebut di `--reopen` dalam sesi baru dan sisanya dibawa apa adanya; tanpa `--reopen` ia memilih sendiri milestone yang terpengaruh. Model lain hanya mereview milestone yang berubah. `decide` mencetak milestone mana yang direvisi dalam rencana, mana yang dibuka kembali untuk dijalankan lagi, dan mana yang hanya menerima keputusan dalam konteksnya; `friday plan KEY --diff` menampilkan selisih dari revisi sebelumnya. Jika revisi gagal, rencana tetap seperti semula dan menunggu persetujuan, dan keputusan tetap tercatat: ulangi `decide` yang sama. Selama rencana dari proses proyek menunggu persetujuan, `decide` melanjutkan sesinya dengan jawaban Anda dan menampilkan revisi rencana yang baru. Setiap `decide` seperti itu adalah kelanjutan sesi yang terpisah, jadi jawab semua pertanyaan rencana dalam satu teks. Dengan cara yang sama `decide` menjawab pertanyaan dari sesi eksekusi proses proyek yang berhenti. Hanya milestone yang disebutkan dan milestone yang bergantung padanya yang dibuka kembali. Tanpa `--reopen`, milestone berikutnya memperhitungkan keputusan tersebut. `resume` melanjutkan tugas yang berhenti atau gagal. `stop` menghentikan tugas yang sedang berjalan: agen berakhir bersama proses anaknya.

Pernyataan tugas yang asli disimpan utuh dan diteruskan kepada eksekutor dan review, sehingga hash dan URL yang persis tetap ada meskipun rencana meringkas fakta. Untuk kartu lama tanpa pernyataan tersimpan, gunakan `resume KEY --brief task.md`. Pernyataan dipulihkan hanya jika teksnya cocok dengan sidik jari perencanaan asli; teks lain memerlukan rencana baru. Persetujuan, tahap, dan penghitung anggaran tidak diatur ulang.

Ketika milestone yang gagal dilanjutkan, commit yang sudah dibuat mempertahankan batas review semula; tidak diperlukan commit kosong tambahan. Eksekutor mendapat kegagalan gate sebelumnya, dengan isi penuh traceback Python dalam batas keluaran diagnostik.

## Profil

Profil adalah berkas JSON. Kunci `extends` menyertakan profil lain (misalnya katalog model bersama); path bersifat relatif terhadap berkas profil.

| Kunci | Fungsi |
| --- | --- |
| `name`, `repository` | Nama proyek dan path ke repositorinya |
| `base_branch`, `worktree_root`, `branch_template`, `worktree_layout` | Dari mana branch tugas dibuat dan di mana diletakkan; secara bawaan `<repository>/{key}`, `branch_template` yang eksplisit memuat satu `{key}`, layout-nya `key` atau `branch` |
| `models`, `roles` | Katalog model dan preferensi peran (lihat di bawah) |
| `engineering_policy` | Aturan untuk perencana, eksekutor, review milestone, review akhir, dan perbaikan |
| `project_lessons` | Jebakan proyek yang terus ditemukan review: daftar pemeriksaan singkat. Eksekutor, review milestone, review akhir, dan perbaikan memeriksa perubahan terhadap daftar ini |
| `rules_docs` | Dokumen berisi aturan proyek. Friday membuat satu ringkasan darinya untuk perencana dan reviewer rencana (bawaan `AGENTS.md`, `CLAUDE.md`, `docs/*.md`). Ringkasan disimpan berdasarkan hash isi dan dipakai ulang oleh tugas selama dokumen tidak berubah; perencana tidak membaca dokumen secara penuh. Pola diperluas dari akar repositori, `**` menelusuri ke dalam folder (`docs/**/*.md`, `src/**/README.md`); hanya berkas yang ditemukan yang masuk ke sidik jari. Eksekutor, review milestone, review akhir, dan perbaikan mendapat aturan yang dipilih rencana, peta dokumen dari ringkasan, dan revisi basis tugas untuk mencari preseden; eksekutor mencari dengan `bin/friday-precedent <base> <pattern> [<path>…]` (pembungkus `git grep` yang tidak meloloskan opsi apa pun) |
| `repo_map`, `repo_map_budget`, `repo_map_mcp` | Peta repositori dalam prompt perencana dan reviewer rencana, agar mereka tidak menjelajahi struktur dengan pemanggilan tool. `none` (bawaan): tanpa peta. `builtin`: berkas yang dilacak beserta jumlah barisnya. `graphify`: ditambah simbol tiap berkas dan berapa banyak berkas yang mengimpornya, diambil dari graf [graphify](https://github.com/Graphify-Labs/graphify) (`uv tool install 'graphifyy[mcp]==0.9.100'`; ia hanya mem-parse kode, tidak memakai model; graf disimpan di `FRIDAY_HOME/maps`, bukan di repositori). Dalam pengukuran pada CS-2, peta tidak membuat perencanaan lebih murah (tanpa peta $6.19, `builtin` $7.08, `graphify` $7.97, masing-masing satu kali jalan), sehingga secara bawaan dimatikan. Peta di-cache per commit. Jika lebih panjang dari `repo_map_budget` karakter (60000), peta dipangkas dulu dengan membuang simbol, lalu dengan melipat folder. `repo_map_mcp: true` (hanya bersama `graphify`) memberi kedua peran kueri graf: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`; belum diverifikasi langsung di Codex. Reviewer rencana menerima teks terkini dari berkas yang disebut dalam rencana (hingga 40000 karakter) |
| `approval` | `owner` (bawaan): rencana menunggu `approve`. `auto`: rencana disetujui otomatis setelah review dan pipeline langsung dimulai; jurnal mencatat bahwa rencana disetujui secara otomatis |
| `limits` | `stage_files` dan `stage_lines`: batas sebuah tahap (10 dan 500); `task_milestones` dan `task_stages` yang opsional membatasi seluruh rencana sebelum dijalankan |
| `toolset`, `project` | Siapa yang menjalankan sebuah fase: `{"plan": "project", "execute": "friday"}` berarti proses proyek menulis rencana dan Friday menjalankannya (kedua fase bawaannya `friday`). `project`: `plan_command` dengan `{statement}` adalah perintah perencanaan proyek, misalnya `"/plan-stages {statement}"`; `plan_file` adalah berkas rencana di worktree; `execute_command` dan `stage_argument` dengan `{stages}` untuk fase eksekusi; `session_env` menyebut variabel lingkungan yang diterima sesi selain yang biasa (misalnya `SSH_AUTH_SOCK` untuk `git fetch`); `disallowed_tools` adalah tool yang ditutup bagi sesi (misalnya browser pemilik: akseptasi dilakukan oleh peran `browser` milik Friday); `timeouts` adalah `idle`, `tool`, `total` dalam detik ([ADR 0015](../adr/0015-project-toolset.md)) |
| `worktree_setup` | Perintah yang dijalankan Friday di worktree baru sebelum perencanaan (dependensi dan sejenisnya): larik argumen dengan substitusi `{repository}` dan `{worktree}`; harus dapat diulang. Contoh untuk npm di macOS: `["sh", "-c", "[ -e node_modules ] \|\| cp -cR {repository}/node_modules node_modules"]` |
| `executor_commands` | Perintah yang boleh dijalankan sendiri oleh eksekutor, dalam bentuk persis: `"python3 -m pytest"`, bukan `python` |
| `executor_deny_read` | Path tambahan yang tidak dapat dibaca oleh shell eksekutor |
| `executor_tiers` | Tingkat yang diizinkan untuk semua agen penulis, misalnya `["strong", "efficient"]`. Tanpa field ini semua tingkat diizinkan. Kompleksitas, eskalasi, kuota, dan perbaikan akhir mematuhi batas ini |
| `milestone_rounds` | Berapa putaran eksekutor yang didapat sebuah milestone (4) |
| `max_parallel_milestones` | Milestone independen yang siap dengan `parallel=true` yang berjalan bersamaan (2); `1` menjalankannya satu per satu |
| `budget` | `max_model_runs` dan `max_milestone_runs` positif yang opsional: batas proses yang diizinkan untuk semua peran per tugas dan per milestone. Reservasi bersifat atomik; percobaan yang gagal dan belum selesai ikut dihitung, dan `resume` serta pembukaan kembali tidak mengatur ulang penghitung. Saat habis, tugas berhenti dengan `budget_exhausted`; anggaran diubah secara eksplisit di profil. Yang dibatasi adalah jumlah proses, bukan biaya |
| `final_review_roles` | Secara bawaan `["final-review", "blind-code"]`; `["final-review"]` mempertahankan satu pemeriksaan akhir. Hasil yang sudah selesai disimpan secara independen dan dipakai ulang hanya jika sumber, rencana, keputusan, pengaturan, dan masukan peran tidak berubah |
| `gate`, `gate_image`, `gate_mode`, `gate_*` | Perintah pemeriksaan di Docker; `git-diff` membandingkan dengan basis tugas. Profil menjelaskan cara membangun image gate sebagai sebuah langkah (`steps`), dan `gate_image_step` menamai langkah itu. Jika `gate_lockfile` di image berbeda dari milik tugas, tugas berhenti: `status` menampilkan "Perlu langkah pemilik" beserta perintah langkahnya; setelah langkah itu, `resume` mengulang pemeriksaan dan tidak membangunkan sesi eksekusi dari proses proyek |
| `environment_errors` | Pola baris log yang berarti kegagalan lingkungan, bukan kegagalan kode |
| `browser`, `preview`, `behavior_test_policy` | Lingkungan uji, preview, dan aturan akseptasi di browser. Backend preview mencakup `storybook` (showcase dari `stories` dengan snapshot kit di `mount`, [ADR 0008](../adr/0008-ui-kit-preview-and-design-check.md)). Untuk `storybook`, semua yang spesifik proyek ada di profil: `command` (larik argumen yang memulai showcase; `{mount}` adalah path kit), `port`, `env`, `tmpfs` (path kontainer absolut yang boleh ditulis), `links` (tautan dari snapshot ke dalam image, misalnya `{"node_modules": "/app/node_modules"}`); image-nya adalah `stories.image` |
| `stories` | Repositori kedua tugas, showcase komponen (Storybook) yang menyimpan worktree kit: `repository`, `base_branch`, `worktree_root`, `mount` (wajib: path kit di dalam showcase), `setup` (perintah di worktree baru; `{repository}`, `{worktree}`, `{kit}`), `commands` (pemeriksaan eksekutor), `image` (image preview), `themes` (tema yang masing-masing dipakai akseptasi di browser untuk membuka story dan membandingkan status komponen) dan `theme_query` (wajib bersama `themes`: parameter URL tema dengan `{theme}`). Berkas showcase ditulis dalam rencana sebagai `stories:src/stories/X.stories.ts`; hasilnya adalah branch tugas di kedua repositori |
| `steps` | Langkah proyek yang tidak diketahui Friday dengan sendirinya; hanya pemilik yang menjalankannya (`friday step NAME [KEY]`, tanpa nama berarti daftar dan statusnya) ([ADR 0011](../adr/0011-profile-steps.md)): `{"<name>": {"run": [...], "scope": "task" \| "profile", ...}}`. `run` adalah larik argumen yang berjalan di host; langkah tugas mendapat `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`, langkah apa pun mendapat `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}`, `{secret.<name>}`. `description`, `env` (tanpa nilai rahasia), `cwd`. `lock` adalah sumber daya bersama selama langkah berjalan: path berbagi kunci repositori, nama adalah kunci bernama. `commit: {"paths": [...], "message": "{key}: ..."}` membuat Friday melakukan commit pada path ini; langkah menjadi usang jika branch berubah di luar path tersebut setelah commit-nya. `required` (langkah tugas): selama langkah belum selesai atau usang, `status`, jurnal, dan teks MR mengingatkannya beserta perintahnya. `check` (langkah profil) adalah perintah kesiapan untuk `doctor`: 0 siap, 2 usang (!), selain itu hilang (✗). `secrets: {"<name>": "<path>"}` adalah berkas yang diterima perintah lewat path; Friday tidak membacanya. Letakkan prosedur yang rumit dalam skrip di sebelah profil |
| `design` | Tool desain untuk tugas UI ([ADR 0007](../adr/0007-design-tools.md)). `figma: {"url": "http://127.0.0.1:3845/mcp"}` adalah server MCP Dev Mode lokal milik Figma desktop; `tools` mempersempit tool baca (`get_metadata`, `get_design_context`, `get_screenshot`, `get_variable_defs`), tool tulis tidak diterima. Jika tiket memiliki tautan `figma.com/design/…?node-id=…`, `start` memeriksa bahwa node terbuka di tab Figma yang aktif, dan perencana serta reviewer rencana membaca frame dan menulis spesifikasi terukur ke dalam rencana. Eksekutor dan review mendapatkannya dalam prompt, tanpa akses ke Figma. Friday menyimpan tangkapan layar frame di folder tugas; akseptasi di browser membandingkan preview dengannya dan mengukur gaya (`computed_style`): selisih pada angka spesifikasi memblokir, selisih yang hanya terlihat dengan mata masuk ke temuan minor MR. Jika Figma tidak menjawab atau node tidak ada, `start` berhenti dan menyebut apa yang harus dibuka; `start --no-design` merencanakan tanpa mockup. `impeccable: {"skill_dir": ".../skills/impeccable", "references": {...}}` menyebut berkas di `reference/` skill /impeccable yang dimasukkan Friday ke prompt milestone UI; `references` wajib dan memetakan peran `develop`, `review`, `final-review` ke daftar berkas (misalnya `{"develop": ["polish.md"]}`) |
| `tracker` | Yandex Tracker (API atau MCP), dipakai untuk membaca deskripsi tugas |
| `journal` | Tempat menulis jurnal tugas: `[{"kind": "markdown", "dir": "...", "page": "{key}/Friday.md"}, {"kind": "jsonl", "dir": "..."}]`; `page` adalah path halaman tugas di dalam `dir` (bawaan `{key}.md`), misalnya ke folder tugas di Obsidian. `journal_dir` dan `journal_page` adalah bentuk singkat untuk satu jurnal markdown; `journal` yang ditetapkan di profil (atau diwarisi) mengalahkan keduanya. Friday tidak menyentuh halaman yang tidak ia tulis (tanpa `friday_generated` di front matter): ia mencetak bahwa halaman itu dilewati dan menulis sisanya |
| `delivery` | `{"transport": "github" \| "gitlab" \| "none", "target_branch": "..."}` dan kunci `github.repository` atau `gitlab.base_url` + `gitlab.project` |

Nama repositori diambil dari URL `origin` (HTTPS, SSH, atau path lokal), tanpa `.git`; jika tidak ada `origin`, dari nama repositori utama di disk, termasuk saat bekerja dari worktree tertaut. Karakter di luar `A–Z`, `a–z`, `0–9`, `_` dan `-` menjadi `-`, dan `-` di awal dan akhir dihapus. Nama yang kosong memerlukan `branch_template` yang eksplisit. Kunci tugas lengkap dipertahankan: `31` menghasilkan `octis/31`, `OCTIS-031` menghasilkan `octis/OCTIS-031`. Branch yang sudah tercatat di kartu tugas dipertahankan saat tugas dilanjutkan; pengaturan baru berlaku untuk tugas baru. Showcase yang tertaut memakai nama repositori utama tugas.

### Model dan peran

```json
"models": {
  "fable": {"model": "claude-fable-5-2", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "strength": 1, "scarce": true, "effort": "high"},
  "opus-high": {"model": "claude-opus-5-5", "vendor": "anthropic", "driver": "claude", "tier": "frontier", "effort": "high"},
  "glm-high": {"model": "glm-5.3", "vendor": "zai", "driver": "claude", "tier": "strong", "effort": "high",
               "token_file": "~/.config/friday/zai.env", "token_key": "ZAI_API_KEY"}
},
"roles": {"plan": ["fable"], "develop": ["glm-high"], "review": ["opus-high"]}
```

- `driver`: apa yang menjalankan model, `claude` atau `codex`. Z.ai berjalan melalui Claude Code; token dibaca dari berkas yang hanya dapat diakses pemiliknya.
- `tier`: `frontier`, `strong`, atau `efficient`; `strength` mengurutkan model dalam satu tingkat.
- `effort`: kedalaman penalaran (`low` … `max`); satu model dapat dideskripsikan beberapa kali dengan effort yang berbeda.
- `scarce`: model yang mahal; dipakai sekali per tugas jika aturan mengizinkan tugas berjalan tanpanya.
- `price`: harga per juta token menurut jenisnya (`input`, `output`, `cache_read`, `cache_write`), dipakai untuk memperkirakan pengeluaran ketika vendor tidak melaporkan harga.

Peran: `plan`, `plan-review`, `develop`, `review`, `final-review`, `blind-code`, `browser`. Daftar di `roles` adalah preferensi: jika daftar tidak memuat model yang cocok, Friday mengambil model lain dari katalog. Aturan keras: hanya model `frontier` yang mereview kode, reviewer tidak lebih lemah daripada penulis pekerjaan, dan pemeriksaan buta tidak dilakukan oleh penulis kode. Aturan lunak, berurutan: bukan model yang sama dengan penulis; model mahal sekali saja; vendor yang berbeda; pemeriksaan buta tidak oleh penulis rencana. Aturan lunak hanya boleh dilanggar jika tidak ada jalan lain, dan pelanggarannya dicatat dalam riwayat tugas.

Contoh penugasan peran ada di [examples/models.json](../../examples/models.json).

Dengan `executor_tiers`, milestone yang kompleks memakai tingkat tertinggi yang diizinkan, dan penggantian karena kuota mempertahankan tingkat yang dibutuhkan dalam batas itu. Penugasan peran lama dengan eksekutor yang terlarang diganti dengan yang diizinkan; penulisan oleh model yang terlarang, atau yang tidak cocok dengan katalog, ditolak. Tingkat dan nama berasal dari katalog profil; Friday tidak menyimpulkannya dari nama model.

Milestone paralel mendapat worktree sendiri dan diintegrasikan sesuai urutan rencana. Friday memeriksa tumpang tindih path yang dideklarasikan sebelum mulai dan perubahan yang sebenarnya sebelum integrasi. Pekerjaan yang tidak dapat diintegrasikan disimpan di branch dan worktree-nya; `parallel_recovery_required` menyebutkannya sebelum tugas dilanjutkan. Setelah meninjau pekerjaan yang dipertahankan, pengendali menyelesaikan pemindahannya atau menyimpan commit yang diperlukan secara terpisah, lalu menghapus worktree dan branch lane yang sudah ditinjau dengan perintah Git biasa. Friday tidak menghapus hasil seperti itu secara otomatis untuk mencoba lagi.

Review akhir yang tersimpan terikat pada worktree yang bersih, commit di kedua repositori, rencana, keputusan, pengaturan model, dan teks persis masukan peran. Perubahan masukan selama pemeriksaan mengembalikan `stale_evidence`. Ketika peran kedua gagal, peran pertama yang sudah selesai dipertahankan; `resume` berikutnya hanya menjalankan pemeriksaan yang kurang untuk masukan yang sama. Menaikkan `budget` dan mengubah `max_parallel_milestones` mempertahankan review yang sudah selesai: pengaturan ini mengendalikan izin dan penjadwalan, bukan isi pemeriksaan.

## Jurnal

Kartu tugas adalah satu-satunya sumber kebenaran. Jurnal menampilkannya dan memperbarui diri setelah peristiwa penting: rencana siap dan disetujui, milestone selesai atau gagal, keputusan pemilik, review akhir, MR, penghentian. Untuk memperbaruinya secara manual, jalankan `friday journal KEY`.

Waktu adalah jumlah durasi proses, termasuk yang paralel, bukan waktu kalender. Untuk proses baru tanpa durasi dari penyedia, runner mengukurnya sendiri. Gangguan sebelum runner mulai mencatat waktu eksekusi nol; proses baru yang tidak terukur mempertahankan durasi yang tidak diketahui. Peristiwa lama yang tertaut memberi perkiraan yang ditandai secara eksplisit dan dapat mencakup waktu menunggu slot. Proses yang hilang tanpa pengukuran memiliki durasi yang tidak diketahui. Harga yang tidak diketahui juga ditampilkan per peran; ia tidak menjadi biaya nol.

- `markdown`: halaman `KEY.md` dan satu halaman ikhtisar bersama yang mendaftar semua tugas. Untuk Obsidian, atur folder vault: halaman memiliki front matter (key, state, pengeluaran, tag `friday`), dan tugas dihubungkan dengan wiki link. Halaman tugas berisi rencana beserta asumsi dan temuan yang belum terselesaikan, milestone beserta ringkasan eksekutor dan commit-nya, temuan yang disengketakan, keputusan, pengeluaran per peran, dan lini masa.
- `jsonl`: semua peristiwa tugas, untuk dianalisis di spreadsheet atau dasbor.

Templat berupa Markdown dengan substitusi `{{key}}`, `{{state}}`, `{{status}}`, `{{plan}}`, `{{milestones}}`, `{{disputes}}`, `{{decisions}}`, `{{costs}}`, `{{timeline}}`, `{{notes}}`. Friday mengambil templat dari field `template` pada target, lalu `.friday/task.md` di repositori proyek, lalu templat bawaan ([friday/templates](../../friday/templates)). Teks di antara `<!-- friday:notes -->` dan `<!-- /friday:notes -->` adalah milik Anda: teks itu dipertahankan pada setiap pembaruan. Friday tidak menimpa halaman yang tidak ia tulis.

## Pengaturan mesin

`FRIDAY_HOME/machine.json` menetapkan sumber daya bersama untuk semua tugas:

```json
{"slots": {"gate": 2, "browser": 2, "vendor:zai": 2}, "ports": [5200, 5399]}
```

Secara bawaan, satu gate dan dua browser berjalan bersamaan, dan vendor tidak dibatasi. Kuota vendor dilacak secara otomatis: proses yang menabrak batas mencatat kapan kuota kembali, dan sampai saat itu vendor dilewati saat memilih model.

### Antrean tugas: `friday serve`

`friday serve` adalah proses yang berjalan lama dengan satu antrean tugas yang disetujui per mesin ([ADR 0014](../adr/0014-work-pool.md)). Selama ia berjalan, `approve`, `resume`, dan jawaban yang diberikan dengan `decide` kepada sesi eksekusi tidak memulai tugas sendiri, melainkan memasukkannya ke antrean; tanpa itu, tugas berjalan sebagai proses latar belakang terpisah seperti sebelumnya, dan `resume` berjalan di terminal.

- Paling banyak `max_workers` tugas berjalan bersamaan (`machine.json`, bawaan 2); tugas yang dimulai di luar antrean juga dihitung.
- Antrean mengikuti waktu rencana disetujui; tugas yang dilanjutkan setelah `decide` didahulukan. `friday status` menampilkan antrean dan status server, `friday stop` mengeluarkan tugas dari antrean.
- Tugas "berjalan" yang prosesnya mati (tidur, restart) dikembalikan oleh server ke antrean sebagai `resume`.
- Ketika tugas berhenti pada pertanyaan atau langkah pemilik, gagal, atau selesai, notifikasi sistem datang (`osascript` di macOS, `notify-send` di Linux).

Bagi server, satu tugas adalah satu pekerjaan: milestone tidak dipecah menjadi pekerjaan, dan belum ada batas per tugas.

`friday service print|install|uninstall` memasang server sebagai layanan pengguna: agen launchd (`~/Library/LaunchAgents/local.friday.serve.plist`) atau unit systemd. Layanan dimulai dengan lingkungan kosong, jadi berkasnya menyebut semuanya sendiri: `PATH` dari direktori `claude`, `codex`, `docker`, `git` (serta `glab`, `gh`, `uvx`, `node`, `npx` jika ada), `FRIDAY_HOME`, `HOME`. `friday service check --profile P` menjalankan `friday doctor` persis di lingkungan itu, sehingga sebelum memasang Anda melihat apa yang tidak akan ditemukan layanan. Apakah layanan menemukan login langganan Claude, baru terlihat dari tugas pertama di bawahnya. Layanan berbicara dalam bahasa yang disimpan dengan `friday config language`.

## Batasan

- **Sandbox eksekutor.** Shell eksekutor (Claude Code) berjalan di dalam sandbox: tanpa jaringan, tanpa pembacaan `~/.ssh`, `~/.aws`, `~/.config` dan sejenisnya, hanya menulis ke worktree dan folder sementara, serta tidak boleh berjalan di luar sandbox. Perintah di luar `executor_commands`, perintah git (`add`, `commit`, `status`, `diff`, `log`, `restore`), dan `bin/friday-precedent` akan ditolak. Codex berjalan di sandbox-nya sendiri dengan batasan yang sama.
- **Git di Codex.** Friday menaruh Git yang terpasang dan salinan terpisah metadata Git ke dalam runtime tugas. Konfigurasi Git global dan profil shell pengguna tidak dimuat; data layanan repositori sumber tidak diperlihatkan kepada agen. Eksekutor menyimpan tahap dengan perintah Git biasa. Setelah prosesnya berakhir, Friday mengambil commit melalui bundle yang terverifikasi dan mengembalikannya ke branch sumber jika HEAD dan indeksnya tidak berubah. Jika terjadi konflik status, bundle tetap ada di log proses sebagai `git-recovery.bundle`; tidak ada yang ditimpa secara otomatis. Reviewer mendapat metadata Git hanya-baca. `doctor` memeriksa skenario nyata tiga commit di worktree tertaut tanpa memanggil model, serta bahwa larangan membaca rahasia dan larangan menulis bagi reviewer berlaku.
- **Reviewer** hanya membaca. Pemeriksaan buta berjalan di folder kosong.
- **Gate** berjalan di kontainer tanpa akses jaringan, pada snapshot commit yang di-mount hanya-baca.
- **Browser** hanya menerima tool Friday untuk satu preview (termasuk `hover` dan `computed_style`, yang membaca gaya dengan skrip tetap, tanpa `evaluate_script`); melewati otorisasi dan membaca header permintaan yang terotorisasi dilarang.
- **Figma** hanya dibaca oleh perencana dan reviewer rencana, dan hanya dengan tool baca dari server Figma desktop lokal. Skill /impeccable tidak berjalan di dalam peran: Friday memasukkan teksnya ke prompt.
- **Publikasi.** Friday hanya mem-push branch tugasnya sendiri dan hanya membuka draft MR/PR. Ia tidak menimpa branch orang lain, tidak melakukan merge, dan tidak men-deploy.
- **Belum diverifikasi langsung:** akseptasi di browser dan publikasi ke GitLab telah diverifikasi lewat tes dengan agen palsu. Git di lingkungan Codex juga diperiksa oleh lab lokal nyata tanpa memanggil model; proses sebuah peran oleh model diperiksa terpisah pada setiap tugas.
