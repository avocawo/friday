# Сборки и другие проектные процедуры — шаги профиля, а не команды Friday

После ADR 0008 и 0010 в Friday появились две команды, знающие устройство одного проекта. `friday image build` собирала образ витрины: BuildKit-секрет, `--add-host`, `git archive` базовой ветки, метка lockfile. `friday dist` повторяла процедуру сборки dist одного UI-кита в контейнере его хост-проекта: пути внутри контейнера, переменные окружения, удаление вложенных пакетов, текст коммита. Кроме того, в коде лежали значения по умолчанию одного проекта: путь кита в витрине, команда запуска Storybook с путями `node_modules`, имя пакета, файлы /impeccable. Владелец решил, что Friday не знает конкретных проектов и способов их сборки. Всё проектное указывается в профиле.

**Шаг профиля.** Профиль описывает шаги в `steps`. Friday умеет только общие вещи: выполнить шаг по команде владельца, проверить его готовность, показать результат и состояние, напомнить о невыполненном. Пример — с вымышленными именами:

```json
"steps": {
  "bundle": {"scope": "task", "required": true, "lock": "{repository}",
             "description": "Собрать dist и закоммитить его",
             "run": ["{profile_dir}/build-bundle.sh", "{worktree}", "{head}"],
             "commit": {"paths": ["dist"], "message": "{key}: build dist"}},
  "preview-image": {"scope": "profile",
                    "run": ["{profile_dir}/image.sh", "build", "{secret.registry}"],
                    "check": ["{profile_dir}/image.sh", "check"],
                    "secrets": {"registry": "~/.npmrc"}}
}
```

- **Кто запускает.** Только владелец: `friday step NAME [KEY] [--profile P]`. Конвейер шаги не запускает: так безопасно для шагов, которые трогают чужой checkout или работающие контейнеры хоста. `friday step` без имени (или `--list`) печатает шаги профиля с `description`, а при указанном ключе задачи — ещё и состояние каждого task-шага. `--dry-run` печатает команду с подстановками и блокировку, ничего не запуская.
- **Команда.** `run` — массив аргументов, выполняется на хосте без shell. Подстановки зависят от `scope`. У шага задачи это `{key}`, `{worktree}`, `{branch}`, `{base}`, `{head}`, `{showcase}`. У любого шага — `{profile_dir}`, `{repository}`, `{base_branch}`, `{stories_repository}` и `{secret.<имя>}`. Подстановку, которой у шага нет, профиль не пройдёт. `env` и `cwd` — для процесса на хосте. В `env` не кладите значения секретов: команда и окружение печатаются в терминал.
- **Блокировки.** На время шага задачи Friday держит блокировку задачи и отказывается работать, пока по задаче идёт `friday run`. `lock` — общий ресурс шага, как `resource_group` в GitLab: путь (например `{repository}`) делит блокировку репозитория, которую Friday сам берёт при создании рабочих копий, любое другое значение — именованная блокировка. Занятый ресурс — ошибка `lock_timeout`, а не ожидание.
- **Результат.** `commit` — после успешного шага Friday коммитит в ветку задачи только перечисленные пути с сообщением из профиля. Если рабочая копия была не чистой, шаг не запускается. Если шаг оставил изменения вне своих путей, Friday их показывает. Неуспешный запуск записывается как «последний запуск упал».
- **Состояние.** Task-шаг с `commit` выполнен, пока ветка после его коммита не менялась вне `commit.paths`; иначе он «устарел» (проверка `git diff --quiet <коммит шага> HEAD -- . ':(exclude)<пути>'`). `required` — пока шаг не выполнен или устарел, `friday status`, журнал и текст MR говорят об этом с командой; упавший последний запуск показывается у любого шага. Состояние считается по ветке и карточке при каждом показе, а не хранится. После шага Friday переписывает сохранённый текст MR. Если ветка уже была доставлена, он напоминает, что коммит шага ещё надо запушить, а текст MR на сервере не обновлён.
- **Готовность для doctor.** `check` (шаг профиля) — команда готовности: код 0 — готово, 2 — устарело (предупреждение), любой другой — нет (✗). Последняя строка вывода — причина, к ней Friday добавляет команду запуска шага. Значит, `doctor` теперь выполняет команды профиля, а не только читает состояние (до 120 с на проверку).
- **Секреты.** `secrets` — файлы, которые команда получает путём. Friday только проверяет, что файл есть, и никогда его не открывает.

Процедуру длиннее одной команды профиль кладёт скриптом рядом с собой, вне репозитория Friday. Восстановление чужого checkout при ошибке или прерывании — тоже забота скрипта. Скрипт, который запускает работу в контейнере, сам останавливает её там при прерывании: `docker exec` не передаёт сигнал внутрь. Прерывать такой шаг не стоит. Если всё же прервали, проверьте заимствованный checkout (`git status`) и что в контейнере не осталось процесса сборки, и только потом запускайте шаг снова.

**Без проектных значений по умолчанию.** Обязательными стали поля, у которых раньше были проектные значения по умолчанию: `stories.mount`, `stories.theme_query` (при `themes`), `design.impeccable.references`. У бэкенда preview `storybook` в профиле указываются `command` (`{mount}` — путь кита), `port`, `env`, `tmpfs` и `links`. Ошибка профиля называет недостающее поле.

## Considered Options

- **Шаги, которые запускает конвейер (`before_delivery`), и шаги в контейнере (`container`).** Были в первой версии и убраны: ни один профиль ими не пользовался. Коммит конвейерного шага уходил бы в доставку мимо гейта, а для контейнерного шага `cwd`, пути и секреты хоста внутри контейнера ничего не значили. Вернуть их можно, когда появится реальный шаг.
- **Поля `preconditions`, `sources`, `outputs`, `confirm`.** Не нужны: `check` с кодами 0, 2 и 1 уже различает «нет» и «устарело» (как `status` в Taskfile), свежесть task-шага Friday видит по git, а подтверждение без терминала невозможно и для шага, который владелец запустил сам, избыточно.

- **Оставить проектные команды и вынести только значения в профиль.** Отклонено: способ сборки — это последовательность действий, а не набор параметров. Каждый новый проект потребовал бы новых ключей и веток в коде.
- **Скрипты в репозитории Friday.** Отклонено: это то же проектное знание, только в другом файле.

## Consequences

- Команд `friday image` и `friday dist` больше нет; ADR 0010 и раздел про сборку образа в ADR 0008 заменены этим решением.
- Отметка `dist` в карточках, сделанных до шагов, читается как выполненный шаг `dist`.
- Известный долг: у бэкенда preview `docker-vite` в `friday/isolated_preview.py` остались проектные значения — переменные Apollo (`VITE_API_APOLLO_URI`, `VITE_APP_ENV`), `/app/node_modules`, путь к `vite.js`, порт 5173, размеры tmpfs. Их нужно вынести в профиль так же, как у `storybook`; это отдельная задача.
- Friday проверяет подстановки, коммит результата, проверку `doctor` и то, что секреты не открываются. Что делает сам скрипт, в том числе возвращает ли он чужой checkout при ошибке, Friday не проверяет: это ответственность профиля.
