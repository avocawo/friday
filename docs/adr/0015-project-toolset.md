# Режим инструментов проекта

Сессии Friday запускаются со своим списком инструментов, `--restricted`,
`--strict-mcp-config` и своей песочницей (`Claude.command` в `friday/runner.py`), поэтому
скиллы, агенты, хуки и MCP проекта им недоступны, а процесс планирования и исполнения
зашит в Friday.

Решение: `"toolset"` в профиле, по фазам (`plan`, `execute`), значение `project`.
Сессия запускается как обычная сессия Claude Code в рабочей копии задачи — с настройками, хуками, скиллами, агентами и MCP проекта.
Friday задаёт только модель, усилие, сессию, режим разрешений (`--permission-mode auto`),
схему отчёта и закрытые сессии инструменты из профиля (браузер владельца). Окружение сессии — то же, что у ролей Friday, плюс переменные из
`session_env` профиля (например, агент SSH для `git fetch`). Профиль
называет команды проекта для плана и исполнения, файл плана и аргумент выбора этапов.

| Фаза | Кто делает |
|---|---|
| Подготовка рабочей копии | `worktree_setup` профиля после её создания |
| План | команда плана проекта со своими проверками и внешним ревью; этапы, зависимости, файлы, признак интерфейса и критерии приёмки — в итоге сессии по схеме Friday |
| Утверждение | владелец читает файл плана проекта, `friday approve` |
| Исполнение | команда исполнения проекта, одна сессия на поток (ADR 0013, 0014) |
| Вопрос | сессия завершается вопросом; после `friday decide` — `--resume` |
| Проверки | Friday после сессии: изолированный гейт по коммиту, размер этапов по `git diff --numstat`, чистое дерево; проверки проекта внутри сессии идут его средствами |
| Приёмка в браузере | роль `browser` Friday после сессии, по этапам с интерфейсом; сессия проекта браузер не открывает |
| Сдача | Friday, как сейчас |

Команды проекта в режиме Friday не ждут человека: шаг «покажи и жди» завершает сессию
отчётом или вопросом.

Что Friday делает с сессией:

- Подготовка рабочей копии с ненулевым кодом выхода останавливает задачу до команды
  плана, как сейчас `worktree_setup`: без неё у сессии нет скиллов и агентов проекта, и
  процесс проекта молча идёт по другому пути.
- Итог сессии — последнее событие `result` потока `stream-json` после выхода процесса.
  Сессия может запустить фоновую задачу, закончить ход промежуточным отчётом и
  продолжиться, когда задача закончится; тогда в потоке несколько `result`, и первый —
  не итог.
- Вопросы и итог сессия отдаёт по схеме отчёта Friday. Процесс проекта без раздела для
  Friday заканчивает план вопросами в прозе и «жду утверждения»; такой ответ Friday не
  разбирает, а показывает владельцу как вопрос без вариантов.
- Сессию, которая закончила без вопросов, Friday продолжает, только когда ей есть что
  сказать: вопрос проверки после неё или ответ владельца. Если задачу остановил сбой
  окружения, `resume` повторяет одни проверки: на пробе такой пустой ход сессии после
  остывшего кэша стоил $13–14 и ничего не менял.

## Considered Options

- **Тексты скиллов в промптах ролей Friday** — проза не исполняется сама, а шаги HITL
  и внешнего ревью противоречат конвейеру.
- **Скиллы внутри песочницы Friday** — песочница закрывает учётные данные и сеть, без
  которых внешнее ревью скилла не работает.

## Consequences

- Изоляции Friday нет: сессия имеет права интерактивной сессии владельца, границы
  держат разрешения и хуки проекта.
- Сессия исполнения идёт на модели роли `develop`; модели ревьюеров внутри неё выбирает
  процесс проекта. После сессии роли Friday проверяют как обычно: браузер, финальное ревью.
- Только Claude Code.

## Решения владельца

1. Разрешения — `auto` явным флагом: прогон не зависит от настроек владельца, пробный
   прогон прошёл без единого отказа. `bypassPermissions` снимает последнюю границу в
   режиме без изоляции, свой список не покрывает десятков команд одного плана.
2. Финальное ревью Friday остаётся поверх процесса проекта: это единственная проверка,
   не зависящая от него. Выключать — по итогам нескольких задач. Карты документов
   дайджеста у этого режима нет, а правила плана выбрал его автор, поэтому финальное
   ревью сначала читает `AGENTS.md` (или `CLAUDE.md`) в корне репозитория и сверяет дифф
   со всеми разделами документов проекта, которые он затрагивает. Слепая проверка
   документов не получает: она остаётся независимой от плана.
3. Режим задаётся по фазам: `"toolset": {"plan": "project", "execute": "project"}`.
   Фазу плана проверил прогон на проекте, исполнение — пока только тесты.
4. Сессия исполнения идёт на модели роли `develop` раскладки, а не на модели плана: код
   пишет модель исполнителя. Этап сессия коммитит с его номером из сводки плана в теме, по
   нему Friday находит коммиты этапа для проверки размера.
