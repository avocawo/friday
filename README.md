<h1 align="center">Friday</h1>

<p align="center"><strong>Личный конвейер разработки, который приближает пятницу.</strong><br>
От задачи до чернового MR: сильные модели планируют и проверяют, недорогие пишут код.</p>

<p align="center">Python 3.9+ · macOS / Linux · <a href="LICENSE">MIT</a> · ранняя версия</p>

---

```text
задача → план (сильная модель) → проверка плана (другой вендор) → ваше утверждение
       → вехи: исполнитель в песочнице → гейт → ревью вехи → браузерная приёмка UI
       → финальное ревью + слепая проверка → черновой MR
```

Вы утверждаете план и принимаете черновой MR. Конвейер исполняет план в пределах настроенного бюджета; исчерпание бюджета или сбой среды возвращаются владельцу. Спорные замечания ревью уходят вместе с MR.

## Что важно

- **Ветки по имени проекта.** По умолчанию `start` создаёт `<репозиторий>/<ключ задачи>`, например `octis/31`. Имя берётся из Git `origin`; свой шаблон задаётся в профиле.
- **Модели по уровням, а не по именам.** В профиле — каталог моделей с вендором и уровнем (`frontier`, `strong`, `efficient`). Код смотрят только `frontier`-модели, ревьюер не бывает слабее автора, по возможности он другого вендора. Дорогую модель можно пометить, чтобы она шла один раз на задачу.
- **Дешёвый исполнитель с быстрой обратной связью.** Исполнитель сам запускает линтер, типы и тесты в песочнице без сети, а гейт отдаёт ему только упавшие проверки.
- **Ограниченный расход.** Профиль может запретить Frontier-исполнителей через `executor_tiers`, ограничить размер всего плана и число вызовов моделей через `budget`; `resume` счётчики не сбрасывает. Финальное ревью сохраняется по ролям: сбой второй проверки сохраняет уже полученный результат первой для неизменных входов.
- **Видно, что происходит.** `friday status` показывает фазу, модель, сколько агент молчит и сколько потрачено на каждую задачу.
- **Несколько задач сразу.** Каждая задача — своя ветка и рабочая копия. Сколько гейтов, браузеров и запусков одного вендора идёт одновременно, задаётся настройками машины.
- **Параллельные вехи.** Независимые готовые вехи работают в отдельных worktree, по умолчанию до двух; общие изменённые файлы блокируют интеграцию.

## Быстрый старт

Нужны Python 3.9+, Git, Claude Code и/или Codex CLI. Для гейта и браузерной приёмки нужен Docker.

```sh
git clone git@github.com:avocawo/friday.git && cd friday
mkdir -p profiles
cp examples/models.json examples/project-profile.json profiles/
# укажите в profiles/project-profile.json путь к репозиторию, команды проверки и гейт
./bin/friday doctor --profile profiles/project-profile.json
./bin/friday start TASK-1 --profile profiles/project-profile.json --brief task.md
./bin/friday approve TASK-1
./bin/friday status
```

## Команды

| Команда | Что делает |
| --- | --- |
| `start KEY --profile P [--brief F] [--no-design]` | Рабочая копия, план, проверка плана другой моделью; с `design` в профиле план сверяется с фреймом Figma из тикета |
| `plan KEY [--diff]` | Показать план с несогласованными замечаниями; `--diff` — что изменила последняя ревизия |
| `approve KEY [--no-run]` | Утвердить план и запустить конвейер в фоне |
| `status [KEY] [--json]` | Что делают задачи и сколько потрачено |
| `decide KEY name "текст" [--reopen M2]` | Решение владельца. Пока план ждёт утверждения, планировщик исправляет по нему названные вехи (без `--reopen` выбирает их сам), и повторную проверку проходят только изменённые ([ADR 0016](docs/adr/0016-decision-revises-the-plan.md)). После утверждения переоткрывает выполненные названные вехи, остальным добавляет решение в контекст. План и исполнение процесса проекта (`toolset`) продолжают свою сессию с ответом |
| `run KEY` / `resume KEY [--brief F]` / `stop KEY` | Исполнить в этом терминале, продолжить, остановить; `--brief` восстанавливает исходную постановку старой задачи по отпечатку планирования |
| `archive KEY [--force]` | Убрать рабочую копию и карточку; ветка остаётся |
| `journal KEY` | Обновить журналы задачи (Obsidian, jsonl) |
| `doctor --profile P` | Готовность машины и профиля |
| `step [NAME] [KEY] [--profile P] [--dry-run]` | Выполнить шаг профиля (`steps`): шаг задачи — с её ключом, шаг профиля — с `--profile`; без имени — список шагов и их состояние. Что делает шаг (сборка образа, бандла и т. п.), описывает профиль ([ADR 0011](docs/adr/0011-profile-steps.md)) |

Подробно о профиле, моделях и границах — в [руководстве](docs/guide.md). Почему конвейер устроен так — в [разборе пилота](docs/process-redesign.md) и [ADR](docs/adr/).

```sh
docker build -f Dockerfile.test -t friday-test:local .
./bin/test-offline
```

Тесты работают с временными данными и фейковыми агентами в контейнере без сети.
